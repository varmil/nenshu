# T4 在籍年数の推移 — plan.md

参照: Issue #835（親: #829）, `docs/timeseries/spec.md` 1.3・2.7・AC-5・AC-17〜AC-22, Claude Design `在籍年数推移.dc.html` の 1b
依存: #74（T0 データ）, #138（T2 の表）

## Context

企業詳細ページの推移は、平均年収（T1〜T3）と稼ぐ力（P2）の2つある。親 Issue #829 は、そこに**平均勤続年数（画面では「在籍年数」）の10年ぶん**を足すよう求めている。社員が長く働ける環境に「継続的に」近づいているかを、読者が判断する材料にするため。

モックは5案あり、運営者は **1b（折れ線＋業種の中央値）** を選んだ。「業界中央値が重すぎたら相談」とあったが、33業種×10年の中央値をビルド時に1回数えるだけなので、重くない。

**T3 と違い、データを取り直す必要がある。** `pipeline/data/salary_history.csv` は在籍年数の列を持っていない。ただし `edinet.to_record` は T0 の時点から `avg_tenure` を返しており、`history.py` が書き出していないだけ。**抽出を書き足す作業ではなく、書き出す作業になる。** 書類の ZIP（gitignore）はコンテナが変わると消えるので、落とし直すところから始める。

## 進め方

1. **書類を落とし直す。** 書類一覧（`warm_lists.py`）→ ZIP（`pipeline/performance/fetch.py`。`salary_history.csv` の `doc_id` を落とす）の順。3並列で約2時間。待つあいだに 2・6 を進める。
2. **`history.py` に `avg_tenure` の列を足す。** 列は `avg_age` の直後。CSV を読む側（`build-data.ts`・`unified.py`・`performance/`・`analysis/`）が列名で引いているか、位置で引いているかを先に確かめる。
3. **読み方が割れた年を点検する。** 2017・2018年は本文の表から拾っていて、平均年収の読みが割れた書類がある（`textblock._best`）。`history.resolve_candidates` が年収だけを選び直すと、在籍年数は選ばれなかった読みのまま残る。**割れた書類の件数と、選び直した年収と在籍年数の組を数えてから**直すかを決める。
4. **作り直した CSV を前の版と突き合わせる。** 在籍年数の列を除いて1文字も変わっていないこと。変わっていたら、書類一覧を取り直した日の違い（窓の後ろに足された提出）を疑う。
5. **在籍年数の値を点検する。** 採用書類の年が `ranking_unified_2026.csv` の `avg_tenure` と全社で一致するか。空欄の行がどれだけあるか。隣の年との差の分布が本文由来の年とタグ由来の年で同じ形か。
6. **`history.json` に `tenureById` と業種の中央値を出す。** 平均年齢（T3）と同じく `buildHistory` の同じループで組む。中央値は `companies.industries` と同じ並び。社数の少ない業種・年をどう扱うかは実データを見て決める。
7. **gzip を測る。** 180KB に届くなら、T3 と同じく誰に読まれているか（ビルド時だけか）を確かめてから上限を決め直す。
8. **パイプラインのテストで AC-17・AC-18 を固定する。**
9. **画面を作る。** 節・折れ線・表・説明文。折れ線は `SalaryCurveChart` の描き方（0起点にしない・各点に値・器の幅で文字を刻む）に揃え、欠損年は線をつながない。点のラベルが中央値の点線に重なる場合の逃がし方を決める。
10. **このページの出典（C12）に載せる。** 在籍年数の推移は実測値、業種の中央値は計算値。
11. **テストを書く。** 行・差・説明文・目盛りは Unit テスト、節が画面に届くこと・カードとの一致・欠損年は E2E（`e2e/company-refresh.spec.ts` の推移のテストの隣）。横スクロールは既存の 375px のループに任せる。
12. **測って出す。** `/company/6861` の HTML を前後で raw・gzip で測り、`/` が変わらないことを確かめる。
