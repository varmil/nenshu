# T2 平均年収推移の表 — plan.md

参照: Issue #138（親: #137）, `docs/timeseries/spec.md` 2.5・2.6（AC-12〜AC-14）と AC-10
依存: #74（T0 データ）, #83（T1 のグラフを同梱した C2）

## Context

推移の節はいま棒グラフだけで、各年の金額は棒の上の3〜4桁の数字として出ている。**「いくらか」は読めるが「どれだけ動いたか」は読者が引き算しないと出ない。** 10年の増減は1文（`buildHistorySummary`）で添えてあるが、これは最初と最後の2点だけで、途中の年ごとの動きは書いていない。

年齢別の推定年収は既に **表 → 説明文 → チャート** の順で並んでいる（C3）。推移も同じ順に揃えて、値は表で、形はグラフで読ませる。

**データは1バイトも増えない。** `history.json` は T0 が出したものをそのまま使い、前年比と累積は描画時の引き算で出す（Workers の CPU 予算に対しては1社×10年＝十数回の割り算なので、`findNeighbors` より軽い）。

## 進め方

1. **境界を確かめてから触る。** 推移は表示基準（実測値／年齢そろえ）と独立で、`byBasis` の外の `SalaryHistory` として渡っている（C2 の design.md）。表もこの外側に置く——`byBasis` 側から値を引くと「年齢そろえにしたら過去の有報の数字が変わる」を作れてしまう。
2. **比の算出を先に、描画から切り離して書く。** 「前年に値があるときだけ前年比を出す」「基準年はその会社で最初に値のある年」の2つは欠損の扱いそのもので、ここが表の正しさのほぼ全部になる。純関数にして先に単体テストで固める。**内部に欠損のある会社が33社ある**（例: 2117 は2023・2024が欠損）ので、その形を実データからテストに引く。
3. **表を組む。** 年齢別の表（`AgeSalaryTable`）と同じ器——罫線・中央寄せ・`TABLE_NO_VERTICAL_SCROLL`——を使う。2つの数表が同じページに並ぶので、見た目が違うと別の種類の情報に見える。
4. **節の並びを 表 → 説明文 → チャートにする。** 増減の1文はいまグラフの `figcaption` の中にいるので、表とグラフの間の `<p>` に出す。`figcaption` には軸の断りだけを残す。
5. **読み上げの経路を1つにする。** グラフが持っている `sr-only` の10件は表と同じ中身なので落とす（AC-10 の担い手が表に移る）。既存の E2E がこの `ul.sr-only` を当たり判定に使っているので、同じ PR で表の行へ寄せ替える。
6. **測って出す。** `/company/[id]` の初期HTMLサイズを raw と gzip の両方で測り直し、13,824 B（Issue #95 時点）からの増減を design.md に記録する。

## 着手前に見えている判断

**「昇給率」とは呼ばない。** 親 Issue の例は「昇給率」「累積昇給率」だが、有報の平均年間給与の前年差は個人の昇給ではなく、採用・退職による構成の変化を含む。**出す数字は親 Issue のとおりのまま、呼び名だけ「前年比」「基準年比」にする**（開発上の約束「根拠を隠した推定値を表示しない」と同じ線で、名前が中身より強い意味を主張しないようにする）。節の説明にも1行で断る。

**基準年は固定の2017年ではない。** 2017年の値を持たない会社が230社ある（T0 実測）。全社を2017年基準にすると、その230社の累積列が丸ごと空になる。**列の見出しに基準年を書く**（`2018年比` のように会社ごとに変わる）。

**表を折りたたまない。** 10行はそのまま置いても縦に長すぎない。SEO の受け皿という狙い（Issue #137）からも、初期HTMLに出ていることが要る。

```bash
cd web && npm run build
```

- 390px と 1280px の両方で横スクロールが出ないことを E2E で固定する（AC-14）
- 欠損のある会社（2117）のページを実際に開き、「データなし」の行と前年比の空欄を目で見る
- ライトとダークの両方を見る（罫線が増える）
- 表示基準を切り替えても表の値が変わらないことを E2E に足す（AC-8 の当たり判定を表に移す）
