# T0 10年ぶんの平均年収の取得 — plan.md

参照: Issue #74（親: #54）, `docs/timeseries/spec.md` 1.（AC-1〜AC-5）, ADR-0006
依存: #51（C0 企業IDの安定化）

着手前の段取り。**この Unit をどの順で作業し、どこで検証するか**だけを書く。使う技術の選定は ADR、出来上がりの内部構造は `./design.md`（型は `docs/AI-DLC実践リファレンス_v10.pdf` p.13）。

## 段取り

1. **書類一覧を10年ぶんキャッシュする。** 各年 6/1〜7/10 の平日のみ。
   *検証*: 取得日数と失敗数を数える。失敗0であること
2. **母集団（現行CSVの `edinet_code`）に絞って有報CSVを取得する。** 中断・再実行で続きから走ること。
   *検証*: 取得件数が spec AC-1 の 17,000〜18,000件に収まり、失敗が1%未満
3. **1年ぶんだけ抽出して現行CSVと突き合わせる。** 2026年で `avg_salary` が全社一致するか。
   *検証*: **ここが spec AC-3。一致しなければ抽出が壊れているので先に進まない**
4. **年ごとの抽出率と `source`（tag / textblock）の内訳を出す。**
   *検証*: 年ごとの取得社数を spec AC-2 の下限と比べる。**下限を割る年があれば、抽出を直すか対象年を狭めるかをここで決める**（判断は design.md に残す）
5. **2020年の落ち込みを切り分ける。** 提出期限延長で 6/1〜7/10 の窓から外れているのか、抽出の失敗か。
   *検証*: 窓を広げて再取得し、拾える件数が増えるかを実測する
6. **全年を抽出して年次CSVにする。**
   *検証*: 行数・年ごとの社数・重複（同一 `edinet_code` × 年）が無いこと
7. **`history.json` を出力に足す。**
   *検証*: spec AC-4（欠損が `null`・内挿なし）と AC-5（gzip 150KB以内）
8. **既存の出力が変わっていないことを確認する。**
   *検証*: `companies.json` / `stats.json` の中身と、`/` のHTMLサイズが変わらないこと

## 依存と前提

- 名寄せキーは `edinet_code`（ADR-0006）。証券コードは上場・廃止で変わる
- 抽出は現行パイプラインと**同じ関数**を通す。式も抽出ロジックも書き写さない——写すと片方の変更を取り逃す。手順3の突き合わせが成立するのもこれが前提
- 取得の窓（6/1〜7/10）は現行の母集団の集め方に合わせる。**窓を変えると母集団が変わり、年をまたいだ比較にならない**

## リスクと、どの手順で潰すか

| リスク | 潰す手順 |
| --- | --- |
| 10年のあいだに開示タグが変わっていて、古い年が取れない | 手順4（年ごとの `source` 内訳） |
| 抽出ロジックの修正が現行の2026年の値を動かす（共有コードのため） | 手順3（全社突き合わせ） |
| 2020年の落ち込みが窓のせいか抽出のせいか分からない | 手順5 |
| 同一年に訂正報告が複数あり、どれを採るか決まらない | 手順6（重複チェック） |
| `history.json` が予算超過 | 手順7（超えたら万円単位に丸める。表示も万円なので情報は落ちない） |
