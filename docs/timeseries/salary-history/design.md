# T0 10年ぶんの平均年収の取得 — design.md

参照: Issue #74（親: #54）, `docs/timeseries/spec.md` 1.（AC-1〜AC-5）, ADR-0006
段取りは `./plan.md`。ここには**出来上がった内部構造**を書く（型は `docs/AI-DLC実践リファレンス_v10.pdf` p.13）。

## ディレクトリ構成

```
pipeline/
  salary/
    warm_lists.py     書類一覧（cache/list_<date>.json）を並列で温める
    fetch_history.py  母集団に絞って有報CSVのZIPを cache/<docID>.zip に落とす
    history.py        キャッシュを展開して年次CSVにする
    edinet.py         （既存）API・ZIP展開・レコード化。T0 で応答検証と候補の受け渡しを追加
    textblock.py      （既存）本文の表から平均年収を拾う。T0 で2017〜2018年の書式に対応
    run.py            （既存）桁ズレ補正。T0 で小さすぎる側の補正を追加
  data/
    salary_history.csv   年次の実測値（このUnitの成果物）
  scripts/
    build-data.ts     `buildHistory` が history.json を出す
web/public/data/
  history.json        1,867社 × 10年
```

## データモデル

### `pipeline/data/salary_history.csv`

`(edinet_code, year)` が主キー。17,684行。

| 列 | 意味 |
| --- | --- |
| `edinet_code` | 名寄せキー。証券コードと違い年をまたいで変わらない（ADR-0006） |
| `year` | **書類の提出年**（決算年度ではない）。spec 2.1 の横軸に一致する |
| `avg_salary` | 提出会社単体の平均年間給与（円・整数） |
| `avg_age` / `employees_nonconsolidated` | 併せて取れるもの。v1 では表示しない |
| `source` | `tag`（XBRL要素）か `textblock`（本文の表） |
| `period_end` / `doc_id` | 出典。1行から元の有報に戻れる |

### `web/public/data/history.json`

```
{ "years": [2017, …, 2026], "byId": { "<企業ID>": [値 or null, …] } }
```

キーは `companies.json` の `id`（証券コード／EDINETコード）。値は円・整数、無い年は `null`。
gzip **65.6KB**（予算150KB）。**`/` は読まない**（Issue #22）。

## 取得の構造

```
warm_lists.py ──→ cache/list_<date>.json （2,609日ぶん・約2分）
                        │
fetch_history.py ───────┴──→ cache/<docID>.zip （17,917件・1.4GB・3並列で約45分）
                        │      universe() = 現行CSVの edinet_code 1,867社
                        │      targets()  = (code, year) ごとに docID 最大＝最後の提出
history.py ─────────────┴──→ data/salary_history.csv
                               edinet.to_record → resolve_candidates → run.fix_salary_typos
build-data.ts ──────────────→ web/public/data/history.json
```

**抽出は現行パイプラインと同じ関数を通す。** `edinet.to_record` と `run.fix_salary_typos` を
呼ぶだけで、式も抽出ロジックも書き写していない。2026年の値が `companies.json` と全社一致
すること（spec AC-3）が成立するのはこれが前提で、`build-data.test.ts` が固定している。

### 取得の窓は暦年ぜんぶ

母集団は2026年の1,867社に固定なので、**窓を広げても母集団は変わらない**。変わるのは
「その会社がその年に出した有報を見つけられるか」だけである。6/1〜7/10 に限ると2020年が
1,655社まで落ちるが、これは COVID期の提出期限延長で**96社が窓の外（7〜10月）に出ていた**
ためで、通年に広げて1,748社になった。追加の取得は10年で210件だった。

### EDINET の流量制限は HTTP 200 で来る

本文が `{"StatusCode":"429","message":"Too Many Requests"}` の JSON になるだけで、
`urlopen` は例外を投げない。**中身を検めずに書くと、ZIPのつもりで50バイトのエラーJSONが
キャッシュに残る。** 6並列で走らせた初回は 17,719件中 **5,195件（29%）がこれ**で、取得側は
`fail=0` と報告していた。`edinet.fetch_csv` は先頭が `PK` であることを確かめてから書き、
違えば待って引き直す。並列は3に落とした。

**書類一覧（`list_documents`）も同じ穴を持つ。** 応答がJSONなので `json.loads` が通り、
`{"statusCode":"429"}` がそのまま `cache/list_<date>.json` に残りうる。ZIPと違って
壊れていることが後段に伝わらず、**その日の提出書類が丸ごと0件として扱われて母集団から
会社が静かに消える**。`_list_status` が `metadata.status` まで見て仕分ける——429 の本文には
`metadata` が無いので落ち、`status: "404"`（未来日・保持期間外）は「取れない」という
正しい答えとしてそのまま置く。既に置かれてしまったエラー本文は読み出し時に捨てて取り直す。

## 抽出器の構造（`textblock.py`）

**2019年に開示のタグ付けが変わっている。** それ以前は平均年間給与のXBRL要素そのものが無く、
2017・2018年は全社を「従業員の状況」本文から拾う。CSV変換後の表はセルが区切りなしで
連結されるため、`4,17934.09.924,320,256` のような数字の並びをどこで切るかが問題になる。

`parse()` は次の順に試し、最初に妥当性検査を通ったものを採る。

| パス | 当たる書式 |
| --- | --- |
| `_parse_headered`（従業員数を固定） | 単位が見出し側。XBRLの単体従業員数で桁を一意にできる |
| `_parse_headered` | 同上。従業員数のタグが無い書類 |
| `_parse_inline` | 単位が値側で1行に並ぶ書式 |
| `_parse_valueunit` | 見出しが裸で単位が値側。`261(440)40.6歳13年6ケ月7,463,281` |
| 空白を落として再試行 | 字送りのため文字間に空白が撒かれた書類（`従 業 員 数 (人)`） |

`_contiguous` が**給与の列を起点に前後へ広げて**、同じ表の見出し行だけを残す。散文中の
「…記載されている従業員数は」も見出しとして拾われるため、先頭から広げると1列目で切れる。

### 1書類の中では決められない曖昧さ

小数桁の取り方で読みが割れることがあり、**構造的に同型なのに正解が逆になる**。

| 書類 | 数字の並び | 読み方A | 読み方B |
| --- | --- | --- | --- |
| キーエンス 2017 | `2,12136.112.418,617,851` | 勤続12.4 / **1,862万（正）** | 勤続12.41 / 862万 |
| コメリ 2017 | `4,179(4,046)34.09.924,320,256` | 勤続9.9 / 2,432万 | 勤続9.92 / **432万（正）** |

どちらも妥当性検査を通る。決め手は**同じ会社の他の年**にしかない。`textblock._best` は
割れたことを `candidates` に残し、`history.resolve_candidates` が **2019年以降の
XBRLタグ由来の値の中央値**に近いほうを選ぶ。86件が割れ、9件が選び直された。

**候補は「平均年間給与」の同じ出現位置に閉じている。** 持株会社の書類には「提出会社の状況」と
「最大人員会社の状況」の表が両方あり、出現をまたいで候補を並べると*別の会社の値*が混ざって、
年をまたぐ選び直しが報告対象の会社を差し替えてしまう（BSNメディアHD で実際に起きた）。

### 桁ズレは小さすぎる側にもある

`run.fix_salary_typos` は「千円単位の数字を円の欄に入れている」書類を直すが、上限側しか
見ていなかった。`7,196` のように**上限に当たらない**タグ付けが10年ぶんに広げて5件見つかり、
下限側（200万円未満）の補正を足した。2026年には無いので既存の出力は動かない。

## 実測値

| 年 | 提出あり | 値を取れた | 抽出率 | カバー率 | tag | textblock |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2017 | 1,710 | 1,637 | 95.7% | 87.7% | 0 | 1,637 |
| 2018 | 1,728 | 1,652 | 95.6% | 88.5% | 0 | 1,652 |
| 2019 | 1,741 | 1,731 | 99.4% | 92.7% | 1,632 | 99 |
| 2020 | 1,757 | 1,748 | 99.5% | 93.6% | 1,663 | 85 |
| 2021 | 1,779 | 1,767 | 99.3% | 94.6% | 1,678 | 89 |
| 2022 | 1,806 | 1,793 | 99.3% | 96.0% | 1,703 | 90 |
| 2023 | 1,828 | 1,815 | 99.3% | 97.2% | 1,723 | 92 |
| 2024 | 1,844 | 1,831 | 99.3% | 98.1% | 1,739 | 92 |
| 2025 | 1,857 | 1,843 | 99.2% | 98.7% | 1,753 | 90 |
| 2026 | 1,867 | 1,867 | 100.0% | 100.0% | 1,764 | 103 |

**カバー率の欠けは、ほぼ「その年は有報を出していない」である。** 2019年以降の抽出率は
99%超なので、線が途切れていたら未提出だと読んでよい。2017・2018年だけは残り4%が抽出の
失敗で、内訳は3列比較表（前期/当期/増減）と、月給社員・日給社員で行が分かれる表である。

**対象年は10年のままとする。** 抽出率を 77.8% → 95.7%（2017年）まで上げたことで、
「欠け＝未提出」とほぼ読めるようになった。2019年以降8年に絞る案は採らない。

## 妥当性の検算

- **spec AC-3**: 2026年の1,867社が `companies.json` と値・`source` とも全一致
- 同一 `(edinet_code, 年)` の重複 0件
- **隣接年で1.8倍以上／0.55倍以下に動いた組は 4件 / 15,817組（0.025%）。** 4件とも
  誤読ではない——マクセルとフジ・メディアHDは持株会社化で単体従業員数が1,770人→42人と
  変わった実態、イー・ギャランティ2020年はXBRLタグそのものの値である
- 各年の中央値は 614万〜690万で単調に近く、最小・最大も帯に収まる

## 表示に影響しない

`app/page.tsx` は `history.json` を読まない。`companies.json` / `stats.json` の中身は
1バイトも変わっていない（再生成の `generatedAt` を除く）。既存のUnitテスト・E2Eは緑のまま。
