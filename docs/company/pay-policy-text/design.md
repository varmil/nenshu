# C18 給与の決定方針の抜き出し — design.md

参照: Issue [#851](https://github.com/varmil/nenshu/issues/851)（親: [#850](https://github.com/varmil/nenshu/issues/850)）, `docs/company/spec.md` 1.23（AC-35）, `docs/company/overview.md` C18, [plan.md](plan.md)

## 出来上がり

```
pipeline/
  paypolicy/
    fetch.py            # XBRL 本体（type=1）を落とし、3つの節の HTML だけを cache/ に残す
    blocks.py           # 節の HTML → 塊（段落・小見出し・表・画像）と文。番号から原文を切り出す
    pick.py             # バッチに切る・答えを確かめる・取り込む・原文と突き合わせる
    prompts/pick.md     # 範囲の判定の指示（エージェントが読む）
    test_blocks.py / test_fetch.py / test_pick.py
    cache/              # gitignore。{書類ID}.json（節の HTML）
    work/               # gitignore。バッチ・答え・確かめた結果
  data/
    pay_policy_2026.json  # この Unit の成果物
docs/company/pay-policy-text/
  sample40.json         # 起票前に1社ずつ読んだ40社。答え合わせの材料
```

**`web/` は1バイトも触らない。** 画面もデータも変わらない（表示は C19）。

## 流れ

```
ranking_unified_2026.csv（決算期末 ≧ 2026-03-31 の doc_id）
  → fetch.py        EDINET API v2 type=1 → cache/{doc}.json
  → pick.py plan    節を塊と文に分けて番号を振る → work/batch_NNNN.json
  → エージェント     prompts/pick.md に従って番号だけを答える → work/pick_NNNN.jsonl
  → pick.py gate    番号の形と位置を確かめ、原文から本文を組み立てる → work/gated_NNNN.json
  → pick.py merge   → data/pay_policy_2026.json
  → pick.py plan --referenced（参照の会社だけ、参照先の節で同じことをもう1回）
  → pick.py verify  AC-35 の実行ログ。社数・空の理由と、全社の本文を原文と突き合わせる
```

**分解の規則を直したら `pick.py recut`。** データに範囲の番号（`range`）を残してあるので、答えを取り直さずにいまの規則で切り直せる。番号は塊の並びで振っているので、塊の中身の作り方（表のセルの改行など）を変えても番号は変わらない。

**塊の分け方そのもの（小見出しの判定・段落のつなぎ方・表の展開）を変えると番号がずれる。** そのときは `relocate` → `recut` の順に回す。`relocate` は、書き出した本文と同じ文字の並びになる範囲をいまの分解から探す。**画像は文字を持たない**ので、文字だけで探すと画像の手前で一致して画像を落とす（日産車体で起きた）。候補を全部集めて、塊の種類の並びまで同じものを選ぶ。**探せても、範囲に分け方が変わった部分を含む会社は判定し直す**（本文の文字は同じでも、新しい分け方なら範囲を選び直せる）。そのあと `work/` は空にする——`merge` は `gated_*.json` を全部読み直すので、古い分解の本文で上書きしてしまう。

## 取得（`fetch.py`）

**CSV 形式（`type=5`）ではなく XBRL 本体（`type=1`）。** CSV の値は段落の区切りを落とす。NTT の節は PDF では5段落なのに、CSV では改行も全角空白も0個の1つの塊になる。XBRL 本体の HTML なら段落が p 要素のまま残る。C5・C8 が CSV で足りたのは、原文を画面に出さなかったから。

**節の要素はタクソノミの外にある。** 2026年版 EDINET タクソノミの公表（2025-11-11）が府令の改正（2026-02-20 公布）より前なので、「人材戦略に関する基本方針等」の標準の要素が無く、各社の独自要素で付いている。

| 書き方 | 例 | 拾い方 |
| --- | --- | --- |
| `…:BasicPolicyOnHumanResourcesStrategyEmployeesEtcTextBlock` | 無作為100件で100件 | 名前が `BasicPolicyOnHumanResources…TextBlock` の要素 |
| `…:BasicPolicyOnHumanResourcesStrategyTextBlock` | いすゞ | 同上 |
| `…:BasicPoliciesOnHumanResourcesStrategyEmployeesEtcTextBlock`（複数形） | ケイヒン | `BasicPolicy` か `BasicPolicies` で始まる名前 |
| 独自要素を付けず、「従業員の状況」の要素に (1) と (2) をまとめて入れる | TDK | 「従業員の状況」の中から見出し「【人材戦略に関する基本方針等】」〜「【従業員の状況】」を切り出す |

**ZIP は残さない。** 1件約1.9MB で、1,925件なら約3.6GB になる。使うのは3つの節だけなので `cache/{書類ID}.json` に HTML を書いて ZIP は捨てる（1件約150KB）。

- `section` — 人材戦略に関する基本方針等
- `sustainability` — サステナビリティに関する考え方及び取組。給与の決定方針の本文をここに書く会社がある（KDDI・兼松）
- `employees` — 従業員の状況。給与の決定方針の在りかとしてここを指す会社がある（LIXIL「（２）従業員の状況 ⑤」）。持株会社の最大人員会社の表もここにあり（spec 1.23 の対象外）、後の Unit が取り直さずに済む

**ix:nonNumeric は入れ子になる。** サステナビリティの節は人的資本などの小さな節を中に持つので、閉じタグは深さを数えて対応を取る（最初の閉じタグで切ると外側が途中で切れる）。

## 塊と文（`blocks.py`）

**生成AIに文を書かせないための土台。** 節を塊の列にし、段落は文に分けて番号を振る。エージェントには番号の列（`render`）を見せ、始まりと終わりの番号だけを答えさせる。本文は `cut` が原文の文字列から組み立てる。

| 塊 | 中身 | 番号 |
| --- | --- | --- |
| `title` | 節の見出し（「（１）【人材戦略に関する基本方針等】」。「人財戦略」の会社がある） | `b1`。範囲に入れると落とす |
| `heading` | 会社自身の小見出し | `b{n}` |
| `para` | 段落。文（`sentences`）の列を持つ | `b{n}s{m}` |
| `table` | 表。セルの文字列を行ごとに持つ | `b{n}` |
| `image` | 画像。文字を持たない | `b{n}` |

**小見出しはタグではなく文字の形で決める。** h5・h6 を本文の段落に使う会社がある（Hamee は本文が h6、日鉄鉱業は長い1文が h5）。句点で終わらない40字以下の行を小見出しとみる。**「方針」で終わる行は80字まで**——府令の文言そのままの見出し（「②提出会社の従業員の給与（賞与を含む。）その他の給付の額及び内容の決定に関する方針」45字）がある。

**文は句点で区切る。括弧の中の句点では切らない。** つなぎ直すと段落に戻る（テストで固めている）。

**文の途中で割れた p はつなぐ。** 行ごとに p を割る会社がある（ケル「…実現してまいり」／「ます。」）。前の段落が長くて句点などで終わらず、次の段落がひらがなで始まるならつなぐ。**文頭によく来る書き出し（これ・この・その・なお・また・さらに…）はつながない**——見出しの後ろの「これらの指標は…」をつなぐと別の段落が1つになる。取得済みの796件で95か所をつなぎ、無作為の20か所はすべて正しかった。

**表は入れ子になる。** セルの中に表を置く会社がある。内側の表は外側のセルの文字列に平たく入れる。

**1列の表は表ではなく枠として扱い、段落に展開する。** 節の本文を1行1列の表に組む会社がある（ANA・山梨中央銀行）。表のままだと1つの塊になり、人材戦略の文と給与の文を番号で切り分けられない（全件の1回目では、ANA は人財戦略の前置きごと表を取り、クレスコは表の後ろから取り、ヨロズは none と答えていて、扱いがばらばらだった）。展開は全件の判定の後に入れた。分解が変わる47社のうち、1列の表を範囲に含めていた5社は判定し直し、範囲が表より後ろにある32社は本文の文字から番号を探し直した（`relocate`。本文は1字も変わっていない）。残りの10社は、範囲が表より前にあって番号が変わらないか、分解が変わった節を本文に使っていない（2回目で none になった会社）。**2列以上の表（項目名と中身を並べたもの）は表のまま**で、セルの中で人材戦略と給与が一続きの会社（ヨロズ・三ツ星ベルト）は切り分けられない。

**空白以外の文字を1字も落とさない。** `plain_text`（正規表現でタグを落としただけの文字列）と、塊をつなぎ直した文字列を、空白を落として比べる（`pick.py check`）。

## 範囲の判定（`pick.py`・`prompts/pick.md`）

エージェントの答えは1社1行の JSON。

```json
{"doc_id": "S100Y8NY", "verdict": "own", "title": "b4", "start": "b5s1", "end": "b5s1", "note": ""}
```

| verdict | 意味 |
| --- | --- |
| `own` | この節（2回目なら参照先の節）に給与の決定方針がある |
| `referenced` | 他の箇所を参照させている。節の中に短い要約があれば、その範囲も答える |
| `none` | 無い。参照先も無い |

**範囲は1つの連続した区間。** 起票前の40社では、給与の文が飛び飛びだったのは2社だけで、1社（愛媛銀行）は会社の小見出しを外したために切れていただけだった。

**参照の会社は2回に分けて回す。** 全社にサステナビリティの節まで見せると読む量が数倍になる（2社で4.1万字）。1回目で `referenced` と答えた会社だけを、2回目で参照先の節で回す。**2回目で見つからなければ、1回目に答えた節の中の要約に戻す**（`fallback`）。

**参照先はほとんどがサステナビリティの節。** 1回目で参照と答えた120社のうち119社がそこを指していた。給与に触れる文が「従業員の状況」を指している会社（LIXIL）だけ、2回目に従業員の状況を見せる（`reference_target`）。

`gate` が機械で落とすのは番号の矛盾だけ（形・範囲外・始まりが後ろ・節の見出しを含む・題が小見出しでない・題が始まりより後ろ）と、**エージェントに見せた番号の列（バッチの `units`）がいまの分解と違うもの**。分解の規則を変えたあとに古いバッチを確かめ直すと、ずれた番号で黙って別の範囲を切るため。**範囲の取り違えは機械では判定できない**ので、40社との突き合わせと目視で見る。

## データ（`pipeline/data/pay_policy_2026.json`）

配列。1社1行（行ごとの差分が読めるように、1社を1行の JSON にしている）。並びは `ranking_unified_2026.csv` のまま。

| 鍵 | 中身 |
| --- | --- |
| `doc_id` / `edinet_code` / `sec_code` / `name` / `period_end` | 母集団の CSV から |
| `verdict` | `own` / `referenced`（2回目の前）/ `none` |
| `source` | `section` / `sustainability` / `employees`。`own` のときだけ。C19 が「どの節から取ったか」の1行に使う |
| `title` | 給与の決定方針そのものに会社が付けた小見出し。無ければ null。**本文（`blocks`）には入れない** |
| `blocks` | 本文。`{kind: heading|para, text}` / `{kind: table, rows}` / `{kind: image, alt}`。表のセルの中の段落の区切りは改行で残る |
| `range` | 本文を切り出した番号（`{title, start, end}`）。`recut` が使う |
| `chars` | 本文の字数（空白を除く） |
| `has_table` / `has_image` | 本文に表・画像を含むか |
| `section_sha1` / `sustainability_sha1` / `employees_sha1` | 判定に使った節の HTML の SHA-1。**翌年、原文が変わった会社だけ回し直すため**。`verify` もこれで原文が変わっていないことを確かめる |
| `referenced` / `fallback` | 参照の会社の記録 |
| `note` | エージェントが迷った点 |
| `picked_at` | 判定した日 |

**`heading` は「句点で終わらない短い行」であって、見出しとは限らない。** 箇条書きの1項目（「・継続的な見直し」）や、箇条書きの前置きの言いさし（「当社における従業員の採用形態は、人数が多い順に」）も `heading` になる。本文の中の `heading` 1,610個のうち、ひらがなや読点で終わるものが103個あった。**C19 は `heading` を太字の小見出しとして強く描かない**ほうがよい（言いさしが見出しの顔をする）。

**`title` を本文と分けて持つ。** spec 1.23 は「給与の決定方針そのものの見出しは落とす」としていたが、C19 のデザイン（Claude Design `C19 給与の決定方針.dc.html`）は引用の先頭に残している。どちらにもできるように分けておき、出すかどうかは C19 が決める。

## 40社との突き合わせ（パイロット）

起票前に1社ずつ PDF で読んだ40社（`sample40.json`）と、トヨタを足した41社で回した。比べるのは空白を落とした文字列。

| 回 | 1字違わず一致 | 主な食い違い |
| --- | --- | --- |
| 1回目 | 33 / 40 | 長い見出しが本文に入る（丸藤シートパイル）・抱き合わせの項目を丸ごと取る（ファインシンター・森下仁丹）・節の中の1文だけを取る（兼松） |
| 2回目（規則を直した後） | **38 / 40** | 下の2社 |

- **愛媛銀行（6字）** — 会社自身の小見出し「＜基本方針＞」を残した差。40社の判定は外していたが、spec 1.23（小見出しは本文の一部として残す）どおりなのは今回のほう
- **西菱電機** — 給与の決定方針と明示した記述が無く、人材戦略の段落の中に処遇に触れる文が2つ離れてある会社。40社の判定は2文を拾い、今回は処遇の方針を言い切った1文だけを取った。範囲を1つの区間に限っているので、間の研修の文を混ぜないほうを採る

1回目の後に直した規則:

- 府令の文言の長い見出しを小見出しと判定する
- 抱き合わせの項目（「給与等の決定方針及び人的資本投資」）は給与の部分だけを取る
- 同格の番号で給与の続きの項目（「③給与体系の概要」「④給与水準の決定プロセス」）が続くなら含める
- 節の中が1〜2文の要約で詳しい記載を参照先に回している会社は、参照先から取る（兼松。節の中は1文、サステナビリティの節には基本給・賞与の決め方まで7文ある）
