# C5 事業の内容テキストの調達 — design.md

参照: Issue [#159](https://github.com/varmil/nenshu/issues/159)（親: [#158](https://github.com/varmil/nenshu/issues/158)）, `docs/company/spec.md` 1.18（AC-18）, [ADR-0010](../../adr/0010-company-summary-sourcing.md)

## 出来上がり

```
pipeline/
  salary/
    edinet.py            # TEXT_BLOCKS（要素の表）を持つ。to_record が business_text を返す
    businesstext.py      # 平文にする規則（純関数）
    test_edinet.py       # 合成した ZIP を読ませる
    test_businesstext.py
  summary/               # 会社説明文のデータセット。**要約（C6）もここに入る**
    fetch.py             # 母集団ぶんの ZIP を落とす（キャッシュがあれば0件）
    extract.py           # ZIP → business_text_2026.csv
    test_extract.py
  data/
    business_text_2026.csv   # この Unit の成果物
```

**`web/` は1バイトも触らない。** 画面もデータも変わらない（AC-18 の3つ目）。

## データモデル

`pipeline/data/business_text_2026.csv`。1社1行、母集団（`ranking_unified_2026.csv`）の並びのまま。

| 列 | 中身 |
| --- | --- |
| `edinet_code` | EDINETコード。**C6・C7 が突き合わせる鍵**（年をまたいで変わらない。ADR-0006） |
| `sec_code` | 証券コード。非上場は空 |
| `name` | 社名 |
| `doc_id` | 書類ID。**1文ごとに原本まで遡れる**ようにここに持つ |
| `period_end` | 期末。有報の決算期そのもの |
| `text` | 平文にした「事業の内容」 |
| `char_len` | `text` の文字数 |
| `text_sha1` | `text` の SHA-1（UTF-8） |

**`text` は改行を含むので、CSV は引用符で囲まれた複数行になる。** `pipeline/scripts/lib/csv.ts`
の `split(",")` では読めない（worklife が `pipeline/worklife/csv.ts` を別に持っているのと同じ
理由）。**読むのは C6 の Python 側**で、`csv` モジュールがそのまま扱える。

**社名と証券コードは書類ではなく母集団の CSV から採る。** 掲載中の表記を確定させているのは
`unified.py` で、書類の中には旧商号が残っていることがある。

**`text_sha1` は平文にした後の文字列で取る。** 翌年に C6 を回し直す対象を決めるための鍵なので、
比べたいのは「要約の入力が変わったか」。**平文にする規則を変えたら全社ぶん変わるのが正しい。**

## 平文にする規則（`businesstext.py`）

`to_plain_text(value)` の4手。

1. ブロック要素の終わり（`</p>`・`<br>`・`</tr>` …）を改行に開く
2. 残りのタグを落とし、実体参照を戻す（`&amp;` → `&`）
3. 連続する空白を1つに畳む。**改行か全角空白（U+3000）を含む並びは改行にする**
4. 行の前後の空白を落とし、空行を捨てる

**2 の順序が決まっている。** タグを落としてから実体参照を戻す。逆にすると、原文に
`&lt;p&gt;` と書かれていた「文字としてのタグ」まで消える。

**3 が この Unit の要点になる。** EDINET の CSV 形式（`type=5`）が返す値には**改行が1つも無い**
（**実測2,960件で0件**）。変換の段階でブロック要素が畳まれ、日本語の字下げに使われていた全角空白
だけが段落の境目として残る（24,361か所）。`spec.md` AC-18 の「改行は落とさない（段落の切れ目は
要約の入力に効く）」がこの形で指しているのは全角空白のことで、**空白を一律に1個へ潰すと原文が
ひと続きの塊のまま C6 に渡る。**

**代償は承知で採っている。** 開いた24,235か所から40件を目視で抜くと、7件は段落ではなく
**参照や表のセルの途中**で割れていた（`「第５` / `経理の状況` / `１` / `連結財務諸表等」` のように
参照が4行になる型が大半）。空白1個に潰せばこれらは1行に収まるが、**代わりに全社の段落構造が
丸ごと消える。** 要約に効くのは段落のほうなので、こちらを採った。**C6 が原文の読みにくさに
つまずいたら、まずここを疑う。**

`pick(values)` は同じ要素が複数のファイルに現れたときの採り方で、**平文にしてから最も長いものを
採る**。実測では本表に1件だけだったが、`namelist()` の走査順で決まる状態にしない。

**見出し（`３【事業の内容】`）は落とさない。** 原文の一部で、書式が会社ごとに揺れる
（`3【事業の内容】` / `３ 【事業の内容】`）。切る規則を C5 に置くと、C6 が原文を読み直したときに
どこまでが原文か分からなくなる。

## テキストブロックの表（`edinet.py`）

`TEXT_BLOCK`（単数の定数）を `TEXT_BLOCKS`（要素 → `TextBlockSpec`）にした。

| 要素 | slot | keep（保存の条件） | multi |
| --- | --- | --- | --- |
| `jpcrp_cor:InformationAboutEmployeesTextBlock` | `employees_textblock` | `平均年間給与` を含む | いいえ（最初の1つ） |
| `jpcrp_cor:DescriptionOfBusinessTextBlock` | `business_textblocks` | 空でない | はい（全部集める） |

**条件と採り方を要素ごとに持つ。** 従業員の状況は表の給与の行が要る（無い値は `textblock.parse`
が読めない）が、事業の内容にその条件は当たらない。**採り方も違う**——あちらは最初の1つで足り、
こちらは最長を採る。**共通化して片方に寄せると、もう片方の条件が消える。**

`to_record` の戻りに `business_text`（平文）が入る。**原文のままではなく平文で持つ**のは、
整える規則を読む側ごとに書き写さないため。

## TSV の読み方を `csv` モジュールに替えた

`parse_csv_zip` は `line.split("\t")` で割って `strip('"')` で引用符を落としていた。
**EDINET の TSV は RFC 4180 と同じ規則**で、本文に含まれる `"` は `""` に倍にして書かれる。
素で割ると倍のまま残る（「事業の内容」の実測で600社中4社。川崎汽船の `""K"" LINE`、
セガサミーの `""ラメント""` など）。**要約に渡す原文では引用符は中身の一部**なので戻す。

同じ替えで2つの穴も塞がる。

- **値の中の改行で行が落ちる。** 素の `splitlines()` は引用符の中の改行も行の切れ目として
  扱うので、**その値の後ろにある要素まで読めなくなる**。CSV 形式の実測では改行入りの値は
  出なかったが、規則としては起こりうる
- **`csv` の既定の欄の上限（131,072字）を超える値。** 「経営者による分析」のような節は本文
  まるごと1セルに入る。超えると例外で**その書類が丸ごと読めなくなる**ので、上限を上げてある

**既存の抽出が変わっていないことを実測で確かめた。** キャッシュ済み1,489件で新旧の
`parse_csv_zip` と `to_record` を並べたところ、**`to_record` の差は0件**。
`employees_textblock` は1,185件で差が出たが**全件が前後の空白だけ**（新しいほうが
`strip()` される）で、`textblock.parse` の結果は変わらない。

## 取得の経路

```
ranking_unified_2026.csv（doc_id 2,961件）
        │
        ├─ fetch.py ──→ salary/cache/<docID>.zip     （既にあれば EDINET を叩かない）
        │
        └─ extract.py ─→ edinet.parse_csv_zip → edinet.to_record → business_text_2026.csv
```

**落とすのは平均年間給与を拾ったのと同じ書類。** 母集団の定義がこの Unit でずれない。

**`run.py` を回し直さない。** あちらの `twelve_month_window()` は「回した日から12か月」を取り直すので、
走らせた日によって母集団そのものが入れ替わる（`universe.json` の窓は 2025-08-25〜2026-08-25）。
原文を足すだけの Unit で母集団を動かさない。

**`extract.py` は EDINET に一切リクエストしない。** キャッシュに無い書類は「取得失敗」として数える。
取得と抽出を分けてあるので、抽出だけを何度でも回せる。

## 実測（2026-08-26）

`fetch.py` で2,960件を取得（**失敗0件・26分**。キャッシュは 326MB）してから `extract.py` を回した。

| | 値 |
| --- | --- |
| 取得率 | **2,960 / 2,961社（100.0%）** |
| 取れなかった会社 | 1社（Ｚｅｎｋｅｎ・7371。理由は「要素が無い」） |
| 文字数 中央値 | 1,021字 |
| 平均 / 最大 | 1,806字 / 28,047字 |
| 200字未満 | 83社 |
| CSV | 15.2MB（gzip 4.5MB） |

**Ｚｅｎｋｅｎの有報には「事業の内容」がタグ付けされていない。** 別の名前空間で拡張されている
わけでもなく（`BusinessRisksTextBlock` や `BusinessPolicy…TextBlock` はある）、要素そのものが
無い。**取得の問題ではないので、回し直しても増えない。** ADR-0010 が見込んだとおり
「書けない会社」の1社目がここで出た形になる。

**ADR-0010 の見積り（無作為90社。中央値1,006字・平均1,415字・最大7,560字）とほぼ合った。**
最大が伸びたのは、90社には入っていなかった大きい会社が事業系統図の表を本文に畳んで持つため。

**同じ要素が2件現れた会社は1社も無かった**（2,960件すべて `values=1`）。`pick` の「最長を採る」は
実際には一度も選んでいない——規則として要るのは走査順で決まらないようにするため。

**CSV は 15.2MB で、`pipeline/data/` の中では最大になる**（次が `performance_history.csv` の
1.9MB）。**それでも置くのは、キャッシュが `.gitignore` 済みで、作り直すのに APIキーと26分が
要るため**（`performance_history.csv` を置いているのと同じ理由）。gzip では 4.5MB。
**gzip して置く案と、置かずに毎回作り直す案を運営者に出して、平文のまま置くことに決めた**
（2026-08-26）——他の派生CSVと同じ扱いにしておくほうが、`grep` も `diff` も効く。

## この Unit で決めなかったこと

- **書けない会社の判定**（ENEOSホールディングス型）。原文があって中身が当期の異動の説明だけ、
  という型は**文字数では検出できない**ので、落とすのは C6 の検証パスが行う（ADR-0010 決定2）
- **要約の生成**（C6）と**画面への表示**（C7）
- **沿革・経営方針の取得。** ADR-0010 決定1のとおり、原文を増やして埋めない

## Python にコミット前のゲートを付けた

`lint-staged` は `pipeline/scripts/**/*.ts` しか見ていなかった。この Unit で足したロジックは
Python 側にあるので、**そのままではテストが一度も走らないまま入る。**

- `pipeline/package.json` に `test:py` を足し、`npm test` から呼ぶ（vitest の後）
- `.lintstagedrc.mjs` に `pipeline/**/*.py` → `npm --prefix pipeline run test:py` を足す

**実物の有報を読むテストは書かない。** `cache/` は `.gitignore` 済みで、まっさらなコンテナには
1件も無い。ZIP は合成する（`test_edinet.py` の `_zip`）。
