# C7 企業詳細ページへの表示 — design.md

参照: Issue [#161](https://github.com/varmil/nenshu/issues/161)（親: [#158](https://github.com/varmil/nenshu/issues/158)）, `docs/company/spec.md` 1.18（AC-21〜AC-23）, [ADR-0010](../../adr/0010-company-summary-sourcing.md)

## 出来上がり

`/company/[id]` の h1 と順位行の直後に、その会社が何をやっているかを述べる2〜3文と、
出典の1行が出る。**説明文の無い178社では丸ごと出ない。** 数値は1つも増えていない。

```
株式会社キーエンス            ← h1
電気機器 ・業界150社中3位 ・全体2,961社中3位
電子応用機器の開発、製造及び販売を主な事業とする。商品の開発から   ← 説明文（2〜3文）
販売までを自社で担い、製造とソフトウェア開発は子会社が分担する。
海外では現地の子会社を通じて販売する。
有価証券報告書「事業の内容」（2026年3月期）をもとに要約（作り方）  ← 出典＋/about への導線
─────────────────
見せ方  [実測値][年齢そろえ]
年齢    [25][30][35]…
```

## データの配り方

| | |
| --- | --- |
| 成果物 | `web/public/data/summaries.json`（`{ byId: { "6861": "…" } }`） |
| 大きさ | 2,783社 / 2,961社（94.0%）・**gzip 261.8KB**（上限 320KB） |
| 作る場所 | `pipeline/scripts/build-data.ts` の `buildSummaries` |
| 読む場所 | `web/features/company/lib/pageData.ts` の1か所だけ |

**`companies.json` に混ぜない。** あちらは `/` が全社ぶんを配るファイルで gzip 100KB の
上限を持っている。説明文は 2,783社ぶんで raw 950KB あり、混ぜた時点で予算を超える。

**`src/pages/index.astro` からは読まない**（Issue #22）。実測で `/` の HTML は
raw 246,171 B（gzip 19,140 B）で、**説明文は1文字も入っていない**（`grep` で0件）。

### 行の配列ではなく ID の辞書にする

`worklife.json`・`radar.json`・`performance.json`・`stats.json` は `companies.rows` と
同じ並びの配列だが、**説明文はそれに倣わない。**

あちらが配列なのは**全社を舐める場面がある**ため——順位を振る、軸の母集団を数える。
説明文にそれは無く、引くのは常に1社ぶんなので、**行がずれると別の会社の文を出すという
危険を持ち込む理由がない。** 掲載の無い178社はキーごと落とす（`history.json` と同じ）
——`undefined` がそのまま「説明文が無い」を表し、`""` を「ある」と読み違える余地が消える。

同じ中身を同じキー（企業ID）で組んで測ると **配列 gzip 260.6KB / 辞書 261.8KB** で、
**差は 1.2KB しかない**（掲載の無い178社ぶんの `""` は圧縮でほぼ消える）。クライアントへ
送らないファイルでもあるので、その差より引き方の安全を採った。

### 突合が全件当たることをビルドで確かめる

`buildSummaries` は CSV の社数と掲載社に当たった数を突き合わせ、食い違えば落とす
（`buildWorklife` と同じガード）。**落とさないと、突合キーを間違えたまま
「説明文の無い会社」として静かに配ることになる**——画面は壊れないので気づけない。

充足率はビルドのサマリーに出る（E2・AC-8 と同じ扱い）。

```
summaries.json: 2783/2961社（94.0%）, gzip 261.8KB
```

## 出し分けは純関数に閉じる

`web/features/company/lib/summary.ts`。

- `buildSummaryView(summary)` — 説明文が無ければ `null`。**空文字・空白だけ・
  `undefined` を全部 `null` にする**（C6 の CSV は落とした会社に空文字を書く）
- `summarySourceLabel(fiscalPeriod)` — 出典の1行

**分岐をコンポーネントに直接書かない。** 「何も出ない」ことはテストで捕まえにくいので、
`null` を返す関数にしてその `null` をテストする（AC-9）。

### 出典の文言を `SummaryView` に持たせない

**Astro の島は props を HTML の属性に直列化するので、固定の文言をビューに載せると
同じ文が props と本文の2か所に出る。** 実測で `/company/6861` が +134 B。

W2（#224）で残業時間の注記が同じ形で二重になり、`WorklifeMetricView` から外して
`metricFootnote(key)` を描画側から引くようにした——**同じ判断をここでも採った**
（`summarySourceLabel` を描画側が呼ぶ）。

**E2E が先に捕まえた。** 「HTML に入っている説明文はその会社の1本だけ」が
`をもとに要約` を2回数えて落ち、そこで気づいた。CLAUDE.md に W2 の記録があったのに
同じ形を書いており、**規則を読んでいても踏む**ことの実例になっている。

## 表示基準に依らない

`CompanyView.byBasis` の中に入れない（AC-23）。説明文は事業の記述であって金額の話では
ないので、表示基準（実測値 / 年齢そろえ）でも年齢スイッチでも変わらない。**型の上で
`byBasis` に置くと「年齢そろえにしたら事業の内容が変わる」を表現できてしまう**
——10年推移（T1）・働きやすさ（W1）・稼ぐ力の推移（P2）と同じ扱い。

## 置く位置

**順位行の直後・「見せ方」の帯より前。** ここまでが「どの会社を見ているか」の段で、
2つの帯からは「その数字をどう見るか」に変わる。モックのアートボード 4b / 2b が3行の
紹介文を描いている位置で、C3（#89）が「データが無い」として空けたまま残した場所になる。

### モバイルで年齢スイッチは押し下がる。畳まない

390px / 375px での実測（`p` の高さと「年齢」の帯の下端。`window.scrollY` 込み）。

| | 字数 | 行数 | 高さ | 年齢の帯の下端（375×667） |
| --- | --- | --- | --- | --- |
| 説明文なし（東京海上 8766） | — | — | 0 | 573px |
| キーエンス（6861） | 83字 | 4行 | 98px | 665px |
| 三菱商事（8058） | 119字 | 6行 | 146px | 719px |
| 最長（4828） | 131字 | 6行 | 146px | **719px** |

**iPhone SE（667px）では最長で 52px ぶん画面から外れる。** Issue #161 の論点2 が
心配したとおりだが、**畳まない**と決めた。

- **押し下げているのは読者が最初に読む文**（`docs/company/intent.md` H1——「◯◯ 年収」で
  1社を頭に置いて訪れる読者に、その会社が何をやっているかを答える）
- **押し下げられているのは既定では使わない操作。** 既定は実測値で、年齢そろえは読者が
  明示的に選ぶモード（ADR-0007）
- **1スクロール未満で見える**（52px）
- 折りたたむと**読ませたい文を隠したうえに操作が1つ増える**

**横スクロールは全幅で0**（375 / 390 / 320px で実測）。

## 出典と `/about` への導線

説明文の直下に `有価証券報告書「事業の内容」（2026年3月期）をもとに要約（作り方）`。

- **決算期は直書きしない**（`docs/site-chrome/spec.md` AC-20）。値は
  `companyFiscalPeriodLabel`——**会社ごとの決算期**で、母集団の幅（`fiscalPeriodLabel`）
  ではない（E1・#172）
- **同じ断りを1画面に2回置かない**（Issue #128 の「推定」と同じ扱い）。下の
  「有価証券報告書の実測値」の節にこの文を重ねていない。E2E が `をもとに要約` の数を
  1で固定している
- 「作り方」は `/about#company-summary` へ飛ぶ。**`Section` に `id` を持たせたのは
  この1つだけ**——9つ並ぶ節のどれかは `/about` を開いただけでは分からない

`/about` の節「会社の説明文の作り方」には、出所（有報の「事業の内容」だけ）・書いてよい
ことの4条件・二段構えの検査・書けない会社では出さないことを書いた。**社数はデータから
引く**（`summaries.json` の件数）。

### `summaries.json` は Worker バンドルに入らない

`dist/server` を `grep` すると、**説明文は1件も無い**。`worklife.json` の注釈も無い。
入っているのは会社名（`companies.json`）だけで、それは `/` が
`export const prerender = false` で読むため。

**F1（Astro・#209）以降、`/company/[id]` だけが読むデータはビルド時に消費され、
バンドルには残らない。** CLAUDE.md と `docs/worklife/overview.md` にある
「`worklife.json` の切り出しは Worker バンドルが 3MiB に近づいたら判断する」は
**OpenNext 時代の前提で、いまは成り立たない**——バンドルは gzip 631.9KB（上限の20.1%）
で、`summaries.json` を足しても動かなかった。

## テスト

| | |
| --- | --- |
| Unit | `features/company/lib/summary.test.ts`（7件）。**空の器を出さないこと**が本体で、空文字・空白だけ・`null`・`undefined` の4つを `null` に倒す |
| E2E | `e2e/company-summary.spec.ts`（9件）。**説明文のある会社と無い会社の両方**——片方だけだと「出さない」ことが通らない |

E2E で**位置を DOM の順序で固定する**（`compareDocumentPosition`）。位置を見ないと、
節がページのどこか別の場所に出ていても通ってしまう。

説明文の無い側に**東京海上ホールディングス（8766）**を使う。C6 の目視レビューで型⑪に
落ち、**原文の事業の中身が1文ぶんしかないので空が正しい**と判定した会社で、
`docs/company/company-summary/design.md` に記録がある。

## spec を1か所直した

AC-22 が「決算期は `companies.meta.fiscalPeriod` 由来である」と書いていたが、**E1（#172）で
この値は `fiscalPeriodRange` に変わっている。** 1社ぶんを出せる場所では会社ごとの決算期を
出す規則（`companyFiscalPeriodLabel`）なので、そちらを指すよう改めた。
