# C9 要約と分析の生成 — plan.md

参照: Issue [#241](https://github.com/varmil/nenshu/issues/241)（親: [#214](https://github.com/varmil/nenshu/issues/214)）, `docs/company/spec.md` 1.19（AC-25〜AC-28）, [ADR-0015](../../adr/0015-company-analysis-subjectivity.md), [ADR-0010](../../adr/0010-company-summary-sourcing.md), [ADR-0008](../../adr/0008-company-logo-sourcing.md)
依存: C8（[#240](https://github.com/varmil/nenshu/issues/240)・実装済み）

## Context

C8 が4節の原文を全社ぶん揃えた。そこから**要約**（評価語なし・原文に書いてある事実だけ）と
**AI分析**（評価を書く・渡した材料から導ける解釈）を作るのがこの Unit で、**web には出さない**
（表示は C10）。

**工程は C6 のものがそのまま使える。** `plan → 生成エージェント → 機械ゲート →
検証エージェント → merge`、再開の仕組み（`source_sha1` が同じ社を飛ばす）、
バッチと生成物の社数を突き合わせる検査、失敗の型を prompts に積み上げるやり方。

**C6 と違うところが3つある。**

1. **規格が2つあり、1回の呼び出しで両方書かせる。** 機械ゲートも検証パスも規格ごとに分かれる
2. **分析の材料が有報の外へ広がる**（ADR-0015 決定2）。生成エージェントが Web を検索して
   取りに行き、**使った URL を出力に残す**。事前調達の工程は作らない（決定6）
3. **量が桁違い。** 有報だけで1社あたり平均21,005字（C6 の説明文は736字）。**切らなければ
   全社で6,220万字**になる

## 進め方

1. **機械ゲートを先に書く。** LLM を呼ばない純関数だけを置き、固定入力でテストする——
   **生成と検証はセッションのエージェントが担うので、テストできるのはこの層になる**（C6 と同じ）。
   要約は C6 のゲートを流用し、**分析は別に作る**（評価語を通し、代わりに算用数字の個数に
   上限を置き、出典の形式を見る）
2. **数値の裏付けの照合を、どこまで機械でやれるか決める。** AC-26 が名指ししている
   「10年で13%下がっている」の型は `history.json` と突き合わせられる。**一般の主張は
   突き合わせられない**ので、**機械でやる範囲を先に切って design.md に書く**——
   できないことをゲートに書くと、通ったことが保証にならない
3. **プロンプトを2つ書く**（生成・検証）。**失敗の型の表は要約と分析で別々に持ち、番号は
   prompts 側に固定する**（C6 の教訓。振り直すと回をまたいで内訳を比べられない）。
   **数値を主役にしない、は対照表で示す**——#214 に3組ある
4. **パイロットを回す。** #214 が**5社について「好調かどうかの一言」を人手で書いている**
   ので、それを回帰ケースにする。生成した一言と突き合わせれば、規格が効いているかを
   実物で見られる。ここで決めるのは次の5つ。
   - 節ごとに原文を何字で切るか
   - 4節すべてを使うか、減らすか
   - 分析に含めてよい算用数字の個数の上限
   - **1社あたりどこまで検索し、何ページ取りに行くか**（決めないと会社ごとに青天井になる）
   - 要約・分析の分量
5. **決めた値を既定にして design.md に書き、全社ぶんの生成を次の回に回す。** C6 は12回
   かかった。**この Unit は「回すたびに進む」形が完成した時点で完了**とし、全社ぶんを
   1セッションで終える前提を置かない
6. **既存の出力が変わっていないことを確かめる。** `build:data` を回して `web/public/data/`
   に差分が出ないこと（この Unit は web に出さない）。

## 着手前に見えている判断

**`pipeline/analysis/` を新しく作る。** `pipeline/summary/` が作るのは説明文
（`company_summary_2026.csv`）で、**作るデータセットが違う**（W0 で `salary35/` を
`salary/` に改名したときと同じ線——ディレクトリは作るデータセットで切る）。C8 が
`summary/` に置いた `extract_analysis.py` も**同じデータセットなので一緒に移す**。
**書類を落とす `fetch.py` は `summary/` に残す**——あれは母集団の ZIP を取るだけで、
どちらのデータセットにも属さない共通の道具である。

**生成は1回の呼び出しで要約と分析を両方書かせる。** 原文を2回読ませない（ADR-0015 決定7）。
**ただし出力は別の欄に分け、ゲートも検証も別に当てる。**

**外部の材料は「取ってきた文書」に限る。** モデルの記憶から補わない（ADR-0015 決定2）。
**取り方は ADR-0008 の線**——UA に偽装しない、ヘッドレスブラウザを使わない、403・503・
画像認証・WAF のチャレンジは拒否として受け取る。

**材料の薄い会社の分析を無理に埋めない。** 外部の文書が取れる量は上場の大手に偏る。
**薄いまま書くか、書けないとして落とす**——埋めにいけば記憶から補うことになる。

**成果物は git に置く。** 要約1,000字＋分析800字なら全社で約550万字＝CSV 十数MB で、
C8 の原文（175MB）とは桁が違う。**説明文（`company_summary_2026.csv`・1.3MB）と同じ扱い。**

## 検証

```bash
cd pipeline && npm test                       # 機械ゲートの純関数
cd pipeline/analysis && python3 generate_analysis.py status
cd pipeline/analysis && python3 generate_analysis.py plan --pilot --size 6 --batches 2
（エージェントが prompts/generate.md に従って work/gen_NNNN.jsonl を書く）
cd pipeline/analysis && python3 generate_analysis.py gate
（エージェントが prompts/verify.md に従って work/verify_NNNN.jsonl を書く）
cd pipeline/analysis && python3 generate_analysis.py merge
cd pipeline && npm run build:data -- --out ../web/public/data && git diff --stat web/public/data
```

- 機械ゲートが固定入力でテストされていること（AC-25・AC-26）
- パイロットの5社で、#214 が人手で書いた一言と突き合わせられていること
- 出典の URL が出力に入り、検証パスがそれを取りに行っていること（AC-27）
- 実行ログに 要約が付いた割合・分析が付いた割合・rejected の理由ごとの件数が出ること（AC-28）
- `web/public/data/` に差分が出ないこと
