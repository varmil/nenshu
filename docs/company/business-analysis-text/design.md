## 4節（`edinet.ANALYSIS_SECTIONS`）

| 鍵 | XBRL 要素（すべて `jpcrp_cor:`） | 節 | 取得 | 中央 | 平均 | 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| `mdna` | `ManagementAnalysisOfFinancialPositionOperatingResultsAndCashFlowsTextBlock` | 経営者による分析 | 2,961（100.0%） | 6,153字 | 6,838字 | 29,897字 |
| `risks` | `BusinessRisksTextBlock` | 事業等のリスク | 2,961（100.0%） | 4,010字 | 5,022字 | 30,000字 |
| `issues` | `BusinessPolicyBusinessEnvironmentIssuesToAddressEtcTextBlock` | 対処すべき課題 | 2,960（100.0%） | 2,749字 | 3,237字 | 21,223字 |
| `sustainability` | `DisclosureOfSustainabilityRelatedFinancialInformationTextBlock` | サステナビリティ | 2,957（99.9%） | 4,104字 | 5,917字 | 29,991字 |

**取れない節を持つ会社は5社だけ。** サステナビリティが無いのが4社
（テー・オー・ダブリュー 4767・テクセンドフォトマスク 429A・ファインシンター 5994・
ムロコーポレーション 7264）、対処すべき課題が無いのが1社（日本エコシステム 9249）。
**別の名前空間で同じ節を持っているわけではない**——節そのものをタグ付けしていない。

**1社でも取れれば行を作る。** 4節すべてを要求しない——C9 に渡す材料が1つでもあれば、
書けるかどうかは**あちらの検証パスが決める**（C5 が「書けない会社をここで落とさない」と
したのと同じ線）。**2,961社すべてで少なくとも1節が取れた**ので、この Unit では
1社も落ちていない。

**「事業の内容」はこの表に入っていない。** 説明文（C7）が同じ原文を使っており、両方を
材料にすると1画面に同じ内容が2回出る（ADR-0015 決定4）。`edinet.TEXT_BLOCKS` の
`DescriptionOfBusinessTextBlock` は説明文だけのものとして残してある。

## 要素名は完全一致で引く。接尾辞で拾わない

**着手前の想定は逆だった。** #214 の精緻化は「人的資本の節は会社独自の名前空間になる
ことがある（キーエンスの `jpcrp030000-asr_E26831-000:StrategyHumanCapitalTextBlock`）
——P2（#168）で経常利益の要素名が決め打ちできなかったのと同じ形なので、**接尾辞で拾う**
必要がある」としており、AC-24 の初版もそう書いていた。

**実測（1,476社）で覆った。**

- **4節とも `jpcrp_cor:` の完全一致で 100.0 / 100.0 / 100.0 / 99.8% 取れる。** 別の名前空間で
  同じ節を持つ会社は1社も無かった。サステナビリティが取れない2社は、**別名前空間の候補も
  1つも持っていない**（節そのものをタグ付けしていない）
- **人的資本の独自要素を持つ331社でも、中身はサステナビリティの節に丸ごと含まれている**
  （1,035件中1,009件）。**残り26件は9社ぶんで、9社とも親の節が30,000字の打ち切りに
  当たっていた**（住友商事・積水ハウス・キリンHD・三菱UFJ・三井物産・アサヒGHD・ヤマハ・
  リコー・富士通）——含まれないのは名前空間の話ではなく、**親が途中で切れている**からだった
- **キーエンス（6861）はそもそも独自要素を1つも持っていない。** 持っているのは
  `jpcrp_cor:` のサステナビリティ1,640字だけ

**そのうえで接尾辞は害のほうが大きい。** `StrategyHumanCapitalTextBlock` で接尾辞を取ると
`ReferenceToOtherInformationStrategyHumanCapitalTextBlock`——中身は
「『１．サステナビリティ全般』を参照してください。」の1行——まで巻き込む。`pick` は最長を
採るので実害は出にくいが、**要らないものを拾う経路をわざわざ足すことになる。**

`test_edinet.py` の `test_人的資本の独自要素は拾わない` がこれを固定している。

## 4節は `to_record` に入れない

C5 は `business_text` を `to_record`（ランキングの1行を組み立てる関数）に入れた。
**4節は入れない。**

`to_record` を呼ぶのは `run.py`（2,961件）と `history.py`（**17,684件**）で、
**この4節を読むのは C8・C9 だけ**である。1社あたり約21,000字を全書類ぶん平文に直す理由が
無い。`parse_csv_zip` は生の値を集めるところまでやり（`analysis__<鍵>` のスロット）、
平文にするのは `analysis_texts()` を呼んだときだけになる。

`test_edinet.py` の `test_ランキングの記録には4節を入れない` が固定している。

## 原文は git に置かない。マニフェストを置く

| | 大きさ |
| --- | --- |
| `analysis_text_2026.csv`（原文） | **175MB**（gzip 46.5MB） |
| `analysis_text_manifest_2026.csv`（字数と SHA-1） | 740KB |
| 参考: `business_text_2026.csv`（C5・コミット済み） | 15.2MB |

**1社あたり平均21,005字・全社で6,220万字**あり、`pipeline/data/` の最大である
`business_text_2026.csv` とは桁が違う（#214 の見積り「1社14,400字」より大きい）。

**原文は `pipeline/.gitignore` に入れ、マニフェストをコミットする。**

- **C9 が要るのはマニフェストのほう。** 「原文が変わった会社だけ回し直す」の鍵は節ごとの
  SHA-1 で、それは740KB に収まる
- **原文はキャッシュから27秒で作り直せる**（実測。切った版も書くようになった C9 以降は51秒）。`extract_analysis.py` は **EDINET を
  1回も叩かない**（`pipeline/salary/cache/` を読むだけ）。C5 が15.2MB をコミットした理由
  ——「作り直すのに APIキーと26分が要る」——は、キャッシュがある環境では効かない。
  **キャッシュが空のコンテナでは `fetch.py` の26分が先に要る**ので、そこは C5 と同じ
- **切ってから置く案は採らない。** 節ごとに2,000字で切れば63MB、1,500字なら48MB まで
  下がる（実測）が、**切る長さを決めるのは C9 のパイロット**（ADR-0015 決定2）である。
  C8 が先に決めて原文を捨てると、切り方を変えたときにどのみちキャッシュから作り直す
  ことになり、gitignore した場合と手間が同じになる。**`--max-chars` は持っているが
  既定では切らない**
  - **【2026-08-28・C9】この判断の後半は覆った。** パイロットが**1,800字**と決めたので、
    **その長さで切った版（gzip 15.8MB）を git に置いた**（`analysis_text_head1800_2026.csv.gz`）。
    覆した理由は**キャッシュがコンテナごと消えること**で、置かないと C9 の約48セッションに
    26分ずつの取り直しが乗る。**切らない版を gitignore にする判断は変わっていない**
    （`docs/company/analysis-generation/design.md`）

## マニフェストの列

```
edinet_code, sec_code, name, doc_id, period_end,
mdna_len, mdna_sha1, risks_len, risks_sha1,
issues_len, issues_sha1, sustainability_len, sustainability_sha1,
truncated
```

**SHA-1 は節ごとに取る。** 4節をまとめて1つにすると、1節だけ変わった会社と全部変わった
会社を区別できず、C9 が回し直す範囲がそのぶん広がる。**平文にした後の文字列で取る**
——整え方を変えたら全社ぶん作り直す、が正しい（C5 と同じ）。

`truncated` は**30,000字の打ち切りに当たった節**の鍵を並べたもの。EDINET の CSV 形式
（`type=5`）が値をそこで切っており、**復元しない**——原本の XBRL（`type=1`）を読めば
伸びるが、この Unit の範囲は「平均年間給与を拾ったのと同じ書類から拾う」ことに閉じている。
**当たったのは31社ぶん32節**（MD&A 7・リスク 5・サステナビリティ 20。2節とも切れたのは
6178・日本郵政の1社）で、母集団の 1.0% にあたる。

**判定は 30,000 ちょうどではなく1字ぶん緩めている。** 実測した32件のうち大半が
**29,999字**だった——`parse_csv_zip` が値を `strip()` しており、**30,000字目が空白だった
書類ではそれが落ちる**ため。**30,000 ちょうどで数えると12件しか挙がらず、20件を取りこぼす**
（最初に書いたときそうなっていた）。

## 実測（2026-08-28）

```
母集団 2961社 → 原文 2961社（100.0%）
  取得失敗: 0社
  4節とも無い: 0社
  経営者による分析: 2961社（100.0%） 中央 6153字 / 平均 6838字 / 最大 29897字 / 打ち切り 7社
  事業等のリスク: 2961社（100.0%） 中央 4010字 / 平均 5022字 / 最大 30000字 / 打ち切り 5社
  対処すべき課題: 2960社（100.0%） 中央 2749字 / 平均 3237字 / 最大 21223字 / 打ち切り 0社
  サステナビリティ: 2957社（99.9%） 中央 4104字 / 平均 5917字 / 最大 29991字 / 打ち切り 20社
  1社あたり合計: 中央 18513字 / 平均 21005字 / 総計 6220万字
```

**書類は1件も取り直していない。** キャッシュが空のコンテナで `fetch.py` を回すと
2,961件で **26分**（並列3・失敗0）。キャッシュが生きていれば0件になる。

**C9 の量の見積りが1つ縮んだ。** #214 は「1社14,400字・全社4,270万字・約96セッション」と
していたが、実測は **1社21,005字・全社6,220万字**で、**切らなければ約140セッション**になる。
節ごとに1,500字で切れば1社6,000字（全社1,776万字）まで下がる——**切る必要があることは
この実測で確かめられた**が、**どこで切るかは C9 のパイロットが決める。**

## この Unit で決めなかったこと

**原文の切り方。** 上のとおり `--max-chars` は持っているが、既定では切らない（C9・ADR-0015 決定2）。

**書けない会社の落とし方。** 節が短い・中身が定型句だけ、という型は**文字数では検出できない**
（C5 の ENEOS と同じ）。落とすのは C9 の検証パスの仕事。

**打ち切りに当たった32節の復元。** 原本の XBRL を読む決定はしていない。`truncated` 列に
残してあるので、C9 が必要と判断したときに数えられる。
