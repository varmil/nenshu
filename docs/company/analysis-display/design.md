# C10 要約と分析の表示 — design.md

参照: Issue [#242](https://github.com/varmil/nenshu/issues/242)（親: [#214](https://github.com/varmil/nenshu/issues/214)）, `docs/company/spec.md` 1.19・AC-28〜AC-30, [ADR-0015](../../adr/0015-company-analysis-subjectivity.md)

## 出来上がり

`/company/[id]` に2つの節が増える（アートボード 8a / 8b / 8c）。

```
h1 社名 / 順位 / 説明文（C7） / 見せ方・年齢の帯
① 平均年収カード                ← C15（#821）でレーダーと入れ替えた
② 公開資料による全体像（レーダー）
③ {社名}の現状と今後            ← AI 分析（muted の面）
④ 残業・有給・男女の賃金の差異
⑤ 年齢別の推定年収
⑥ 有価証券報告書の実測値
⑦ 平均年収推移（過去10年間）
⑧ 稼ぐ力の推移（過去10年間）
⑨ {社名}の有価証券報告書の要約   ← 要約（地のまま）
⑩ この数字の作り方（C12・#805 で「このページの出典」に作り替えた）
```

### 要約の節

h2「{社名}の有価証券報告書の要約」、説明の1行（**原文の決算期**・4節の名前・「書いてある事実だけを
まとめたもの」）、本文。**面も断りも付けない。**

## 2つを見分けられるようにする（AC-29）

| | 分析 | 要約 |
| --- | --- | --- |
| 面 | `bg-muted` で囲う | 地のまま |
| 断り | 見出しの直下に「2026年3月期の有価証券報告書・公開資料をもとにAIが書いた評価です」 | 無い（事実なので、付けると区別が消える） |
| 時点 | **原文の決算期**（断りの先頭） | **原文の決算期**（説明の1行の先頭） |
| 位置 | 平均年収カードとレーダーの後ろ | 稼ぐ力の推移の後ろ |
| 出典 | 参照した資料（URL・ドメイン・参照日） | 4節の名前 |

- **見出しに「（AIによる分析）」を付けない。** AI である旨は直下の断りが持つ。見出しにも書くと
  同じことを2回言う（アートボード 8b の注記）
- **一言は見出しより大きくしない。** 大きい太字にすると見出しと張り合い、どちらが節の名前か
  読めない。強さは白地の内側カードと「ひとことで言うと」のラベルで出し、字は本文より一段強い
  semibold に留める
- **要約の説明は C7 の出典（「事業の内容」をもとに要約）と重ならない言い方**にする
- **2つの節はどちらも原文の決算期を名乗る。** 要約は `digestNote(fiscalPeriod)` が説明の先頭に、
  分析は `analysisNote(fiscalPeriod)` が断りの先頭に置く。**値は要約と分析の原文にした有報の決算期**
  （`AnalysisView.fiscalPeriod`。refresh の D3・`docs/refresh/text-period/design.md`）で、数字の側の
  決算期を借りない——毎日の更新では数字が先に新しい書類へ替わり、文章は書き直すまで前の書類のまま
  出るので、借りると前の期の文章が新しい期を名乗る
- **分析に書いた年月は出さない**（2026-10-10・運営者の判断。2026-09-24 からは断りの末尾に
  「（2026年9月時点）」を出していた）。前の期の有報で書いた分析が、書いた月の新しさで最新に見えた
  ——数字だけが2026年6月期に替わったロジザードで、2025年6月期の有報で書いた一言「来期はあえて減益
  計画」が「2026年9月時点」の評価として出ていた。決算期と並べると日付が2つになって読みにくい。
  新しい有報が出るたびに書き直すので、いつの評価かは原文の決算期で読める。公開資料の時点は
  「参照した資料」の参照日が持つ。**書いた年月はデータ（`generatedAt`）には残す**
- **決算期が企業詳細に複数回出るのはこのため**（S3 の「1画面に1回」を改めた・`docs/site-chrome/spec.md`
  5.1）。Q&A・分析・要約・給与の決定方針の各節が、自分の中身がどの有報かを言う。**それ以外の場所には
  増やさない**——説明文（C7）の出典の1行には入れない（`e2e/data-period.spec.ts` が回数と場所を固定
  している）

## 置き場所

- **分析は平均年収カードとレーダーの後ろ。** 「◯◯ 年収」で来た読者の答え（カード）より上に置くと、
  答えがさらに下がる（C10 の時点ではスマホでカードの金額がすでに最初の画面の外にあった）。カードの
  後ろなら、数字を見た直後に「この会社はいまどうなのか」が続く。C10 の時点ではレーダー → カード →
  分析の順で「カードの直後」だった。**C15（#821）でカードとレーダーを入れ替え、いまはレーダーの
  直後**になる（`docs/company/card-first/design.md`）。上の2つの理由はどちらもそのまま成り立つ
- **要約は稼ぐ力の推移の後ろ。** 1文目が事業の説明になりやすく、ページ上部の説明文（C7）と
  内容が重なる。近くに置くと同じ話が2回続いて見える
- 2つが離れていることも、取り違えにくさに効いている
- **h2 に社名を入れる。** 「◯◯ 今後」「◯◯ 事業」のような検索の受け皿になる。「将来性」は
  評価の語が見出しに出るので採らない

## データの配り方

| | |
| --- | --- |
| 成果物 | `web/public/data/analyses.json`（`{ byId: { "6861": { digest, headline, body, sources, generatedAt } } }`） |
| 大きさ | 2,961社（100%）・raw 6.9MB・**gzip 2,155.0KB**（上限 2,600KB） |
| 作る場所 | `pipeline/scripts/build-data.ts` の `buildAnalyses`（純関数は `pipeline/scripts/lib/analysis.ts`） |
| 読む場所 | `web/features/company/lib/pageData.ts` の `companyAnalysisFor` と `/about` の社数 |

- **`summaries.json` と同じく ID の辞書。** 全社を舐める場面が無い
- **要約と分析を1つの記録に入れる。** 別のファイルにすると片方だけの会社を作れてしまう（AC-28）
- **`generatedAt` は CSV の `generated_at`（C9 が UTC の ISO 8601 で書く）を日本時間の年月にしたもの**
  （`generatedMonth`）。UTC のまま月を取ると、月末の夜に書いた分析が前の月になる。形が崩れていたら
  ビルドを落とす。**画面には出さない**（上の「2つを見分けられるようにする」）。**原文の書類と決算期は
  `filing`**（`{ docId, period }`。refresh の D3）に持ち、2つの節の時点はこちらから出す
- **`/` からは読まない**（Issue #22・AC-30）
- **クライアントへは送らない。** ページごとにビルド時に1社ぶんを抜いて静的な HTML にする

### 島の props に載せない——名前付きスロットで差し込む

```
[id].astro
  const analysis = companyAnalysisFor(id)          ← data（props）とは別に取る
  <CompanyDetailIsland data={data} client:load>
    <AnalysisSection slot="analysis" …/>           ← React だが client 指示なし＝静的 HTML
    <DigestSection slot="digest" …/>
  </CompanyDetailIsland>

CompanyDetailIsland({ data, analysis, digest })    ← スロットは同名の prop として届く
  └ CompanyDetail が {analysis} {digest} を置く位置だけ決める
```

Astro は名前付きスロットを `<astro-slot name="…">` に包んだ静的な HTML として島に渡し、
props には直列化しない。**props で渡すと同じ文章が HTML の属性にも入る**（1社あたり約2.4KB）。
どちらの節も表示基準で変わらない（AC-30）ので、クライアントが持つ理由が無い。E2E が生の HTML で
一言と要約が1回ずつしか出ないことを固定している。**2つの節のコンポーネントに状態を持たせない**
——ハイドレーションされないので動かない。

### 一言と本文の重複はビルド時に直す

一言がそのまま本文の書き出しになっている会社が **29社**あった（伊藤忠ほか。アートボード 8b の
注記が残していた論点）。「ひとことで言うと」の枠のすぐ下に同じ文が続くので、**取り込みで本文の
1文目を落とす**（`dropRepeatedHeadline`）。一言は本文の要約なので、失われる主張は無い。

- **かぎ括弧の種類はそろえてから比べる。** 伊藤忠は一言が『川下』、本文が「川下」で、そろえないと
  26社しか拾えない
- **言い換えは落とさない。** 書き出しが似ているだけの会社が28社ある（「〜に乗っている会社で、…」と
  「〜に乗っている会社だ。…」）。一言を本文が言い直すのは要約として正常で、機械的な線を引けない
- 生成（C9）はやり直していない

## 出典の表示

- **ドメインと参照した日を添える**（`www.mitsui.com・2026年9月8日に参照`）。spec の未決事項
  「リンクが切れたときの扱い」をこれで決めた。**切れたリンクを検出して落とすことはしない**——
  データは年1回の更新で、参照日が読めれば、開いて404でも「その日にはあった」と読める。ドメインは
  開く前に誰の文書かを示す（出所の信頼性は読者が評価してよい・ADR-0015 決定4）
- **`rel="nofollow noopener"`・別タブ。** 2,961ページに外部リンクが載るので、評価を渡す意図の無い
  リンクとして示す（未決事項「`rel` を付けるか」を決めた）
- **資料が無い会社（2,515社）では「参照した資料」ごと出さない**
- 形が崩れた出典（`http(s)` でない URL・空の題名・日付の形が違う）は**ビルドを落とす**
  （`parseSources`）。黙って空にすると「資料の無い分析」として配られる

## /about

`#company-analysis`「要約と分析の作り方」を「会社の説明文の作り方」の直後に置いた。材料の4つ
（有報の4節・同じページの数値・会社が自ら出している文書・一般知識）、**具体的な数値は材料に
あるものだけ**、検査の2段、対で出すことを書く。説明文の節（一般知識を使わない）と並べて、線の
違いが読めるようにした。
