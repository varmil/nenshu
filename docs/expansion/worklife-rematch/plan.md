# plan.md — E5 働きやすさ指標の再突合

Issue: [#177](https://github.com/varmil/nenshu/issues/177)
spec: `docs/expansion/spec.md` 1.6・1.6a・AC-8 ／ 手順書: `docs/worklife/data-ingest/design.md`
ADR: [ADR-0009](../../adr/0009-worklife-corporate-number.md)（突合キーは法人番号だけ）

E2（#173）で母集団が 1,867社 → 2,961社になった。**新しく入った1,094社に働きやすさ指標が1つも無い**ので、女性活躍DBとの突合をやり直す。**設計上の判断は無い。**

---

## 段取り

### 1. 全件版 ZIP を手に入れる

**ダウンロードURLに UUID が入っていて固定できない**（`extract.ts` の注記）ので、取得は自動化されていない。落としたものを `pipeline/worklife/source/` に置く。

**置いたファイルの名前・sha256・行数は `manifest.json` に残す**——同じ日付の版が2つ出回ったときに、どちらで作ったデータかが後から分かる。

### 2. 母集団の社数を合わせる

`extract.ts` の `EXPECTED_COMPANY_COUNT` は CSV の行数と一致していないと落ちる。**直さないと走らない。**

### 3. 回して、突合率を見る

**突合キーは法人番号だけ**（ADR-0009）。証券コードと社名では突合しない——女性活躍DB側の証券コードは自己申告で誤登録があり、社名は同名別会社が多い。

**新規社の `corporate_number` が全件引けていること**を確かめる（1件でも引けなければ `unified.py` の段で落ちる）。

**率の比較は母集団の変化を織り込んで読む。** 分母が1.59倍になるので、同じ絶対数でも率は下がる。

### 4. 生成物の上限に当たったら、切り出しの発動条件を確かめる

`worklife.json` は gzip 160KB の上限を持ち、**母集団が1.59倍になれば超える見込み**（spec 1.6a の見積もりは約207KB）。

**`docs/worklife/overview.md` が「超えたら注釈を切り出す」と決めているが、その発動条件は Worker バンドルが 3MiB に近づいたときであって、このファイル単体の大きさではない。** W0 の実測では「増分152.5 KiB の6割が注釈・説明で、**バンドルが苦しくなったら**ここが最初の切り出し候補」と書いてある。

**だからバンドルを実測してから決める。** 苦しくなければ上限を引き上げ、根拠を書く。

### 5. 検証

1. **`npm run extract:worklife`** — 236列の検証（`assertHeader`）が通ること。**厚労省が列を足していたらここで止まる**
2. **`npm run build:data`** — サマリーの働きやすさの充足率が上がること（AC-8）
3. **Unit テスト** — 突合社数・gzip の上限・レーダーの母集団
4. **型・lint・ビルド**
5. **Worker バンドルの実測** — 4. の判断の裏を取る
6. **E2E** — 働きやすさの節が新しく入った会社でも出ること
7. **ブラウザで触る**

### 6. docs を書く

`design.md` に突合率・記入率・上限の判断を残す。`manifest.json` を更新する。CLAUDE.md の「現在地」を実態に合わせる。
