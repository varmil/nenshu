# plan.md — E0 初回ロードのペイロード方式（全件embedをやめる）

Issue: [#174](https://github.com/varmil/nenshu/issues/174)
spec: `docs/expansion/spec.md` 1.5・AC-5・AC-6 ／ `docs/ranking/spec.md` 3.・AC-7
ADR: [ADR-0013](../../adr/0013-initial-payload-separate-asset.md)（全件embedをやめる）・[ADR-0004](../../adr/0004-cloudflare-workers-ssr.md)（キャッシュの設計）・[ADR-0012](../../adr/0012-prerender-company-pages.md)（`/` は事前生成できない）

`/` の初回HTMLに全2,961社ぶんのデータを埋めるのをやめ、同じデータを静的アセットとして1回だけ配る。**方式は ADR-0013 が決めてある**ので、この Unit で決めるのは**アセットのURLの形・キャッシュ規則・フォールバックの実装**の3つ。

---

## 段取り

### 1. 先に測る

**動かす前に、いま何バイトが何に使われているかを分ける。** ADR-0013 は「全社ぶんの直列化」を動かすと言っているが、`/` の HTML にはそれ以外も入っている（30行ぶんの markup・業種チップ33件・母集団統計・ロゴのマスク・JSON-LD・RSCペイロード）。**動かせる分がどれだけかを数字にしてから実装する。**

`next start` に対して `curl -H 'Accept-Encoding: gzip'`。現状は gzip **93,327 B**（予算100KBの93.3%）。

**#179 の教訓を踏まえる。** あちらは生成物を2つ増やして cold 1.7〜2.0ms を稼ごうとして戻された。**この Unit が動かすのは桁が違う**——それを先に数字で見せる。

### 2. サーバーが渡すものを決める

**全件の配列を渡すのをやめ、そのURLで表示する1ページぶんと、絞り込みに要るメタデータだけにする。**

いま `RankingApp` は `companies`（全件）から、描画に要るものを全部その場で導いている（`buildRankedCompanies`・`industryCounts`・`fiscalPeriodLabel`・`meta.count`）。**サーバーは同じ関数を通した結果だけを渡す。**

**`curves` は渡したままにする。** 17系列×10点しかなく、推定年収の計算に要る。

### 3. クライアントが全件を取りに行く経路を作る

**初回に1度だけ。** 取れたら以後の操作はいまと同じくクライアント側で完結する（`docs/ranking/spec.md` AC-7 を割らない）。

**URLの形とキャッシュ規則をここで決める。** `/data/companies.json` は既に公開されていて 200 を返すので**新しいビルド成果物は要らない**が、**古いHTMLが新しいJSONを引く組み合わせ**（`/` はブラウザ1時間・エッジ24時間キャッシュされる）を塞ぐ必要がある。

**キャッシュ規則の置き場所は `web/lib/cache/headers.ts` の1か所**（ADR-0004）。`public/_headers` と `headers()` のどちらに置くかを design.md で決める——**`_next/static/*` は Worker を経由しないので `public/_headers` にある**が、`/data/*` はどちらの経路にも書ける。**`headers()` を触ったら E2E を Worker に向けて回す**（CLAUDE.md）。

### 4. 届く前・届かなかったときの経路

**すべての状態は URL にあり、`/` はどの URL でも正しく SSR できる**（ADR-0004）ので、**実ナビゲーションに倒せる。**

**この経路を持たない実装にしない**——届かなかったときに操作が沈黙する（ADR-0013 の「結果」）。

**分岐は1か所に閉じる。** いま `RankingApp` の操作はすべて `applyFilter` / `setState` を通る。**ボタンごとに分岐を書くと、増やしたフィルタで倒し忘れる**（`page` を1に戻すのを1か所に閉じているのと同じ理由）。

**業種チップとページ送りは既に `<a href>` の実体を持つ**（クロール経路のため・ADR-0006／U6）ので、横取りをやめれば実ナビゲーションになる。**ボタン類（表示基準・年齢・並び替え・フィルタ）は実体を持たない**ので、そこをどうするかが設計になる。

**`useLocationSyncedState`（U14）の3規則と両立させる。** マウント時は URL が正・アプリ側の操作でだけ URL に書く・自分のパスを離れたら書かない。

### 5. ビルドがずれたときに引き継がない

**`companies.meta.version` を突き合わせる**（ADR-0013）。食い違ったらクライアント側の引き継ぎをやめ、実ナビゲーションのまま動かす。

**`version` はデータの版（`DATA_VERSION`）で、ビルドごとには変わらない。** それで足りるか、`generatedAt` まで見るかを design.md で決める。

### 6. E2E の測り方を変える

**「リクエスト数0」から「操作の後に増えない」へ**（ADR-0013）。初回に1回だけデータを取りに行くようになるので、**そのリクエストを数えない形にする。緩めすぎると AC-6 が守れなくなる**——`collectPageRequests` を画像とファビコンで緩めたときと同じ扱いにする。

### 7. 検証

順に確かめる。**前を確かめずに次へ進まない。**

1. **Unit テスト** — サーバーが渡す形・クライアントの引き継ぎ・version の食い違い・フォールバック
2. **型・lint・ビルド**
3. **ペイロードの再測** — 1. で測った値と突き合わせる。**AC-5（gzip 100KB以内）は元から満たしているので、見るのは「どれだけ動いたか」**
4. **E2E** — AC-6（操作でネットワークが増えない）・初期表示の30社が HTML に残っていること（SEO）・JS 無効でも表が出ること
5. **`wrangler dev --local` で `/` の CPU を前後で測る**（ADR-0012 と同じ手法・40リクエストの平均）。**全社ぶんの直列化がリクエストから消えることの裏を取る**
6. **ブラウザで触る** — 届く前に操作したときに実ナビゲーションになること。届いた後はネットワークが起きないこと

### 8. docs を書く

`design.md` に**出来上がりの構造**を書く。サーバーが渡す形・アセットのURLとキャッシュ規則・フォールバックの経路・version の突き合わせ・実測値（ペイロード・CPU）。

`docs/ranking/spec.md` 3.「データ量」の読み方をはっきりさせる（予算はHTMLにかかり、アセットは別枠）。`docs/ranking/ranking-pagination/design.md` の「クライアントは既に全件を持っている」を「初回ロード後は持っている」に改める。
