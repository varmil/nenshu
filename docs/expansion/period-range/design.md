## 時点は2種類ある

**母集団の時点は幅、1社の時点はその会社の決算期。** この2つを混ぜない。

| | 出す場所 | 値 |
| --- | --- | --- |
| **幅** | `/` の title 末尾・`/`/`/?age=N`/`/?ind=X`/`/about` の description・`/` のリード文・`/about`「対象範囲」 | `companies.meta.fiscalPeriodRange` |
| **1社** | `/company/[id]` の description・「有価証券報告書の実測値（◯◯）」の見出し | `companies.periods[row[9]]` |

**企業詳細に幅を出さない理由。** 3月期の会社のページに「〜4月期」が付くと、そのページの数字がいつのものかがぼやける。1社ぶんを出せる場所で幅を出す理由が無い。

## データの形

```jsonc
{
  "meta": {
    "count": 1867,
    "fiscalPeriodRange": { "from": "2026-03", "to": "2026-04" },  // 最古と最新
  },
  "periods": ["2026-03", "2026-04"],   // 会社ごとの決算期（昇順）
  "rows": [
    ["6861", "株式会社キーエンス", 8, 5, 35, 11.3, 21783259, 3306, 0, 0]
    //                                                            ↑ periods への添字
  ]
}
```

**会社ごとの決算期は文字列プールの添字で持つ。** 値の種類は現状2つ・拡大後14しかない。`YYYY-MM` をそのまま並べると `/` の HTML が4倍以上増える（`/` は全社ぶんをHTMLに埋めている）。

**`meta.fiscalPeriod`（単一の代表）は消した。** 残すと「代表」と「幅」の2つの時点が同時に存在し、どちらを出すかの分岐が場所ごとに要る。

## 文字列にするのは `web/lib/data/period.ts` の1か所

S3 の決定をそのまま持ち越す。3つの関数を出す。

| 関数 | 入力 | 出す |
| --- | --- | --- |
| `fiscalPeriodLabel(meta)` | 幅 | `2026年3月期〜4月期` |
| `companyFiscalPeriodLabel(companies, row)` | 1社 | `2026年3月期` |
| `periodLabel(period)` | `YYYY-MM` 1つ | `2026年3月期` |

**同じ年なら後ろの年を省く。** `2026年3月期〜2026年4月期` は冗長。**年が違えば省かない**——`2025年3月期〜2026年5月期` を `2025年3月期〜5月期` と書くと2025年5月期と読めてしまう。

**`from` と `to` が同じなら1つだけ出す**（`2026年3月期`）。全社が同じ決算期のデータでも自然に読める。

## 代表の過半チェックを、幅のガードに置き換えた

**旧**: 最頻が過半に届かなければ落とす。
**新**: `from` と `to` の差が24か月を超えたら落とす。

**旧ガードは拡大後に通ってしまう。** 3月期は 1,881/2,962 = 63.5% で過半を超えるので落ちない。**1,081社の決算期が違うまま「2026年3月期」と名乗るほうが、落ちるより危ない。**

**24か月の根拠。** 母集団は「直近12か月に有報を出した会社」（ADR-0011）なので幅は普通12か月に収まり、提出が遅れた会社が混じっても15か月で止まる（拡大後の実測が `2025-03` 〜 `2026-05`）。**24か月を超えるのは取得側の異常**で、黙って通すと何年も前の数字が同じ表に並ぶ。

**幅は毎回ビルドのサマリーに出る。** ガードを緩めたぶん、目に入る場所に置いた。

```
companies.json: 1867行, gzip 44.3KB, 決算期 2026-03〜2026-04（2種類）
```

## `/about` は幅と偏りの両方を出す

**幅だけだと端が全体を代表しているように読める。** いまの端は4月期の2社（ヤガミ・ダイサン）で、全体の 0.1% しかない。

```
2026年3月期〜4月期 の有価証券報告書（EDINET に 2026年6月1日〜7月10日 に提出されたもの）。
決算期は会社ごとに違い、いちばん多いのは 2026年3月期 の 1,865社（全体の 99.9%）です
```

**「3月期が中心」という直書きをやめ、`buildAboutFacts` の `fiscalPeriodTop` から引く。** 拡大後は自動で「2026年3月期 の 1,881社（全体の 63.5%）」に変わる。

**ここだけは幅と1社ぶんの決算期が同じ画面に出る**が、これは同じ語の重複ではなく「範囲」と「その内訳」という別の情報になる。E2E の「1画面に1回」は**幅のほう**を数える。

## ペイロード（実測）

`next start` に対して `curl -H 'Accept-Encoding: gzip'`。

| | 前 | 後 | 増分 |
| --- | ---: | ---: | ---: |
| `/`（gzip） | 63,856 B | **64,157 B** | **+301 B** |
| `/`（raw） | 374,617 B | 378,474 B | +3,857 B |
| `/company/6861`（gzip） | 18,726 B | 18,730 B | +4 B |
| `/about`（gzip） | 20,892 B | 20,966 B | +74 B |

**予算（100KB）の 62.7%。** 余白は 36.1KB。

**拡大後は +301 B では済まない。** いまは決算期が2種類しかなく添字がほぼ全部 `0` なので gzip が極端に効く。**拡大後の分布（14種類・実測の比率）を合成して測ると 1,867社で +1,301 B、2,962社なら +2,064 B**。`/` の見込み（90,724 B）に足すと 92.8KB で、**余白が 9.3KB → 7.2KB に減る**。E0（ADR-0013・#174）の必要性はそのぶん強まる。

**新しいデータファイルは作らなかった。** #179 が「仕掛けの重さに対して効果が見合っていない」として生成物を2つ戻したばかりで、gzip +301 B のために1つ増やす理由が無い。

## 検証

- **Unit** — 幅の文字列（同一・同じ年・年をまたぐ・0落とし・壊れた値）、会社ごとの決算期、新しいガード（15か月は通る／24か月超は落ちる）、`buildData` の出力（`fiscalPeriodRange` と `periods` の添字が全1,867社で CSV と一致）
- **E2E**（`e2e/data-period.spec.ts`）— title・description・画面の3方向、モバイルで消えない位置、1画面に1回、データとの一致。**4月期の会社（ヤガミ `/company/7488`）で別の値が出ることを見る**——同じ文字列がハードコードされていないことは、これで初めて分かる
- 全体: web 471件・pipeline 158件・E2E 355件が通る
