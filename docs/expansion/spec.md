# spec.md — 掲載企業数の拡大

対象面: user-web（ユーザー画面）

親 Issue: [#22](https://github.com/varmil/nenshu/issues/22)

有報を出している内国法人を、決算期によらず全部載せる。用語は `docs/product/glossary.md` に従う。

数値はすべて実測値。EDINET API の書類一覧は2025-08-25〜2026-08-24の平日261日ぶん、有報CSVは同じ窓の4,132件を実際に落とし、いまと同じフィルタに通したうえで `npm run build:data` と `npm run build` まで回して測った。

---

## 1. 何を作るか（WHAT）

### 1.1 母集団の定義

**「直近12か月に有報（`docTypeCode=120`）を提出した内国法人・組合」を母集団にする**（ADR-0011）。

いまは「2026年6月1日〜7月10日に提出されたもの」で、これは3月期決算に貼り付いた窓になる（`pipeline/salary/unified.py` の `build()` が日付を直書きしている）。**この窓を外す。**

**なぜ12か月か** — 有報は事業年度ごとに1回出る。12か月の窓なら、決算期がいつであっても各社ちょうど1回入る。窓を狭めると決算期で会社が消え、広げると同じ会社の複数年ぶんが入る。

**外国法人・組合と外国政府等は落とす。** 窓の中に外国法人200社・外国政府等28社がいるが、転職先ではない。いまの `run.unlisted_docs()` が非上場側で使っている線（`提出者種別 == "内国法人・組合"`）を、上場側にも同じように当てる。

### 1.2 1社1件の選び方

**EDINETコードで1件に寄せ、期末（`periodEnd`）が新しいものを採る。**

いまの `edinet.annual_reports()` は証券コードをキーに、`run.unlisted_docs()` は EDINETコードをキーに、**どちらも「後に見つかったものが勝つ」で寄せている**。窓を12か月に広げると、これが会社を落とす。

**同じ年に有報を複数出す会社が実在する。** 実測で、りそな銀行と三井住友信託銀行は窓の中にそれぞれ4件の有報（`docTypeCode=120`）を持つ。**「後に見つかったものが勝つ」で「従業員の状況」を持たない書類が残り、この2社が母集団から消えた**（期末で選び直したら戻った）。

**提出が遅れて、窓の中に前の期の有報しか無い会社もある。** ニデック（6594）は 2025-03-31 期の有報がこの窓の中にあり、それがこの会社の最新になる。**窓が「いつの数字か」を決めるのではなく、会社ごとの期末がそれを決める**（決算期の出し方は 1.4）。

**期末が同じ書類が複数あるとき（訂正報告など）は `docID` が大きいほうを採る**（`fetch_history.targets()` と同じ規則）。

**キーを証券コードから EDINETコードに変える。** 証券コードは非上場の会社に無く、上場廃止で外れる。EDINETコードは年をまたいで変わらない（ADR-0006）。

### 1.3 掲載の条件は変えない

`unified.build()` のフィルタはそのまま置く。

- 平均年間給与と平均年齢の両方がある
- 平均年齢 20〜65歳、平均年間給与 100万円超
- **単体従業員100人以上**（`MIN_EMPLOYEES`）

**この線を緩めて社数を増やさない**（intent.md「作らないもの」）。母集団が広がるのは窓を外した結果であって、条件を緩めた結果ではない。

**省いた社数を `/about` に出す。** 条件そのものは既に `/about` の「対象範囲」に理由付きで書いてある（`単体従業員100人以上（数人しかいない持株会社が上位を埋めるのを避けるため）`）が、**それが何社を落としているかは書いていない。** 窓を広げると **4,132社のうち 1,049社**（掲載する2,962社の3分の1超）がこの線で落ちるので、**数を出さないと「有報を出している会社は全部載っている」と読めてしまう**。運営者の指示（2026-08-24）。

### 1.4 決算期の表し方

**決算期は1つで代表できなくなる。** いま `companies.meta.fiscalPeriod` は最頻の1つ（`2026-03`）で、`build-data.ts` の `dominantFiscalPeriod()` は**代表が過半に届かなければビルドを落とす**。母集団を広げると3月期は6割弱まで下がる。

**「代表を1つ出して過半で名乗る」をやめ、時点は幅で出す。** 画面と title・description に出す文字列は `web/lib/data/period.ts` の1か所のままにする（S3・`docs/site-chrome/spec.md` 5.）。

**`2026年3月期` の直書きは引き続き禁止。** 値はデータから引く。

### 1.5 初回ロードのペイロード

**全件をHTMLに埋めたままでも予算には収まる。** 実測で `/` の HTML は gzip 63,654 B → **90,724 B**（予算100KBの90.7%）。**親 Issue のコメントが見込んでいた137KB超過は起きない**——社数を4,000で見積もったことと、gzip 後のサイズを行数に比例させたことの2つで外れていた。

したがって**ペイロードは母集団の拡大の前提条件ではない。** 満たすべき値は次のとおり。

- `/` の初回ロード（HTML）は **gzip 後 100KB 以内**（`docs/ranking/spec.md` 3.「データ量」を引き継ぐ）
- 年齢スイッチ・フィルタ・検索・並び替え・ページ送りの操作で、**HTMLとRSCペイロードを取り直さない**（`docs/ranking/spec.md` AC-7）

**ただし余白は 9.3KB しか残らない。** 1行あたりの情報を増やす変更（1.4 の会社ごとの決算期など）がそのまま予算にぶつかる。**全件embed をやめる方式は決めてある（ADR-0013）が、この施策の中では拡大を待たせない。**

### 1.5b 上位の顔ぶれと外れ値

**1位が入れ替わる。** 実測でヒューリック（2,295万円・12月期）とＭ＆Ａキャピタルパートナーズ（2,266万円・9月期）がキーエンス（2,178万円）の上に来る。**`docs/ranking/spec.md` の AC-1 が固定している「1位にキーエンス」は成り立たなくなる**ので、あちらの受け入れ基準を書き換える。

**「従業員の状況」本文からの読み取り（`source == "textblock"`）が上位に出る。** 103社から139社に増え、そのうち1社が3位に来る。

```
株式会社山田クラブ２１（E04731・非上場）
  本文: 231(13)57.309.822,360,598
  「勤続9.8／2,236万円」とも「勤続9.82／236万円」とも読める（パーサは候補を2つ返す）
```

これは既知の問題（CLAUDE.md「同じ表の読み方が割れることがあり、1書類の中では決められない」）で、**年をまたいで選び直す仕組み（`history.resolve_candidates`）はタグ由来の値を基準にするため、どの年もタグを持たないこの会社では効かない。**

**textblock 由来を切り捨てない。** 同じ経路でサントリーホールディングス（1,176万円）・日本経済新聞社（1,224万円）・竹中工務店（1,152万円）が正しく入る。切ると非上場の大手が丸ごと落ちる。

**上位30社を目視で確かめてから公開する。**

### 1.6 派生データの追随

母集団はロゴ・10年推移・働きやすさ指標の単位でもある。**新しく入った会社だけ空になる状態を、気づけないまま公開しない。**

| 施策 | 追随のしかた | 追随しなかったときの見え方 |
| --- | --- | --- |
| `logo` | 新規社ぶんを `npm run build:logos` で調達 | 頭文字のマス目が並ぶ（壊れはしない） |
| `timeseries` | 新規社ぶん10年を `fetch_history.py` → `history.py` | 推移の節が出ない |
| `worklife` | 新しい母集団で `extract.ts` を回し直す | 「掲載なし」になる |
| `performance` | 新規社ぶんを `pipeline/performance/extract.py` で抜き直す | 稼ぐ力の軸と推移の節が欠ける |

**`performance` は2つのデータを持ち、要る書類が違う。**

- **稼ぐ力（P0・`performance.json`・レーダーの軸）は最新年の書類1件で足りる。** 5期ぶんの経常利益が1書類にタグ付けされている（`jpcrp_cor:OrdinaryIncomeLossSummaryOfBusinessResults` が5つのコンテキストで来る）ので、**E2 が落とした ZIP がそのまま使える**
- **稼ぐ力の推移（P2・`profit-history.json`）は10年ぶんの書類が要る。** 各年の従業員数は**その年の書類の当期からしか取れない**（`docs/performance/profit-trend/design.md`）。**E4 と同じキャッシュを使う**

**壊れはしないが、追随の順序を決めずに公開すると「新しく入った会社は中身が薄い」状態が固定される。** overview.md で Unit の順序として持つ。

### 1.6a データファイルの上限に当たるもの

`build-data.ts` は生成物ごとに gzip の上限を持ち、**超えるとビルドが落ちる**。母集団が 1.59倍になると、**2つが上限を超える見込み**になる。

| ファイル | 現状（gzip -9） | 2,962社の見込み | 上限 | |
| --- | ---: | ---: | ---: | --- |
| `companies.json` | 44,631 B | 70,610 B（実測） | 102,400 B | |
| `history.json` | 68,012 B | 約108,000 B | 153,600 B | |
| `worklife.json` | 130,222 B | **約207,000 B** | 163,840 B | **超える** |
| `performance.json` | 7,882 B | 約12,500 B | 32,768 B | |
| `radar.json` | 11,303 B | 約18,000 B | 49,152 B | |
| `profit-history.json` | 194,085 B | **約308,000 B** | 262,144 B | **超える** |

**見込みは 1.587倍を掛けただけで、実測ではない。** `companies.json` の実測（44,631 → 70,610 B = 1.582倍）がほぼ比例だったので、同じ形（会社ごとの数値配列）のファイルは比例で読んでよい。

**上限は「気づくための線」であって守るべき値ではない**（`build-data.ts` のコメントがどれもそう書いている）。**超えたら実測に合わせて引き上げる。** ただし `worklife.json` は「増分の6割が注釈なので、超えたらそこを別ファイルにする」と `docs/worklife/overview.md` が決めているので、そちらの判断を先に通す。

**`profit-history.json` と `worklife.json` は `/company/[id]` だけが読む。** `/` のペイロードには効かない。

### 1.6b Worker の実行予算

**`/company/[id]` は全社ぶんが事前生成されている**（ADR-0012・R1・Issue #180）。**事前生成するページ数は母集団そのもの**なので、この施策はデプロイの成果物をそのまま押し上げる。

現状は 1,874ページ・**344MB**・ファイル数 3,528（`docs/adr/0012-prerender-company-pages.md` の実測）。無料枠の上限は**ファイル数 20,000・1ファイル 25MiB**。

2,962社にすると 2,969ページになる。**比例で伸ばした見込みは 545MB・約4,600ファイルで、上限には当たらない**（ページ数がそのまま増え、1ページあたりの大きさは変わらないので、gzip のときと違って比例で読んでよい）。**ビルドの事前生成は 19.9秒 → 32秒ぶん**を見込む。

**この施策が壊すものではないが、E2 の後で実測して ADR-0012 の数字を更新する。**

**`/` は事前生成できない。** `searchParams` を読むので動的なまま残る（ADR-0012 決定4）。**動的なまま残るページで母集団に比例するのは、モジュールの初期化（`import` したデータの `JSON.parse`）と、全社ぶんの直列化（ADR-0013・E0）になる。**

### 1.7 対象外

**有報を出していない会社。** 外資系日本法人を含め、公式情報が無い（intent.md）。

**掲載条件の緩和。** 1.3 のとおり。

**過去年の母集団の遡及。** いま載っている1,867社の過去10年（`timeseries`）はそのまま。新規社の過去10年は 1.6 の追随で足す。

## 2. 受け入れ基準

### AC-1 決算期で会社が消えない

```gherkin
Given ランキングを開く
When 「キヤノン」「日本たばこ産業」「楽天グループ」「イオン」「ファーストリテイリング」を検索する
Then いずれも1件以上ヒットする
```

### AC-2 1社1行

```gherkin
Given 母集団を組み直す
When 同じ EDINETコードの会社を数える
Then どの EDINETコードも1行しか無い
And 同じ年に有報を複数出す会社（りそな銀行・三井住友信託銀行）が母集団に残っている
And その行は「従業員の状況」を持つ書類から作られている
```

### AC-3 外国法人を載せない

```gherkin
Given 母集団を組み直す
When EDINETコードリストの提出者種別を引く
Then すべての行が「内国法人・組合」である
```

### AC-4 掲載条件が変わっていない

```gherkin
Given 母集団を組み直す
Then すべての行が 単体従業員100人以上・平均年齢20〜65歳・平均年間給与100万円超 を満たす
And いま載っている1,867社は1社も落ちない
```

```gherkin
Given /about の「対象範囲」を読む
Then 単体従業員100人未満の会社を省いていることと、その理由が読める
And この線で何社を省いたかが数で読める
And その数は直書きではなくデータから導かれている
```

### AC-5 初回ロードのペイロード

```gherkin
Given 本番ビルドの / を JavaScript 無効で取得する
Then レスポンスの gzip 後のサイズが 100KB 以内である
```

### AC-5b 上位の顔ぶれ

```gherkin
Given 母集団を組み直したあと
When 平均年間給与の上位30社を読む
Then 「従業員の状況」本文から読み取った値（source == "textblock"）で、
     候補が2つ以上あるものが1件も残っていない
And docs/ranking/spec.md の AC-1（1位はキーエンス）が新しい母集団に合わせて改訂されている
```

### AC-6 操作でネットワークが起きない

```gherkin
Given ランキングを開き、初回ロードが終わっている
When 年齢・業種・検索語・並び替え・ページを操作する
Then HTML と RSC ペイロードのリクエストが発生しない
```

### AC-7 時点が幅で出る

```gherkin
Given データの時点を出しているすべての場所（/ の title・全ページの description・/・/company/[id]・/about の画面）
Then 単一の決算期を代表として名乗っていない
And 決算期の直書きが1つも無い
```

### AC-8 派生データの欠けが見える

```gherkin
Given 母集団を組み直したあと
When ビルドのサマリーを読む
Then ロゴ・10年推移・働きやすさ指標・稼ぐ力のそれぞれについて、母集団のうち何社ぶんが揃っているかが出る
```

### AC-9 生成物の上限

```gherkin
Given 母集団を組み直したあと
When npm run build:data を実行する
Then どの生成物も gzip の上限で落ちない
And 上限を引き上げたファイルは、引き上げた値が実測に基づいている
```
