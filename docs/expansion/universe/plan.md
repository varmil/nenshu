## 段取り

### 1. 母集団の組み立てを spec 1.2 の規則に置き換える

**先にここを直す。窓を広げるのは後。** 順序を逆にすると、寄せ方のバグで消えた会社が「そもそも窓に入っていない会社」と見分けられなくなる。

いまは上場側（`edinet.annual_reports()`）が証券コード、非上場側（`run.unlisted_docs()`）が EDINETコードで、**どちらも「後に見つかったものが勝つ」**。これを EDINETコードで寄せ、**期末が新しいほう（同じなら `docID` が大きいほう）**を採る形にする。

**証券コードの有無で経路を分ける理由が無くなる。** 上場側にも「内国法人・組合だけ」を当てる（spec 1.1）ので、2つの関数がやることは同じになる。**分けたままにすると同じ規則が2か所に増える。**

**`unlisted_docs()` が窓を持っていない**のも同時に直す。いまはキャッシュ済みの `list_*.json` を全部走査するので、**母集団が「キャッシュに何年ぶんあるか」で変わる**（10年推移のために10年ぶん取ってある）。

**この段でいったん現状の窓のまま回し、1,867社が1社も減らないことを確かめる。** 寄せ方の変更だけを切り分けて見る。

### 2. 窓を直近12か月にする

**窓は取得を回す日から遡って12か月**（ADR-0011）。決算期に貼り付いた日付を直書きしない。

**「同じ会社の複数年ぶんが入る」ことを 1. の期末優先が受け止める。** 窓の両端では前年の書類も入るが、期末で選べば新しいほうが残る。

### 3. CSV を作り直し、上位30社を目視する

`unified.py` を回して `pipeline/data/ranking_unified_2026.csv` を差し替える。**書類一覧と有報 ZIP は 2025-08-25〜2026-08-24 ぶんがキャッシュにある**ので、落とし直すのは窓が動いたぶんだけになる。

**AC-5b は目で見る以外に方法がない。** `source == "textblock"` の会社が139社に増え、**そのうち候補が2つ以上ある行が上位に来る**（山田クラブ２１が3位）。パーサは1書類の中では決められず、年をまたいで選び直す仕組み（`history.resolve_candidates`）も**タグを1度も持たない会社では効かない**。

- 上位30社を印字して、**候補が割れている行が残っていないか**を見る
- **textblock 由来そのものは切らない**——同じ経路でサントリー・日経・竹中工務店が正しく入る（spec 1.5b）
- 落とすなら**どう落としたかを design.md に残す**

**いま載っている1,867社が1社も落ちないことを機械で確かめる**（AC-4）。目視ではなく、旧CSVの `edinet_code` を全部引く。

### 4. 生成物を作り直し、上限に当たったものを実測で引き上げる

`npm run build:data`。**`EXPECTED_ROW_COUNT` を先に更新しないと落ちる。**

上限は「気づくための線」であって守るべき値ではない（spec 1.6a）。**超えたら実測に合わせて引き上げ、引き上げた根拠を書く。** ただし `worklife.json` は「増分の6割が注釈なので、超えたらそこを別ファイルにする」と `docs/worklife/overview.md` が決めているので、**そちらの判断を先に通す**——E2 の時点では worklife は追随していない（E5・#177）ので行数は増えないはずだが、当たったら止まって考える。

### 5. 派生データの充足率をサマリーに出す（AC-8）

**新しく入った会社だけ中身が空になる状態を、気づけないまま公開しない**（spec 1.6）。ビルドのサマリーは既に生成物ごとの社数を出しているので、**母集団に対する割合を添える**形にする。

ロゴは `build:data` の管轄ではない（`build:logos` が作る）が、**AC-8 が名指ししている4つのうちの1つ**なので、`logos.json` を読んで同じ行に並べる。

### 6. ランキングの spec と E2E を新しい母集団に合わせる

**`docs/ranking/spec.md` の AC-1 が「1位はキーエンス」を固定している。** ヒューリック・Ｍ＆Ａキャピタルパートナーズが上に来るので改訂する（spec 1.5b・AC-5b）。

**社数の直書きを実態に合わせる**——`/about`「対象範囲」・`docs/product/product.md`「データの前提」・`docs/ranking/spec.md`。**画面に出る社数は `companies.meta.count` から引いているので直さなくてよい**（S3 の決定）。直すのは docs の地の文と、テストの期待値。

**`/about` に「単体従業員100人未満で省いた社数」を出す**（spec 1.3・AC-4 の2つ目）。**運営者の指示（2026-08-24）で、条件そのものは既に書いてあるが数が無い。** 1,049社は掲載2,962社の3分の1超で、**数を出さないと「有報を出している会社は全部載っている」と読める。** 数はデータから導く——直書きしない。

### 7. 事前生成の成果物を実測する

`generateStaticParams` は `companies.json` から引く（ADR-0012）ので**追随は自動**だが、成果物は母集団に比例する。現状 1,874ページ・344MB・3,528ファイルに対し、**見込みは 2,969ページ・545MB・約4,600ファイル**（比例。実測ではない）。無料枠の上限は**ファイル数 20,000・1ファイル 25MiB**。

**実測して ADR-0012 の数字を更新する。** 見込みどおりなら数字を差し替えるだけ、外れたら原因を design.md に書く。

### 8. 検証

順に確かめる。**前を確かめずに次へ進まない。**

1. **母集団の性質** — AC-2（EDINETコードが一意・銀行2社が残る・その行が従業員の状況を持つ）・AC-3（全行が内国法人）・AC-4（現行1,867社が全部残る／掲載条件を満たす）を**テストで固定する**。目視で1度確かめて終わりにしない
2. **`npm run build:data`** — 落ちないこと。サマリーに充足率が出ること
3. **`pipeline` の Unit テスト** — Python と TypeScript の推定式の一致（`build-data.test.ts`）が**新しい母集団の全社**で通ること
4. **型・lint・ビルド** — `cd web && npm run typecheck && npm run lint && npm run build`。**事前生成が 2,969ページぶん走る**ので、ここで 7. の実測も採る
5. **web の Unit テスト** — 社数・順位・偏差値を固定しているテストが新しい母集団で通ること
6. **ペイロードの実測** — `/` の HTML が gzip 100KB 以内（AC-5）。見込みは 90,724 B
7. **E2E** — AC-1（キヤノン等が引ける）を足す。**既存の期待値のうち、1位や社数に依存しているものを直す**
8. **ブラウザで触る** — 新しく入った会社の `/company/[id]` が 404 にならないこと（`dynamicParams = false` なので一覧に入っていなければ404）

### 9. docs を書く

`design.md` に**出来上がりの構造**を書く。母集団の組み立ての形、寄せ方、窓の決め方、実測値（社数・上位の顔ぶれ・ペイロード・事前生成の成果物）。

ADR-0012 の実測値を更新する。CLAUDE.md の「現在地」を実態に合わせる。

## 先に決めてあること

**掲載の条件は変えない**（spec 1.3・ADR-0011）。`MIN_EMPLOYEES = 100` も年齢と金額の範囲もそのまま。**社数を目標にして緩めない。**

**textblock 由来を経路ごと切り捨てない**（spec 1.5b）。

**1位はキーエンスでなくなる**（spec 1.5b）。これは直すべきバグではなく、母集団を広げた結果として受け入れる。

## この Unit でやらないこと

**派生データの追随** — ロゴ（E3・#175）・10年推移（E4・#176）・働きやすさ指標（E5・#177）・稼ぐ力（E6・#182）。**新しく入った会社はこれらが空のまま公開される。** 空であること自体は壊れではない（「掲載なし」の表示を持っている）が、**どのくらい空かはサマリーに出す**（5.）。

**全件embed をやめること**（E0・#174・ADR-0013）。ペイロードは予算内に収まる（spec 1.5）ので拡大を待たせない。

**掲載条件の緩和・外国法人の掲載**（spec 1.7）。
