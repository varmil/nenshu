## 5軸と、その向き

**12時から時計回り**（アートボード 6a）。

| 位置 | 軸 | 値 | 出どころ | 向き |
| --- | --- | --- | --- | --- |
| 上 | 平均年収（有報） | 円 | 有報 | 高いほど外側 |
| 右上 | 有給の取得 | % | 女性活躍DB | 高いほど外側 |
| 右下 | 定着（在籍） | 年 | 有報 | 長いほど外側 |
| 左下 | 稼ぐ力 | 円 | 有報 | 高いほど外側 |
| 左上 | 残業の少なさ | 時間/月 | 女性活躍DB | **少ないほど外側** |

**男女の賃金の差異は軸にしない**（#154）。数値は W1 の節に残っている——図から降ろしただけで、法定開示をそのまま見せる立場は変えていない。

**軸の名前も向きに合わせる。**「残業時間」ではなく「残業の少なさ」。5軸すべてが「外側＝良い」で揃っていないとレーダーは図として読めない。

## 位置は順位で決める

**その指標を公表している会社の中での順位**を 0〜1 に写す。**母集団は軸ごとに違う。**

| 軸 | 母集団 |
| --- | ---: |
| 平均年収・定着 | 1,867社 |
| 稼ぐ力 | 1,864社 |
| 有給の取得 | 895社 |
| 残業の少なさ | 974社 |

**欠測を最下位として数えない。** 掲載率6割の軸で、公表している会社が軒並み上位に寄ってしまう。図の上に「その指標を公表している会社の中での相対位置」と書いてあるのはこの意味になる。

**金額そのものを線形に当てない。** 稼ぐ力は業種中央値に対する倍率が 5%tile 0.08 / 95%tile 4.46 / 99%tile 11.47 で（P0 の実測）、線形だと上位が振り切れて下位が中心に潰れる。**順位なら5軸を同じ規則で置ける**——1軸だけ別の目盛りにすると、1枚の図の中で位置の意味が2種類になる（#154）。

**最下位でも中心には置かない**（`MIN_POSITION = 0.1`）。中心に貼り付けると、**頂点を打たない軸（掲載なし）と見分けがつかなくなる。**「掲載なし」を最低評価に見せないという判断は、逆側からも要る。

## 欠測軸は頂点を打たない

**中心まで引き込んで破線でつながない**（#154・AC-7）。「掲載なし」と書いてあっても、形としては最低評価と同じに見える。

- 頂点を打たない軸を**飛ばして**多角形を閉じる。掲載なしがあっても面積が広がらない
- **軸のラベルは残す**（グレー）。軸ごと消すと5角形が4角形になり、何が公表されていないのかが図から消える
- 頂点が2つの会社は多角形にならないので線だけを引く

キーエンス（残業なし）は4点、三菱UFJフィナンシャル・グループ（有給・残業なし）は3点で閉じる。**#154 が「最悪でも三角形が残る」と書いたとおりになった。**

## 雇用管理区分が2つ以上ある会社は軸に乗せない

**節の表示（W1）は「代表を選ばない」**——区分をそのまま全部並べる（spec 2.2b）。だが**レーダーは1軸に1点しか打てない。**

そこで `representativeValue` は次の順で決める。

1. 全体値があればそれ
2. 無ければ、**区分がちょうど1つのときだけ**その値
3. それ以外は掲載なし

**区分が2つ以上ある会社で1つを選ぶことは、spec 2.2b が禁じた「代表の1区分を選んで残りを捨てる」ことそのものになる。** 平均もしない（spec 1.4）。

キーエンスの有給（区分「正社員」1件・38.8%）はこの規則で軸に出る——アートボード 6a・6b がそう描いている。新日本空調（営業・管理系 67.4 / 技術系 60.8）は掲載なしになる。

## 平均年収の軸だけが表示基準に追随する

**`radar.json` に平均年収は入っていない。** 表示基準（実測値 / 年齢そろえ）で変わるので、`CompanyDetail` が `stats.json` 由来の `current.rankAll` から5軸目を組む（AC-11）。

`radar.json` に入れると、表示基準ごとに9通りの順位を持つことになり、しかも同じものが `stats.json` に既にある。

残り4軸は年齢補正を通さない値なので、サーバーが確定した値のまま渡る。

## モックに合わせなかったもの

| モック（6b） | 実装 | 理由 |
| --- | --- | --- |
| `上位82%` | `895社中883位` | **`上位82%` は上から82%の位置の意味だが、日本語としては上位＝良いに読める。** キーエンスの有給は実データで883/895位なので、「上位99%」と出ると事実と逆の印象になる。「画面には数字だけを出し、水準は順位で読ませる」という既存の判断（偏差値の「上位◯%」を2026-08-20 に外した件）にも揃う |
| リストの並びが 年収→残業→有給→定着→稼ぐ力 | **図と同じ時計回り**（年収→有給→定着→稼ぐ力→残業） | 図とリストの対応が取れる。モックの並びには規則が読み取れなかった |
| 稼ぐ力 `1,240万円`・電気機器の中央値 `310万円` | `4,062万円`・`181万円` | モックの数値は仮のもの。実データを出す |

## `radar.json` は順位だけを持つ（ADR-0011）

**初版は軸の値も一緒に持っていた。落とした。**

4軸の値はすべて、その画面が既に読んでいる別のファイルから引ける。

| 軸 | 値の出どころ |
| --- | --- |
| 有給の取得・残業の少なさ | `worklife.json` ＋ `representativeValue()` |
| 定着（在籍） | `companies.json`（`rows[i][5]`） |
| 稼ぐ力・業種中央値 | `performance.json` |

**同じ数字を2か所に置くと、`radar.json` の `JSON.parse` が倍になる**——`import` したファイルは1バイトしか使わなくても丸ごと解析され、しかも isolate の初回リクエストに課金される（ADR-0011）。

| | raw | `JSON.parse` |
| --- | ---: | ---: |
| 値を持っていた初版 | 84KB | 0.524ms |
| **順位だけ** | **29KB** | **0.161ms** |

`performance.json` を読む側に足したぶん（+0.043ms）を引いても **0.32ms** 減る。

**表示側は、ビルド時に順位を決めたときと同じ `representativeValue()` を通す。** 別の規約で選ぶと**図の頂点と、その隣に出る値が食い違う**——「区分が2つ以上ある会社は軸に乗せない」という規則が片側にしか効かない状態になる。

## レイアウト

**PC は図の右に指標リスト、モバイルは図だけ**（アートボード 6b / 6a）。モバイルで値が読めなくなるわけではない——**軸ラベルに値が入っている**ので、図の中のテキストとして DOM に出る（AC-9）。

**ラベルは5軸とも中央寄せ。** 左右の軸を `start`/`end` にすると、「残業の少なさ」のような6文字のラベルが viewBox の外へ出て切れる。中央寄せなら必要な余白が半分で済み、そのぶん図を大きく取れる（`400×330`・R=88 → `360×300`・R=105）。

**文字は器の幅で決める**（`@container`）。viewBox が固定なので SVG ごと拡大縮小し、user unit で書いた文字も同じ倍率で伸びる（C3 の教訓）。
