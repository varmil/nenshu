# plan.md — P2 稼ぐ力の推移（過去10年間）

Issue: [#168](https://github.com/varmil/nenshu/issues/168) ／ 親 [#154](https://github.com/varmil/nenshu/issues/154)
参照: `docs/performance/spec.md` 2.3・AC-10・AC-11、Claude Design `改善案.dc.html` のアートボード 6e

着手前の段取り。作る形は `design.md`。

## 段取り

1. **年次の従業員数が古い年でも取れるかを最初に確かめる。** T0 では2019年より前で平均年間給与のタグ付けが変わっており（`docs/timeseries/`）、同じことが従業員数にも起きていれば10年ぶんの棒は描けない
   → 検証: キャッシュ済みの書類で年ごとの取得率を測る

2. **10年ぶんの書類を取る。** P0・P1 は最新年の1件で足りたが、**この Unit だけが取り直しを要する**——経常利益は1書類に5期ぶん入っているが、従業員数は当期だけ
   → 検証: 年ごとの社数がサマリーに出る

3. **`parsePerformanceHistoryCsv` に従業員数を足す。** CSV には既に列がある（読んでいなかっただけ）
   → 検証: `cd pipeline && npm test`

4. **`build-data.ts` に `buildProfitHistory()` を足す。** 年ごとに割る——**P0 の「5期の中央値 ÷ 当期の従業員数」とは分母が違う**
   → 検証: `npm run build:data` が通り、`profit-history.json` が出る。gzip 上限

5. **棒グラフを共用にする。** 平均年収の推移と稼ぐ力の推移は「10年ぶんの金額を万円で並べた棒」で同じ。**同じ図を2つ書くと、片方だけ直したときに並んだ2枚の見た目がずれる**
   → 検証: 既存の推移の E2E が緑のまま

6. **表を書く。** 列は 年度・稼ぐ力・従業員数・経常利益（アートボード 6e）。**器は平均年収推移の表と同じ**
   → 検証: 390px で横スクロールが出ない

7. **赤字の書式と経常利益の単位を決める**（spec 5. の未決事項）
   → 検証: 単体テストで固定する

8. **E2E を書く**（`e2e/company-profit-history.spec.ts`）。AC-10・AC-11

9. **`design.md` を書く。** 決めた規則と実測を残す

## 依存

- P0（#155・実装済み）の `extract.py` が年を指定して走らせられる形になっている
- T2（#138）が作った推移の表の器をそのまま使う

## リスク

- **取得だけで約150分かかる**（17,684件・並列3・実測1.9件/秒）。P0・P1 と同時に走らせない
- **年ごとに割らないと分母が実態と合わない。** 従業員数が10年で倍になった会社では、当期の分母で割った過去の年が嘘になる
- **経常利益はあるが稼ぐ力が出ない年がある。** 従業員数はその年の書類からしか取れないので、古い年の書類が取れていない会社ではそうなる。**内挿しない**
- **経常利益を万円で出すと8桁が並ぶ。** キーエンスは 63,575,600万円になり、桁を数えないと大きさが読めない
