# design.md — P0 一人当たり経常利益の取り込み

Issue: [#155](https://github.com/varmil/nenshu/issues/155) ／ 親 [#154](https://github.com/varmil/nenshu/issues/154)
参照: `docs/performance/spec.md` 1.（データ）・AC-1〜AC-5

出来上がった内部構造。段取りは `plan.md`。

## 1書類に5期ぶん入っている（追加のダウンロードが要らなかった）

**`jpcrp_cor:OrdinaryIncomeLossSummaryOfBusinessResults` が `Prior4YearDuration` 〜 `CurrentYearDuration` の5つのコンテキストで来る。** 連結（接尾辞なし）と単体（`_NonConsolidatedMember`）の両方。

**直近5期の中央値は最新年の書類1件だけで出せる。** #155 が「T0 のキャッシュで足りるかを最初に確かめる」と書いていたのはここで、**足りた**。

**従業員数はそうではない。** `NumberOfEmployeesSummaryOfBusinessResults` に相当する要素は無く、当期の `jpcrp_cor:NumberOfEmployees` しかタグ付けされていない。5期ぶんは本文（`BusinessResultsOfGroupTextBlock`）の中にしかない。**年次の従業員数が要る P2（稼ぐ力の推移）だけが、10年ぶんの書類を取り直すことになる。**

## 計算

```
稼ぐ力 ＝ 連結の経常利益（直近5期の中央値） ÷ 連結の従業員数
```

- **連結で組む**（#154 の決定）。理由は `intent.md`。実測でも上位20社に「本社のみ」バッジが1社も無い
- **直近5期は「その会社が持つ年のうち新しい5つ」。** 固定の年で切らない——決算期は会社ごとにずれる
- **連結の従業員数が無い会社（191社）は単体で代用する**（`employeesConsolidated ?? employeesNonConsolidated`）。連結財務諸表を作っていない会社なので、単体がグループ全体でもある。**ただし「連結の従業員数が空」は「連結財務諸表を作っていない」とは限らない**——IFRS の書類は別の要素で連結の人数を書くことがある（次の節）
- **連結の経常利益が無い年は単体で埋める**（`extract.py` の `_put` が基準の優先を見る）
- **最新年の経常利益が単体だけで、連結の従業員数がある会社は出さない**（IFRS・米国基準の240社。下の「連結の経常利益が無い会社は稼ぐ力を出さない」）
- **赤字は負のまま持つ。** 捨てると「データが無い」と区別できなくなる

**同じ年が複数の書類から来る**（2026年の書類の `Prior1` と 2025年の書類の当期）。**遡りの少ないほう＝その年の書類の当期を優先する**——遡った値は会計基準の変更で組み替えられていることがあり、当期のほうが一次の記載になる。

## 連結の従業員数は IFRS 用の要素にもある（#905）

**症状。** ソフトバンクグループの2017年が **144億円/人**（経常利益 2兆8,709億円 ÷ 199人）、2018年が −7.7億円/人と出ていた。有報の連結従業員数は 68,402人・74,952人で、割り直すと 4,197万円/人・−201万円/人になる。

**原因。** 連結の従業員数は `jpcrp_cor:NumberOfEmployees`（当期・メンバー無し）だけでなく、IFRS の書類では「主要な経営指標等」の `NumberOfEmployeesIFRSSummaryOfBusinessResults` にだけ書かれていることがある。**会社独自の名前空間で書く会社もある**（テクマトリックスは `jpcrp030000-asr_E05463-000:` の要素）。完全一致で `NumberOfEmployees` だけを見ていたので連結が空になり、上の「単体で代用する」の規則が**連結を持つ会社に当たっていた**。

**直し。** 代わりの要素の表は `edinet.EMPLOYEES_CONSOLIDATED_FALLBACK_LOCAL_NAMES` の1か所（ローカル名で照合する）。**`NumberOfEmployees` があればそちらを優先し、無いときだけ使う。** ランキング側（`edinet.to_record`）と推移側（`performance/extract.py` の `parse`）が同じ表を見る。毎日の差分更新も `parse` を通るので、新しい書類にも効く。

**影響の範囲。** `performance_history.csv` で連結従業員数が空の行のうち、`back = 0` の3,529行（647社）の書類をすべて読み直した。**埋まったのは24行・16社**（2017年4・2018年11・2019年4・2022〜2026年5）で、残りは連結財務諸表を作っていない会社。**経常利益は1行も動いていない**（従業員数の空欄が埋まっただけ）。ランキング側（`ranking_unified.csv`）で埋まったのはテクマトリックス1社で、レーダーの稼ぐ力が 568万円/人 → 207万円/人になった（情報・通信業の業種中央値 163万円/人に対して 3.49倍 → 1.27倍）。

**分析文も書き直した。** テクマトリックスの生成済みの分析文は、修正前の稼ぐ力を材料にしていた（「情報・通信業の中央値と比べると、一人当たりの経常利益は3倍を超える水準」・一言に「稼ぐ力は業種中央値を大きく上回っている」）。分析は `performance.json` の稼ぐ力を材料に取る（`pipeline/analysis/generate.py`）ので、材料が変わったこの会社だけ `generate.py plan --only E05463` で要約と分析を書き直した。**新しい分析は稼ぐ力の倍率に触れていない**——この会社の指標は「単体の経常利益 ÷ 連結の従業員数」になり、分析規格の見送り条件①（基準の食い違い）に当たるため。材料の数値が変わった会社の文章は、書いた文が数字と食い違わないかを見る（数字の書類は同じなので、定期実行の差分生成では選ばれない）。

| --- | --- | ---: | ---: |
| ソフトバンクグループ | 2017 | 144億円/人 | 4,197万円/人 |
| キリンホールディングス | 2019 | 4億7,849万円/人 | 314万円/人 |

## 連結の経常利益が無い会社は稼ぐ力を出さない（#911）

**規則。** 最新年の経常利益が単体だけで、連結の従業員数がある会社は、稼ぐ力を出さない。レーダーの稼ぐ力は「掲載なし」（`performance.json` の `perEmployee` が `null`）で、業種中央値の母集団にも数えない。推移は `profit-history.json` にキーを作らないので、企業詳細では**「稼ぐ力の推移」の節が節ごと出ず**、「このページの出典」の計算値にも稼ぐ力を挙げない。**判定は `pipeline/scripts/lib/profitBasis.ts` の1か所**で、レーダー（`buildPerformance`）と推移（`buildProfitHistory`）が同じ関数を通る。片方だけ落とすと、同じページで推移は出るのにレーダーは掲載なし（またはその逆）になる。

**対象は240社。** 直近5期がすべて単体の203社と、最新年だけ単体の37社。**すべて IFRS（234社）か米国基準（6社）**で、有報に連結の経常利益が無い（J-GAAP の会社が連結の経常利益の取りこぼしで混ざってはいない）。連結決算を後から作り始めた会社（旧年だけ単体で新しい年が連結の155社）は、旧年の単体がグループ全体なので対象にしない。連結の従業員数が無い会社（連結財務諸表を作っていない）も、単体がグループ全体なので対象にしない。

**なぜ出さないか。** 単体の経常利益は連結の値の代わりにならない。2026-09-30 に、最新年の書類で実測した。

| 比較（当期） | 比の中央値 | ±25%以内 | 0.5〜2倍以内 | 符号が逆 |
| --- | ---: | ---: | ---: | ---: |
| J-GAAP・単体経常 ÷ 連結経常（連結の経常利益がある会社から無作為450社のうち、連結が黒字の415社） | 0.85 | 51% | 83% | 11社 |
| 240社・単体経常 ÷ 連結の税引前利益（連結側でいちばん近い項目。連結が黒字の213社） | 0.59 | 21% | 59% | 15社 |

- 240社の比の10〜90%点は 0.17〜1.04。単体は連結より小さい側に偏り、ばらつきも大きい。物差しを税引後の親会社帰属利益にそろえても向きは同じ（240社 0.86・J-GAAP 1.15）
- 単体従業員が連結に占める割合で分けても、近い値になるのは単体が大半を占める会社だけ（J-GAAP の中央値は 10%未満 0.46・10〜30% 0.68・30〜70% 0.80・70%以上 0.95。240社で 70%以上にいるのは22社）
- ソフトバンクグループは 2024年3月期に単体 −1兆1,612億円・連結の税引前利益 +578億円。武田薬品工業は単体 +2,055億円・連結 −1,424億円
- 連結の経常利益を主要な経営指標等に載せる IFRS の会社もある（グローリー・東京海上ホールディングス・グロービングなど）。連結の経常利益（参考値）と単体の経常利益が別々に載っており、値も違う——有報のとおりなので、連結の値として扱う
- 節の説明「連結の経常利益 ÷ 連結の従業員数」は、240社では事実と違っていた

**逆向き（連結の経常利益 ÷ 単体の従業員数）も出さない。** 判定は「分子と分母の範囲がそろわない」ことで、両向きを見る。分母の代用（連結が無ければ単体）は連結財務諸表を作らない会社のための規則で、連結の利益を単体の人数で割ると大きく出る。当たるのはクラサスケミカル1社（910万円/人と出ていた）。この会社の最新の書類は有価証券届出書の様式（第四号様式）で、2025年12月期が「前期」の文脈にしか無く、連結の従業員数（903人）が取れていない。書類の選び方の問題で、連結・単体の取り違えではない。

**元データ（CSV）の連結・単体の取り違えを全社で確かめた。** 全社の最新の書類（2,979件）を取り直し、主要な経営指標等の経常利益を、同じ書類の損益計算書の経常利益（`jppfs_cor:OrdinaryIncome`）と連結・単体ごとに突き合わせた。

| 確かめたこと | 結果 |
| --- | --- |
| CSV の行（最新の書類から来た3,206行）が書類のラベル・値と合うか | 食い違い0 |
| 主要な経営指標等と損益計算書の経常利益（10,616件） | 157件の差はすべて百万円の丸め |
| 連結と単体が1円まで一致し、従業員数は10%超違う（4件: サンゲツ・ミヨシ油脂・アートネイチャー・コナカ） | 損益計算書でも同じ値で、営業利益と営業外損益の内訳は連結と単体で違う。偶然の一致で、有報のとおり |
| 経常利益を「経常収益」の要素でタグ付けした書類 | **3社14書類**（弘電社・ディーブイエックス・キクカワエンタープライズ）。経常利益が CSV から13行抜けていた |
| 10年推移に書類があるのに経常利益の行が無い（会社×年） | 14件で、上の3社とクラサスケミカルだけ |

**「経常収益」の要素に入った経常利益は読み替える**（`performance/extract.py` の `_mistagged_ordinary_income`）。読み替えるのは、その側（連結・単体）に正しい要素が1つも無く、**当期の値が損益計算書の経常利益と一致するとき**だけ。銀行・保険の経常収益は経常利益と別の要素で並んで載るので当たらない。キャッシュにある6,153書類で旧版と新版の結果を比べ、変わったのは上の3社の14書類だけだった。埋めた13行は差分更新と同じ関数（`update_numbers.merge_performance`）で合流させ、既存の行は1行も変えていない。これで弘電社・キクカワエンタープライズにも稼ぐ力が出る（それぞれ186万円/人・273万円/人）。ディーブイエックスは2023〜2025年が埋まって直近5期の中央値が変わった（297万円/人 → 175万円/人）。

**影響。**

- 稼ぐ力の1位だった ＩＮＰＥＸ（1億7,678万円）と8位の中外製薬が外れた。ソフトバンクグループ・武田薬品工業・三菱商事・第一三共も出なくなった。5期の中央値が0以下の会社は139社 → 130社
- **業種中央値は母集団が変わるので動く。** 33業種のうち27業種で動き、中央値の変化率は絶対値で 6.6%、最大は鉱業 −42%（3社 → 2社）・医薬品 −41%（41社 → 27社）・証券、商品先物取引業 +27%・保険業 +24%。**誤った値を母集団から外した結果**で、鉱業（2社）・空運業（5社）・石油・石炭製品（7社）は母集団が8社に届かない
- 「稼ぐ力」に使う母集団は 2,976社 → 2,737社（91.9%。出さなくなった241社、新たに出た2社）、`profit-history.json` は 2,978社 → 2,738社

**分析文への影響と直し。** 分析は `performance.json` の稼ぐ力と業種中央値を材料に取る（`pipeline/analysis/generate.py`）。数字の書類は同じなので定期実行の差分生成には選ばれず、放っておくとその会社の次の有報まで食い違いが残る。そこでこの変更と一緒に、倍率や向きが新しい値と合わなくなった分析を直した（196社）。

- **全文を書き直した67社**（`generate.py plan --only` → 生成 → 機械ゲート → 検証 → `merge`）。出さなくなった会社で一人当たりの稼ぐ力や業種中央値との比較を書いていた15社、倍率や向きが大きく外れた38社、業種中央値が動いて見送り条件④（またぎ）か①（基準の食い違い）に新たに当たった14社。①④に当たると倍率を書けないので、1文の直しでは主題が崩れる
- **倍率を言う1文だけを直した129社**。「3.9倍に達し」→「3.5倍を超え」、「5倍近く」（5.24倍）→「5倍を超え」、「半分に届いていない」（0.50倍）→「半分ほどにとどまる」のように、`prompts/rounding.md` の線（「近く」は届かない側で9割以上、「超え」は下限の言明、「ほど」は最も近い丸い数、向きを名乗らない語は誤差1%未満、小数の言い切りは表記の桁で一致）に合わせた。直した本文も機械ゲートと別の検証パスに通した
- **見つけ方。** 「中央値」「業種平均」を含む文の倍率・割合・向きの言い方を、旧い値と新しい値の両方で上の線に当て、旧い値で合って新しい値で外れる文と、倍率が1%以上動いて外れている文を直した。見送り条件①④も新旧の中央値で判定した。**検出は言い方の型に頼るので、1回で全部は拾えなかった**——最初は「近く」の9割の線と小数の言い切りを見ておらず、検証パスが「届いていない」「業種並み」「◯倍に達し」の型や新たなまたぎを見つけるたびに型を足して回し直した（4回）
- **後から直した29社**（#917）。
  - この変更で倍率がほとんど動かない（1%未満）のに、前から外れていた文（21社。例: 「1.5倍を超え」で実際は1.48倍）。うち20社は、本人は有報を出していないのに、2026-09-29 の数字の差分更新（refresh の D4）で同業の有報が入って業種中央値が動いたもの。残る1社は書いた当時から丸めが外れていた。倍率の言い方を直し、小数第2位の言い切りや線の際の言い方は、幅のある言い方（「◯倍ほど」「◯割ほど」）に寄せた
  - 前から見送り条件①に当たっていたのに、業種中央値と比べていた6社。比較を外した
  - この変更で外れたのに見落としていた2社（「8割強」で実際は0.88倍、「7割強」で0.77倍）。照合で「◯割強」を下限の言明として扱っていたが、`prompts/verify.md` では上から近づく語で、誤差1ポイント台までしか認めない
  - ほかに、本人が有報を出して数字が先に替わり、分析が差分生成（D6）を待っている4社も外れていたが、これは D6 に任せた
- **「業種平均」「業界平均」と書いていた45社も、業種中央値の言い方に替えた。** データが持つのは業種中央値で、平均は持っていない（平均だと業種の代表値が最上位の1社に引きずられる）。規格（`prompts/generate.md`）が止めていたのは見出しだけで、本文には決まりが無く、検証側にも無かった。同じ文の前半で中央値と比べている文は、後半を「同業の中で高い部類」のように言い直した（同じ比較を2回書かない）。言い換えるときに倍率や向きが今の値と合わない文（「業界の平均並み」で1.125倍、「半分に届かない」で0.447倍）も直した
- **業種中央値が毎日動いて倍率の文が外れていくこと自体は、まだ止めていない**（#916）。D6 が書き直すのは本人の数字の書類が替わったときだけで、機械ゲートと検証は書いた時点のデータとしか突き合わせず、この食い違いを見るテストも無い
- **1文だけ直すときの注意。** 機械ゲートは切らない版の原文があればそちらで照合するが、切った版しか無い環境では、以前に切らない版で通した要約の文が落ちる（4社で「素形材メーカー」「ウェブサイト」などを含む1文が落ちた）。直していない要約は前の版に戻した

**採らなかった案。** 連結の税引前利益など別の連結指標で出す案（定義の違う指標が同じ軸・同じ順位に混ざる）。節を残して稼ぐ力の列とチャートだけ外す案（節の名前と中身が合わなくなる）。

## `performance.json` が持つのは金額と業種中央値だけ

**相対位置（レーダーの頂点をどこに打つか）の算出は表示側（P1）に置く。** 目盛りの決め方を後で変えてもデータを作り直さずに済む。

```
meta:           { count: 1867, matched: 1864, years: [2022..2026] }
perEmployee:    (number | null)[]   companies.rows と同じ並びの2,961件
industryMedian: (number | null)[]   companies.industries と同じ並びの33件
```

**`companies.rows` と同じ並びにする。** `stats.json`・`worklife.json` と同じ制約で、**行がずれると別の会社の稼ぐ力を出す。** 同じループで作り、テストで長さと代表値を固定してある。
