# design.md — W1 企業詳細ページの働きやすさの節

Issue: [#150](https://github.com/varmil/nenshu/issues/150) ／ 親 [#148](https://github.com/varmil/nenshu/issues/148)
参照: `docs/worklife/spec.md` 2.（表示）・AC-6〜AC-12、ADR-0009、`docs/product/glossary.md`

出来上がった内部構造。段取りは `plan.md`。

## 節の見出しは「残業・有給・男女の賃金の差異」

**spec.md 5. の未決事項に対する答え。「働きやすさ」の語は画面に出さない。**

3指標がそれを代表しているわけではない——残業と有給は労働時間、賃金の差異は処遇の話で、束ねる名前を付けると3つの数字が総合評価の材料に見える。`docs/worklife/intent.md` が「働きやすさランキング・スコア・総合評価を作らない」と決めているのに、見出しだけが総合を名乗ることになる。

**指標名をそのまま並べる。** 施策名（`worklife`）とドキュメントの表題は「働きやすさ指標」のままでよい——読者が見るのは画面の側だけである。

## 節の位置

**上部カードと「年齢別の推定年収」の間**（アートボード 6b）。

上のカードまでが有価証券報告書の数字で、ここから下は**別の出典・別の時点**になる。推定の話（年齢別）に入る前に区切りを1つ挟む形にしてある。

節の順序は次のとおり。

```
上部カード（金額・順位・偏差値・分布）
残業・有給・男女の賃金の差異     ← この Unit
年齢別の推定年収
有価証券報告書の実測値（2026年3月期）
平均年収推移（過去10年間）
この数字の作り方
```

## 表示基準と独立であることを型で表す

**`CompanyView.byBasis` の中に入れない。** 推移（`SalaryHistory`）と同じく `CompanyDetail` の別の prop として渡す（AC-11）。

`byBasis` に置くと「年齢そろえにしたら残業時間が変わる」状態を**型の上で作れてしまう**。C2 で推移を `byBasis` の外に出したのと同じ理由で、ここも外に置く。

## 「データが無い」を先に決めてある

3指標のいずれも無い会社が全1,867社中319社（突合できた1,690社のうち142社＋未突合177社）。**欠測は例外ではなく主要な状態**なので、`buildWorklifeView(null)` が**3指標ぶんの空の器を返す**ようにしてある。呼び出し側に「掲載がある会社」と「無い会社」の分岐は無い。

- **節ごと消さない。** 掲載が無い会社でも節は出て、「掲載がありません」「掲載は任意」と書く
- **項目ごとも消さない。** 消すと「残業が少ない会社」と見分けがつかない。「掲載なし」＋その指標に固有の1文を出す
- **その1文は390pxで1行に収める**（Issue #192）。iPhone 12 Pro の本文幅は358pxで、12px の字は29文字までしか入らない。初版は3つとも指標名をそのまま繰り返しており（`この会社は有給休暇の取得率を…`＝30文字）、有給と賃金の差異の2つが2行に折れていた。**指標名は隣の `dt` が持っているぶんを繰り返さない**——`有給休暇の取得率` は `取得率`、`男女の賃金の差異` は `差異` と書く（残業は `残業時間` で26文字なので元から1行）。**単体テストは長さで、E2E は390pxでの高さで固定する**——文言を書き写しても折り返しは捕まらない

## 雇用管理区分は会社が登録したまま

spec 2.2b の決定を、コードの側では次の3点として持っている。

- `unitRows()` は**並べ替えない**（会社が主たる区分を先に置いていることが多い）
- **値が `null` の区分だけを落とし、`0` は残す**（欠測と「残業0時間」は別物）
- **全体値を先に置き、区分をその後ろに続ける。** 残業の全体値のラベルは**「公表する範囲」**（`対象正社員` / `その他`）をそのまま使う

**有給の全体値だけは原典に対応する語が無い**ので `全体` を当てている。原典の列名は「対象労働者(%)」だが、これは**トヨタ自動車が区分名として登録している文字列と同じ**で、並べると同じ語が別の意味で2回出る。

## 単位は見出しに1回、値には付けない

**行ごとに繰り返さない**（アートボード 6c）。残業は `時間 / 月`、有給は `%` を見出しの隣に置く。

**男女の賃金の差異だけは値の隣に `%` を付ける。** 見出しの側が定義（`女性の平均賃金 ÷ 男性の平均賃金 × 100`）で埋まっており、そこに単位を足すと定義が読みにくくなる。**数字だけを単独で置かない**（spec 2.4）ためにこの定義は省けない。

## バーは10メモリ・上限100

**1メモリ＝10時間・10%**（アートボード 6c）。**塗られていないメモリは描かない**——10個の空セルを敷くと、値の小さい会社ほど灰色の帯が目立ち、棒が短いことより器の長さが先に目に入る。

**値そのものは丸めない。棒の長さだけ上限で止める**（AC-7）。繰越分の消化で有給取得率が100%を超えるのは正しい記録で、`103.0` は `103.0` と出す。

**賃金の差異にはバーを描かない。** 100を基準に上下する値で、「長いほど良い」の向きが他の2つと揃わない（親 Issue #154 がこの軸をレーダーから降ろした理由と同じ）。

## レイアウト

**1指標＝1行。PC は2カラム（左 13rem にラベルと単位、右に区分名・バー・値）、モバイルは上下**（アートボード 6b / 6c）。

- **左カラムで `justify-between` を PC まで効かせない。** 縦積みになると左カラムの高さ（区分5件ぶん）いっぱいに引き離され、**単位が5行下の行末に落ちる**（実測。`sm:justify-start` で止めている）
- **長い区分名は字を一段落として収める。省略しない**（AC-12）。`契約社員(フルタイム)` のような16文字級が実在し、`truncate` で切ると何の区分か読めなくなる。10文字を超えたら `0.65rem` に落とす
- 会社が登録した注釈・説明（716社）は muted の枠に**そのまま**出す。改行を含む自由記述なので `whitespace-pre-line` で行を保つ

## 語彙

**「推定」とも「実測値」とも呼ばない。「自己申告値」**（AC-9・glossary）。「実測値」は有報の平均年間給与を指す語で、同じ画面にある以上ぶつかる。単体テストが節のビュー全体を文字列にして両方の語が無いことを確かめている。

**時点は `lib/data/period.ts` に相乗りさせない。** 決算期（`2026年3月期`）は有報の時点で、女性活躍データベースのデータ集計時点（`2026年3月時点`）とは別物である。会社ごとに違う（三菱商事は `2026年4月時点`、みずほ銀行は `2025年3月時点`）ので、`worklife.json` から会社ごとに引く。

## `worklife.json` は切り出さない（cold の実測）

この Unit は、R0（Issue #165）が入っていた間に実装した。R0 の ADR-0011 は「W1 が `worklife.json` を足すときに**切り出しの形をそこで決める**」と課しており、**決めた答えは「切り出さない」**だった。

**R0 は 2026-08-24 に運営者がリバートした**（#179）。仕掛けの重さに対して効果（`/company/[id]` の cold で 1.7〜2.0ms）が見合わず、代わりに `/company/[id]` の事前生成に進む——実測で 25.5〜28.7ms → 15.6〜15.8ms と桁が違う。**ADR-0011・`population.json`・`logo-ids.json`・ページ単位の lint は無くなった。**

**それでも「切り出さない」という結論は変わらない。** 切り出しが効くのは「複数のページが大きいファイルの一部だけを使う」ときで、これはどちらにも当たらない。

- **読むのは `/company/[id]` の1ページだけ**（`app/page.tsx` からは読まない。Issue #22）
- **そのページは全社ぶんを必要とする。** 使うのは当該1社の行だが、**どの会社が来るかはリクエストが来るまで分からない**
- **注釈・説明（716社・raw 141KB）を別ファイルにしても減らない。** 同じページが同じリクエストで読むので `JSON.parse` の合計は変わらない

### 実測（Node 22・中央値61回・`web/public/data/` の実ファイル）

| ファイル | raw | `JSON.parse` |
| --- | ---: | ---: |
| `companies.json` | 130KB | 0.811ms |
| `curves.json` | 2KB | 0.013ms |
| `stats.json` | 131KB | 0.942ms |
| `history.json` | 160KB | 0.641ms |
| **`worklife.json`** | **491KB** | **1.600ms** |
| `radar.json` | 29KB | 0.161ms |
| `performance.json` | 15KB | 0.043ms |

**`worklife.json` はこの画面がいちばん重く払うファイルになる。** 事前生成が入ればリクエスト時には走らなくなるが、**入るまではこの 1.600ms を毎 isolate の初回リクエストで払う。**

**それでも減らしたくなったときの手は1つだけある。注釈・説明を落とすこと。** 141KB は `worklife.json` の3割で、画面から消せば 0.5ms 前後は減る。**表示を削る判断なので運営者のもの。**

## モックに合わせ直したもの（運営者の指摘）

初版をアートボード 6b・6c と突き合わせて直した3点。**どれも「値は合っているのに読めない」形の崩れ**で、単体テストでも E2E でも落ちない。

- **バーの器が 64px では棒が見えない。** 1メモリが 6px しかなく、残業10.5時間（1メモリぶん）で**棒があること自体が分からなかった**。**96px・高さ8px** にした（アートボード 6c の寸法）
- **賃金の差異の定義が2行に割れていた。** `女性の平均賃金 ÷ 男性の平均賃金 × 100` を既定の折り返しに任せると `100` だけが2行目に落ち、式として読めない。**左カラムを 230px（アートボード 6b の値）に広げ、字を 0.625rem に落として `whitespace-nowrap` で固定**した
- **値が本文より小さかった。** 区分名（12px）と値（14px）の差が付かず、行の中で何が主役か分からない。値を 16px にした

## 踏んだもの

- **`127.0.0.1` に向けた E2E は Next.js の dev origin チェックに 403 で弾かれる。** HTML は 200 で返るがチャンクの一部が 403 になり、**ハイドレーションだけが起きない**。「値は出ているのにクリックが効かない」という形で出るので、テストの書き方を疑ってしまう。`E2E_BASE_URL` には `http://localhost:<port>` を渡す（`playwright.config.ts` の既定もそうなっている）
