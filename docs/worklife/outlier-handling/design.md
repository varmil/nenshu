# design.md — W2 異常値の除去と「区分別」の表記

Issue: [#215](https://github.com/varmil/nenshu/issues/215) ／ 親: [#185](https://github.com/varmil/nenshu/issues/185)（[#207](https://github.com/varmil/nenshu/issues/207) は重複として閉じた）
参照: `docs/worklife/spec.md` 1.4・2.2b・AC-3・AC-13〜AC-15 ／ ADR-0009

女性活躍DBは会社の自己申告で、入力ミスがそのまま入っている。**落とす規則を取り込み側に置き、図の側は表記だけを直した。**

---

## 直したものは2種類ある

| | 症状 | 直す場所 |
| --- | --- | --- |
| **データ** | ソニーグループの有給が 100%（#185 例1）／野村総合研究所の残業が 0.0h（#185 例2） | `pipeline/worklife/positivedb.ts`。**CSV に書かない** |
| **表記** | ラクスの有給がレーダーだけ「掲載なし」（#207 例1） | `web/features/company/lib/radar.ts`。**値の選び方は変えない** |

**混ぜない。** データ側を直せば表記の食い違いも減るように見えるが、両者は別の原因で起きている——前者は登録された値そのものが誤りで、後者は正しい値が1点にまとめられないだけである。

## 落とす規則（取り込み側）

### 0 は落とす

**`dropReasonForRate` が負と 0 を同じ入口で判定する。** 「1か月あたりの平均残業時間」が 0 になるのは対象者が1年間まったく残業していないときだけで、**未記入を 0 で埋めたのか本当に 0 なのかを我々は区別できない。**

自社の中で矛盾している会社が実在する。

- 花王 — 全体 15.4h なのに区分5件がすべて 0.0
- 東洋エンジニアリング — 全体 0.0 なのに総合職 8.0h
- 野村総合研究所 — 全体・総合職・事務職がすべて 0.0

**残業の軸は小さいほど上位**なので、残すとこの会社がレーダーの最上位に出る。

**代償として、パート・嘱託の本物の 0.0 も一緒に消える**（商船三井の嘱託社員、みずほ銀行の無期契約パートタイム等。実測で区分別128セル）。**それでも一律に落とす**——「この区分名なら 0 は本物」という判定は、spec 2.2b が禁じた「区分名を分類する」ことそのものになる。

**取り込み時点で落とす。** 節・レーダー・順位のすべてで同じ扱いになる。表示側で落とすと**「節には 0.0 があるのにレーダーは掲載なし」という、いま直している食い違いを新しく作る**ことになる。

**区分の行そのものは残す**（値だけ空にする）。その会社が自社をどう切っているかは 2.2b のとおり情報で、値が落ちたことと関係が無い。

### 有給の全体値 100% ちょうど

**`isMisenteredFullRate` が「100 ちょうど、かつ区分別の値がすべて 100 未満」だけを見る。** 実測でこの条件を満たすのは4社で、**いずれも自社の登録した区分別の値がその 100 を否定している。**

| 会社 | 全体値 | 区分別 |
| --- | ---: | --- |
| ソニーグループ | 100 | 全体 63.7 |
| 富士電機 | 100 | 正社員 78.1 |
| ＩＭＶ | 100 | 社員 67.0 / 嘱託社員・契約社員 74.0 / パート 73.0 |
| 極東貿易 | 100 | 正社員 60.2 |

列の見出しが `8.(1)年次有給休暇の取得率-対象労働者(%)` で「**対象労働者の割合**」とも読めるため、100 は「対象は全労働者（100%）」の意味で書かれたとみられる。

**100 ちょうど以外は判定しない。** フロンティア・マネジメント（98.8 / 34.5）やテクノ菱和（88.3 / 61.0）のような怪しい組み合わせは他にもあるが、**どちらが正しいかを決める根拠が無い。**

**全体値が区分の [最小,最大] の外にあることを判定に使わない。** 一見すると「全体は区分の加重平均だから範囲内に入るはず」に見えるが、**区分は会社の全労働者を覆っているとは限らない**——滋賀銀行が登録している区分は「パートタイマー、シニアスタッフ」だけで、全体値 13.1h が区分の 0.2h より大きいのは正しい。実測で範囲外は残業50社・有給33社あり、大半がこの形である。

### 落としたものは理由ごとに出す

`DroppedValue` に `reason` を足し、`extract.ts` が理由ごとにまとめて出す。**件数が3桁になったので、平坦に並べると読めない。**

```
落とした異常値 135件:
  0（overtime_unit）: 118件
    株式会社商船三井（4010401082896） overtime_unit:嘱託社員(フルタイム) = 0
    …
  0（overtime_all）: 10件
  全体値が100%ちょうど（paid_leave_all）: 4件
  負の値（overtime_all）: 1件
  負の値（overtime_unit）: 1件
  0（paid_leave_unit）: 1件
```

**それでも会社名は全部出す。** 黙って消さない（spec 1.4）と決めているのに、数だけ出して中身を隠しては同じことになる。

### 読む順を明示する

`normalizeRow` は**オブジェクトリテラルの中で読み取り関数を呼ばない。** 呼ぶと `dropped` が並ぶ順が書いた順と一致せず（実測で `overtime_all` が `overtime_unit` より先に出た）、サマリーの並びがコードから追えなくなる。区分 → 全体の順で先に `const` に取り出してから組む。

## 「区分別」（表示側）

### 値の選び方は変えない

`representativeValue` はそのまま——**全体値があればそれ、無ければ区分がちょうど1つのときだけその値。** 区分が2つ以上ある会社で1つを選ぶのは spec 2.2b が禁じた「代表を選ぶ」ことで、単純平均は人数の重みが無いぶん実際の全体値とずれる（ラクスは正社員 88.0・RAM社員 92.7・契約社員 96.8 で、単純平均は全体より高く出る）。

**足したのは `representative` で、`{ value, byUnit }` を返す。** `byUnit` は「値が無い」のではなく「**区分ごとには公表されているが、1点にまとめられない**」ことを表す。`representativeValue` はその薄いラッパとして残した——`build-data.ts` は順位を決めるだけなので値しか要らない。

### 文言は3文字

`buildRadarAxes` の `valueText` が `掲載なし` / `区分別` / 実数 の3通りになる。**頂点を打たないことも順位が空になることも、掲載なしと同じ**（AC-13）。変えたのは文言だけである。

**3文字に収めた。** リストの値の列は 13px・`min-w-[4.75rem]`（76px）固定で、**右寄せの文字が器を超えると左へはみ出して隣のラベルを押す**（`OverviewSection` の既存の注記）。「区分別で公表」は6文字＝約78pxで入らない。

**何の区分かは節の説明文が引き受ける。**

> 公表の無い指標は頂点を打たず、残りの点で閉じています。有給・残業を雇用管理区分ごとに公表している会社は「区分別」とし、値は下の節に区分のまま出しています。

行の中では説明しきれないので、既に「欠測軸の描き方」を断っている1文に足した。

### 誰が判定するか

**`page.tsx` が `representative` を1回呼び、値と `byUnit` を一緒に `RadarAxisInput` へ入れる。** 値と文言を別々に判定すると、図の頂点と文言が別の規約で決まる——`radar.json` の順位はビルド時に同じ関数で決めてあるので、そこだけ食い違うと直す手がかりが残らない。

### 落とした結果

| | 前 | 後 |
| --- | ---: | ---: |
| `worklife_2026.csv` の行数 | 2,369 | **2,367**（残業 0 しか持たなかった2社が消えた） |
| 残業を持つ会社 | 1,534 | **1,525** |
| 有給を持つ会社 | 1,487 | **1,486** |
| レーダーの母集団（残業） | 1,420 | **1,413** |
| レーダーの母集団（有給） | 1,266 | **1,264** |
| 落とした値 | 1件 | **135件** |

**男女の賃金の差異は1件も動いていない**（2,235社のまま）。落とす規則を当てたのは残業と有給だけである。

**指標を丸ごと失った会社**は残業9社（野村総合研究所・日本製鉄・キヤノン・セイコーエプソン・フューチャー・新日本理化・シャルレ・鳥越製粉・ＮＴＴファイナンス）と有給1社（日東工業）。**読者から見れば数字が消える**が、消えたのは 0.0h という誤りうる数字である。

### 「区分別」に変わった会社

**有給221社・残業114社**が「掲載なし」から「区分別」になった。図の形は1つも変わっていない（頂点を打たないのは同じ）。

### ページの重さ

同一手順（`npm run build` → `next start` に対して raw バイト数）で前後を測った。

| | 前 | 後 | 差 |
| --- | ---: | ---: | ---: |
| `/company/6861`（キーエンス。どの規則にも当たらない） | 141,075 B | 141,291 B | **+216 B** |
| `/company/3923`（ラクス。有給が「区分別」） | 142,416 B | 142,624 B | **+208 B** |
| `/company/6758`（ソニーグループ。有給の全体値が消えた） | 145,952 B | 145,524 B | **−428 B** |

**増えるのは説明文の1文ぶん（+約210 B）だけで、どの会社でも同じ。** 同じ文が RSC ペイロードにも流れるので2回ぶん入る（CLAUDE.md「HTML は `<meta>` の見た目より増分が大きい」と同じ理由）。**値が消えた会社はそれより大きく減る。**

`/` は `worklife.json` も `radar.json` も読まないので1バイトも動かない（Issue #22）。

## テスト

- **`positivedb.test.ts`** — 判定関数（`dropReasonForRate`・`isMisenteredFullRate`）の境界と、`normalizeRow` が区分の行を残すこと。実データ側は「0 以下が1件も残っていない」ことと、ソニーグループ・野村総合研究所の実際の値
- **`radar.test.ts`** — `representative` の `byUnit`、`buildRadarAxes` の文言が3文字に収まること
- **`lib/data/worklife.test.ts`** — **実物の `worklife.json`** に対してソニーグループ・野村総合研究所・みずほ銀行の値を固定する
- **`e2e/company-radar.spec.ts`** — ラクスで「区分別」が出て頂点が4つであること、ソニーグループの画面に 100.0% が出ないこと、野村総合研究所の残業が図でも節でも消えていること

**「欠測と 0 を分ける」を固定していた既存のテストは書き換えた**（消していない）。方針が変わったことがテストの差分に残る。

## 残している食い違い

**落とした10社では「この会社は残業時間をデータベースに登録していません。」が事実と違う。** 登録はしていて、その値を我々が採らなかった。**この Unit では直していない。**

- 文言と字数（29文字）は Issue #192 で運営者が詰めたもので、勝手に置き換えない
- 正しく書き分けるには「登録は無い」と「登録された値を採らなかった」を**データが区別できる必要がある**。CSV に列を足し、`worklife.json` と `WorklifeView` の両方に通すことになる（10社のために3層を動かす）
- 主語を消して「掲載がありません」に寄せる手もあるが、**本当に登録していない会社（残業1,436社・有給1,475社）に対する情報が減る**

読者から見れば「その指標の数字が無い」ことに変わりはないので、**直すかどうかは運営者の判断**として残す。
