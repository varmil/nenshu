# plan.md — W2 異常値の除去と「区分別」の表記

Issue: [#215](https://github.com/varmil/nenshu/issues/215) ／ 親: [#185](https://github.com/varmil/nenshu/issues/185)（[#207](https://github.com/varmil/nenshu/issues/207) は重複として閉じた）
参照: `docs/worklife/spec.md` 1.4・AC-3・AC-13〜AC-15 ／ `docs/worklife/overview.md` の W2

着手前の段取り。出来上がりの構造は `design.md` にある。

## 前提の確認

**ZIP が手元に無いと `worklife_2026.csv` を作り直せない。** `pipeline/worklife/source/` は gitignore されていて、コンテナは毎回まっさらでクローンされる。**最初に ZIP を取り直し、`manifest.json` の sha256 と一致することを確かめる**——一致しなければ、直した規則の効果と厚労省側の更新が混ざって前後を比べられない。

## 手順

1. **ZIP を取り直して sha256 を照合する。** 一致しなければここで止まり、母集団の変動も一緒に報告する段取りに切り替える
2. **落とす規則を決める前に数える。** 0 の残業・100% ちょうどの有給・全体値が区分の範囲外——それぞれ何社で、その会社が自社の中で矛盾しているかまで見る。**「怪しい」で落とさない**ため、反例が0件であることを確かめてから規則にする
3. **方針を運営者に諮る。** 落とすかどうかは読者に見える数字を消す判断なので、実測を添えて選んでもらう
4. **取り込み側を直す**（`positivedb.ts`）。判定を関数として切り出し、`normalizeRow` から呼ぶ。落とした理由を `DroppedValue` に持たせる
5. **CSV を作り直して差分を読む。** 意図した会社だけが変わっているか、行数の増減が説明できるかを見る
6. **`worklife.json`・`radar.json` を作り直し、母集団の変化を控える**
7. **表示側を直す**（`radar.ts` → `page.tsx` → `OverviewSection`）。**代表値の規則は変えず、なぜ1点に決められなかったかだけを足す**
8. **テストを直す。** 既存のテストのうち「欠測と 0 を分ける」は方針が変わったので**書き換える**（消さない）。新しい規則は Unit テストで、画面に出るかは E2E で固定する
9. **検証の順序**は 取り込みのUnitテスト → web の Unit テスト → 型・lint → E2E。**E2E は最後**——データを作り直す工程が全部終わってからでないと、落ちた原因がデータか表示か切り分けられない
10. spec.md 1.4 の表と受け入れ基準を改訂し、design.md を書く

## 確認すること

- 落とした結果、**指標を丸ごと失う会社**が何社出るか（読者から見れば「表示が消えた」になる）
- レーダーの母集団（`population`）が変わるので、**順位を書き写している既存のテスト**がどこにあるか
- 「区分別」の文字列が**リストの値の列（76px 固定）に収まるか**
