## 実施順序

```
D0 ─→ D1 ─────────────────┐
D0 ─→ D7 ─────────────────┤
D2 ─→ D3 ─→ D4 ───────────┼─→ D8 ─→ D10
       └──→ D6 ───────────┘   （D6 は D8 の後から足してよい）
D2 ─→ D5
D2 ─→ D9 ─→ D11（D4 も要る）
```

**D0 と D2 が起点。** どちらにも依存が無く、並べて進められる。

**D0 が無いと、毎日の更新は1回目から落ちる。** いまのテストとビルドは、いまのデータの値を固定している——ビルドは社数を2,961で決め打ちし（`pipeline/scripts/build-data.ts:17`・`pipeline/scripts/build-logos.ts:31`）、`e2e/company-page.spec.ts` はキーエンスの `2,178万円`・`偏差値 149.5`・`2位 /2,961社` を見ている。社数や金額が1つ動けば落ちる。**D0 で書き直した不変条件が、spec 1.11 の止める線 A・B の置き場所にもなる。**

**D3 は D4 より先に入れる。** D4 で数字だけを新しい書類に替えると、D3 が無いままでは要約の節が新しい決算期を名乗り、中身は前の期の原文のまま、という状態になる。給与の決定方針はビルドそのものが落ちる。

**D8 は D6 を待たずに動かし始めてよい。** D4 だけで回すと、数字は新しく、文章は前の期のまま、という状態が続く。これは spec 1.5 の状態そのもので、読者に誤りは出ない。**D6 が入った時点で、文章も追いつき始める。**

## Unit の中で決めること

Inception では決めず、各 Unit の design で決める。

- **機械の工程をどこで回すか**（D8）。トークンを使わないので、Claude Code のルーティンではなく GitHub Actions の cron に載せる手もある。生成AIの工程はルーティンで回す
- **台帳の形と置き場所**（D2）。git の中に置く（spec 1.1）
- **給与の決定方針の節の、期の名乗らせ方**（D3）。常に出すか、数字の期とずれたときだけ出すか
- **止める線の閾値**（D4）。起点は ①±50%・②上位30社。回しながら調整してよい（運営者）
- **1日の上限の社数**（D6）。最初の数回で1社あたりの消費を測ってから決める
- **提出が途切れた会社を sitemap に残すか、ページのどの節を残すか**（D9）→ sitemap に残し、母集団に依存する節・表示基準・年齢別の推定年収・分析と要約を外した（`lapsed-pages/design.md`）

## D0 テストをいまのデータの値から切り離す

**書き直す前に、テストを2つに仕分ける。**

- **規則のテスト** — 計算・整形・選び方の規則。合成データか、実データでも値ではなく関係を見るもの（例: `build-data.test.ts` の「Python と TypeScript の推定式が全社で一致する」）。**そのまま残す**
- **いまのデータのテスト** — 特定の会社の金額・順位・社数・決算期の幅を書き写したもの。**不変条件に書き直す**（例: 「社数は前回から一定以上減っていない」「1位の会社の金額は、ランキングの2位以上である」）

E2E は画面の崩れ（横スクロール・切り詰め・重なり）を見るものが大半で、そこで会社を1つ名指しする必要はある。**名指しは残してよいが、その会社の値は書き写さず、データから引く。** CLAUDE.md の「E2E は文言を書き写さない」（`e2e/metadata.spec.ts`）と同じ考え方になる。

## D2 更新台帳・企業 ID の固定・母集団の出入り

**台帳を作った時点で、画面は1つも変わらない。** いまの全社をそのまま写すので、ID も母集団も今日と同じになる。変わるのは「次に有報が出たときにどう振る舞うか」だけ。

**年の直書きもここで外す。** ファイル名の `_2026` と `DATA_VERSION = "2026-06"`（`pipeline/scripts/build-data.ts`）は、毎日回す前提では意味を持たない（親 Issue「足りないもの」4.）。10年推移の 2017〜2026 は、会社ごとの範囲にする D5 で外す。**C18 の `FIRST_PERIOD_END = "2026-03-31"` は外さない**——開示府令の改正が適用される期末の日付で、年の直書きではない（Issue 起票時に確かめた）。

## D8 定期実行・自動マージ・知らせ

**テストが通ったかどうかを、定期実行のセッションの報告で判定しない。** C6 で「エージェントの報告を数えない。ファイルを数える」と決めた（報告とファイルが食い違う事故が4回あった）のと同じ理由で、D1 の CI の結果を見る。

**基準を変える PR の見分け方**は、変更したファイルで決める（テスト・止める線の閾値を置いたファイル・`pipeline/*/prompts/`）。どのファイルが基準に当たるかは design で一覧にする。
