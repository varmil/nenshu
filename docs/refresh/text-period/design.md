# design.md — D3 文章の節が自分の期を名乗る

Issue: [#873](https://github.com/varmil/nenshu/issues/873)
spec: `docs/refresh/spec.md` 1.5・AC-3、`docs/site-chrome/spec.md` 5.1 ／ 段取り: `plan.md`

文章の記録（要約と分析・給与の決定方針・説明文）が、自分を作った有報の書類と決算期を持つようにした。文章の節は数字の側（`companies.json` の決算期・`filings.json` の書類）を借りず、それを名乗り、その書類を指す。給与の決定方針の書類が数字の書類と違うとビルドが落ちるガードは外した。

**いまのデータには、数字と文章の書類がずれた会社がいない**（D2 の台帳で確かめた）。ずれた会社は、毎日の更新（D4）で有報が出た会社の数字が先に替わったときに現れる。

---

## 文章の記録が持つもの

```ts
// pipeline/scripts/lib/filing.ts・web/lib/data/sources.ts
interface FilingRef {
  docId: string;  // EDINET の書類 ID（S100YAHE の形）
  period: string; // その書類の決算期（YYYY-MM。companies.json の periods と同じ形）
}
```

| 成果物（web） | どこに持つか | 写し元（`pipeline/data/`） |
| --- | --- | --- |
| `analyses.json` | 記録の `filing` | `company_analysis.csv` の `source_doc_id`・`source_period_end` |
| `pay-policies.json` | 記録の `filing` | `pay_policy.json` の `doc_id`・`period_end` |
| `summaries.json` | 別の辞書 `filingById` | `company_summary.csv` の `source_doc_id`・`source_period_end` |

- **各成果物の列から写す。台帳からは引かない。** 台帳（D2）も同じ書類を持っているが、ビルドが両者の一致を検めているので値は同じになる。記録の中身を作った成果物から取るほうが、記録と書類の対応が近い
- **説明文だけ別の辞書にした。** 説明文は島の props に載る（`CompanyPageData.summary`）が、書類を使うのは島の外の「このページの出典」だけ。記録に入れると props が全社ぶん膨らむ
- **形が崩れていたらビルドを落とす**（`filingRef`）。黙って空にすると、その会社の節だけ期もリンクも無いまま配られる

gzip は `summaries.json` 273.7 → 295.9KB（上限 320KB）、`analyses.json` 2,155.0 → 2,184.6KB（上限 2,600KB）、`pay-policies.json` 582.4 → 597.1KB（上限 700KB）。どれも `/company/[id]` のビルド時に1社ぶん読まれるだけで、クライアントには届かない。**`summaries.json` は上限の 92% になった**——書類 ID は8文字の乱数に近く、圧縮が効かない。

## 節ごとの期と書類

| 節 | 名乗る期 | 指す書類 |
| --- | --- | --- |
| 年収に関するQ&A（C16） | 数字の決算期（変えていない） | 数字の書類（変えていない） |
| 有価証券報告書の要約（C10） | **要約の原文の決算期**（`AnalysisView.fiscalPeriod`） | — |
| 現状と今後（C10） | **分析の原文の決算期**（`AnalysisView.fiscalPeriod`。断りの先頭。書いた年月は出さない——2026-10-10 に改めた） | — |
| 給与の決定方針（C19） | **原文の期。節の説明の先頭に常に出す** | **原文の書類**（引用の `cite`・下辺の EDINET の帯） |
| 説明文（C7） | 出さない（C7 の決まりのまま） | — （出典の節で辿れる） |
| このページの出典（C12） | 出さない | **行ごとに、その行の中身を作った書類** |

### 給与の決定方針の期は、常に出す

spec 1.5 が design に任せた論点。**節の説明の1行の先頭に「{期}の有価証券報告書に会社が書いた方針です。」と常に出す**（`PayPolicyView.fiscalPeriod` は期の文字列で、`null` を持たない）。置き方は Q&A・要約の説明と同じ。

- **日次更新では、どの有報の原文かが節ごとに日ごとに動きうる。** 数字は新しい有報、給与の決定方針は前の有報、という会社が毎日できる。節の中で常に期が読めるほうが、そろっているかずれているかを読者に判断させずに済む
- **置き場所は引用の枠の中ではなく節の説明。** 枠の先頭は出どころの節の名前（「人材戦略に関する基本方針等」）で、ここに期を混ぜると、そろっている会社とずれた会社で枠の先頭の形が変わる

**当初は「そろっているときは出さず、ずれたときだけ引用の枠の先頭に出す」としていた**（D3）。そろっていれば直後の Q&A の説明が同じ期を言っており、常に出すと企業詳細の決算期が3か所になって「1画面に1回」（site-chrome spec 5.1）を崩すのに情報が増えない、という理由だった。**2026-09-30 に運営者の判断で改めた**——Q&A・要約の説明に期があるのに給与の決定方針だけ無いのは節ごとの読み方がそろわない、日次更新でどの有報の原文かを明示したい、が理由。site-chrome spec 5.1 は、決算期を節ごとに1回、給与の決定方針の無い会社は最大2回、ある会社は最大3回と改めた。

## いまの全社で変わるもの

数字と文章の書類がそろっているので、期の文字列はどの節も変わらない。変わったのは次の2つだけ（D3 の時点。給与の決定方針の期を常に出すようにした変更は上の節）。

- 「このページの出典」の AIの要約・AIの評価の行の「有価証券報告書」がリンクになった（文字は同じ）
- 給与の決定方針の引用の先頭の行に `data-pay-source`（E2E が引くための印）が付いた

## 揺らしの道具と E2E

- **揺らしの4つ目（`newer_period`）は、文章の節をすべて持つ会社から選ぶ。** 数字だけを新しい書類（翌月の決算期）にし、説明文・要約と分析・給与の決定方針は前の書類のまま残す。D3 の前は、ガードを避けて給与の決定方針を持たない会社を選んでいた
- **ずれた会社の E2E は `e2e/data-period.spec.ts` の2本。** 会社はデータから選ぶ。要約・分析がずれた会社は D4 の1回目から実データにいるので、ふだんの E2E で走る。**給与の決定方針がずれた会社はいまのデータにいない**（節は改正後の有報にしか無い）ので skip になり、`tools/perturb/check.sh --e2e` で走る。D3 の時点では3つともずれた会社を1社選ぶ1本で、D4 の後も給与の決定方針のずれが無いために skip のままだったので分けた
- **「企業詳細の決算期」の数を数えるテストは、文章が数字とそろっている会社で数える**（`textAlignedWithNumbers`）。ずれた会社では要約と給与の決定方針が別の期を名乗るので、数えても合わない。数えるのは給与の決定方針のある会社（3か所）と無い会社（2か所）の両方

## 検証

| 見たこと | 結果 |
| --- | --- |
| いまのデータで作り直した成果物 | 変わったのは `analyses.json`・`pay-policies.json`・`summaries.json` に書類と期が足されたことだけ |
| 合成データのユニット | 要約の期（`buildAnalysisView`）・給与の決定方針の期とリンク（`buildPayPolicyView`）・出典の行（`buildSourceRows`。ずれた会社・説明文と要約の書類が違う会社） |
| ビルドの出力と台帳 | 全社で、文章の記録の書類が台帳の工程ごとの書類と一致する（`build-data.test.ts`） |
| いまのデータの E2E | 企業詳細の決算期は Q&A・要約・給与の決定方針の説明の先頭（給与の決定方針の無い会社は2か所）。ずれた会社のテストは skip |
| 揺らしたデータ（`tools/perturb/check.sh --e2e`） | ずれた会社で、要約・給与の決定方針・出典の行がそれぞれ文章の書類の期とリンクを出す |
