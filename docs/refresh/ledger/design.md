# design.md — D2 更新台帳・企業 ID の固定・母集団の出入り

Issue: [#872](https://github.com/varmil/nenshu/issues/872)
spec: `docs/refresh/spec.md` 1.1・1.3・1.4・AC-7（母集団の側）・AC-8 ／ ADR: [0017](../../adr/0017-stable-company-id.md)・[0018](../../adr/0018-universe-entry-exit.md) ／ 段取り: `plan.md`

会社ごとの状態を持つ更新台帳（`pipeline/data/ledger.csv`）を置き、2026-09-29 時点の全2,961社を写した。企業 ID はビルドのたびに計算し直さず台帳から引き、母集団は台帳の提出日で決める。**台帳を作った時点では、数字も ID も母集団も変わらない**——作り直した `web/public/data/` は、`companies.json` の `meta.version`・`meta.generatedAt` 以外は1バイトも変わっていない。画面で変わるのは `/about`「対象範囲」の説明だけ（下の「`/about` の対象範囲」）。

---

## 構成

```
pipeline/
  data/
    ledger.csv            更新台帳（1社1行・EDINETコード順）
    universe.json         取得の窓・掲載条件で落とした社数（変わらず）。出る条件の基準日もここ
    ranking_unified.csv   数字の工程の成果物（`_2026` を外した。下の「ファイル名」）
  ledger/
    ledger.py             台帳を書く側。ID の振り方・入る条件・読み書き
    seed.py               いまの全社を写した道具（1度だけ回した）
    test_ledger.py
  scripts/
    lib/ledger.ts         台帳を読む側。出る条件で母集団を絞る・工程ごとの書類を突き合わせる
    lib/ledger.test.ts
    build-data.ts         台帳から ID を引き、母集団を絞る
    build-logos.ts        台帳から ID を引く（出る条件では絞らない）
  worklife/extract.ts     台帳から ID を引く
```

**書くのは Python、読むのはビルド（TypeScript）。** 毎日の取得（D4）と文章の工程（D6）が Python なので、ID を振るのも入る条件を見るのも `ledger.py` に置いた。ビルドは ID を振らない。**同じ規則を両側に持たない**——振り方と入る条件は Python だけ、出る条件は TypeScript だけにある。例外は月の足し算（`add_months`／`addMonths`）で、両側のテストが同じ境界（月末・2月29日）を見ている。

`pipeline/scripts/lib/slug.ts`（`makeId`）は消した。振り方は `ledger.assign_id` に移った。

## 台帳の形

| 列 | 中身 |
| --- | --- |
| `edinet_code` | 鍵。年をまたいで変わらない（ADR-0006） |
| `id` | 企業 ID。一度振ったら変えない（ADR-0017） |
| `filed` | 最後の有報の提出日（`YYYY-MM-DD`）。出る条件はここから数える |
| `doc_numbers` | 数字の工程（平均年収・平均年齢・在籍年数・従業員数と、そこから作る派生データ）に反映した書類 |
| `doc_description` | 説明文（C6） |
| `doc_analysis` | 有報の要約と分析（C9。2つは対で作るので1列） |
| `doc_pay_policy` | 給与の決定方針（C18） |

- **CSV・1ファイル・1社1行・EDINETコードの順。** 毎日書き換わるので、`git diff` で「どの会社の何が替わったか」が1行ずつ読める形にした。会社ごとのファイルにしないのは、2,961ファイルに分けても差分の粒度は変わらず、読むのが遅くなるだけのため。JSON にしないのは、ほかの `pipeline/data/` と同じ読み書きの道具（Python の `csv`・`worklife/csv.ts`）で済むため。167KB
- **行は足すだけで、消さない。** 行があることが「一度載った」ことを表す（ADR-0018 の入る条件が要る情報）。24か月を過ぎて母集団から外れた会社も行は残る——ページを残し（D9）、ID もその会社のものとして取っておくため
- **工程の書類の空は「その工程をまだどの書類でも回していない」。** 説明文は1社（Ｚｅｎｋｅｎ。原文が無い）、給与の決定方針は改正前の様式の1,036社が空。**説明文や方針の本文が空でも、工程を回した書類は入る**（説明文が空の9社・方針が空の63社）——その書類ではもう回さなくてよいことを表す
- **読む側は見出しを完全一致で検める。** 列を足すときは `ledger.py` の `COLUMNS` と `ledger.ts` の `LEDGER_COLUMNS` を両方直す。更新できなかった会社と理由（spec 1.1・1.13）は台帳に列を足さず、**D4 が別のファイル（`numbers_pending.csv`）に持った**——反映できなかった書類ごとの情報で、まだ台帳に載っていない新しい会社の書類も入るため（`docs/refresh/numbers/design.md`「待ち行列」）

## 企業 ID

- **台帳にあればその ID。** 上場で証券コードが付いても、上場廃止で消えても変えない（`ledger.admit` は既存の会社の `id` に触らない）
- **台帳に無い会社は `ledger.assign_id` で振る。** 証券コードがあれば証券コード、無ければ EDINETコード（ADR-0006）。**0 だけの証券コード（`0000`）は無いものとして扱う**（`normalize_sec_code`。D4 で足した。EDINET は証券コードがまだ無い会社に `00000` を入れることがある）。**証券コードが既に別の会社の ID なら、後から来た会社を EDINETコードにする**（ADR-0017 決定4）。どちらも使われていたら落とす
- **同じ ID が2社にあったら落とす**——書く側（`ledger.check`）と読む側（`parseLedgerCsv`）の両方
- **ビルドは台帳に無い会社を出さない**（`companyIdOf` が落ちる）。行を足した回で台帳も書くのは、行を足す側の仕事
- **`salary/run.py` の全件の取り直しは台帳を書かない。** 回して新しい会社が行に入ると、ビルドが台帳に無い会社で落ちる。台帳を書く取得の経路は、毎日の差分取得（`refresh/update_numbers.py`・D4・#874）で、`ledger.admit` の上にある。`unified.py --from-csv`（派生列だけ計算し直す）は会社も書類も変えないので、そのまま回せる

写した時点の内訳は証券コード 2,819社・EDINETコード 142社で、全社の ID が写す前の `companies.json` と一致した（ADR-0017 決定2）。

## 母集団の出入り

| | 規則 | 置き場所 |
| --- | --- | --- |
| 入る | 台帳に無い会社は、提出日が直近12か月（基準日から遡って12か月・両端を含む）のときだけ台帳に足す | `ledger.may_enter`・`ledger.admit` |
| 残る | 台帳にある会社は、次の有報が遅れても最後の有報の数字で並ぶ | 行を消さない（`ranking_unified.csv` の行もそのまま） |
| 出る | 基準日が「最後の提出日の24か月後」以降なら母集団の外 | `ledger.ts` の `isLapsed`・`selectUniverse` |

- **基準日は `universe.json` の `filingWindow.to`**（データを取った日）。**ビルドを回した日ではない**——同じ入力から同じ成果物ができるようにする。Cloudflare のビルドは push のたびに回るので、回した日で決めると同じコミットから別の母集団ができうる。毎日の取得（D4）は `filingWindow.to` をその日に進める
- **ちょうど24か月の日に外れる。** 月末は丸める（2024-02-29 に出した会社は 2026-02-28 に外れる）
- **`selectUniverse` は、行と台帳が1社ずつ対応していなければ落とす。** 台帳にあって行に無い会社は「最後の有報の数字で残る」はずの会社が消えている状態で、黙ると企業ページが消える
- **外れた会社は `companies.json` に入らない**（ランキング・順位・偏差値・母集団の統計の外）。ビルドのサマリーに社数を出す。**企業ページは D9（#879）が `lapsed.json` から残す**（`docs/refresh/lapsed-pages/design.md`）。いまの台帳で最初に外れうるのは **2027-08-26**（最も古い提出が 2025-08-26）

## 工程ごとの書類の突き合わせ

`build-data.ts` の `checkLedgerDocs` が、台帳の工程ごとの書類と各成果物の書類を全社で突き合わせる（`ledger.ts` の `checkStageDocs`）。

| 工程 | 成果物の書類 |
| --- | --- |
| 数字 | `ranking_unified.csv` の `doc_id` |
| 説明文 | `company_summary.csv` の `source_doc_id` |
| 要約と分析 | `company_analysis.csv` の `source_doc_id` |
| 給与の決定方針 | `pay_policy.json` の `doc_id` |

- **食い違ったら落とす。** 台帳は成果物を写したもので、食い違うのは片方だけ書いた回があるとき
- **見るのは同じ工程の中だけ。** 工程どうしで書類がずれているのは正しい状態（数字は新しい書類・文章は前の書類。spec 1.5）
- 給与の決定方針の「書類が数字の書類と違えば落とす」ガードは残っている。工程どうしのずれを通すように直すのは D3（#873）

## `/about` の対象範囲

1行目の「（EDINET に◯◯に提出されたもの）」を外し、入る条件と出る条件を別の行にした（ADR-0018「結果」）。

> 新しく載るのは、EDINET に2025年8月25日〜2026年8月25日に有価証券報告書を提出した会社です。一度載った会社は、最後の提出から24か月たつまで、その報告書の数字で載せ続けます（提出の遅れや決算期の変更で、一時的に消えないように）

**猶予中の会社は窓より前に提出している**ので、1行目のままだと全社について言えることではなくなる。いまは猶予中の会社がいないので、どちらの書き方でも事実と合っている。

## `universe.json` との関係

変えていない。**会社ごとのことは台帳、母集団全体のことは `universe.json`** に置く。

- `filingWindow` — 取得の窓。`to` が出る条件の基準日を兼ねる
- `excludedByEmployees` 等 — 掲載条件で落とした社数。落とした会社は台帳にも行にもならないので、ここにしか残らない。**全件の組み直しの時点の記録で、差分更新では動かない**（`/about` に出すのは 2026-09-29 にやめた。ビルドは読まない）

## 写し（`seed.py`）

いまの全社を台帳に写した道具。**台帳が既にあれば何もしない**——台帳ができた後は D4・D6 が行を書き換え、作り直すとその後に振った ID や反映した書類を失う。

- **提出日は EDINET の書類一覧から引いた。** `ranking_unified.csv` には書類 ID と決算期しか無い。取得の窓（2025-08-25〜2026-08-25）の平日262日の一覧を取り直し（並列3で約2分）、**全2,961社の書類が一覧に見つかった**（窓の外から来た書類は無い）。提出日の幅は 2025-08-26〜2026-08-25
- ID は `assign_id` を通したうえで、写す前の ID から変わる会社があれば落とす

## データの版（`meta.version`）

`DATA_VERSION = "2026-06"` の直書きをやめ、**`companies.json` の中身から決める**（`datasetVersion`。`version` と `generatedAt` を除いた `companies.json` の SHA-256 の先頭12桁）。

- 版は、キャッシュに残った古い HTML が新しい `companies.json` を引いたときに、クライアントが引き継ぎをやめる突き合わせに使う（E0・ADR-0013・`web/features/ranking/lib/dataset.ts`）。**毎日行が動くのに版が同じだと、別の会社の順位やロゴを出す組み合わせを見逃す**
- `generatedAt` にしないのは、同じ入力から作り直すたびに版が変わるため
- 今回の版は `b719e9e34984`。写しただけで中身は変わっていないので、次に行が動くまでこの値のまま

## 決算期の幅のガード

`fiscalPeriodRange` の線を **24か月 → 36か月**（`MAX_PERIOD_RANGE_MONTHS`）に引き直した。

- 母集団が「最後の有報から24か月たっていない会社」になった（ADR-0018）ので、最古の決算期は基準日から「24か月＋期末から提出までの間」より前には来ない。提出の期限は期末から3か月で、大きく遅れた会社を見込んでも12か月で足りる
- 以前の24か月は、母集団が「直近12か月に有報を出した会社」だった頃の線で、猶予中の会社が混ざると超えうる（ADR-0018「結果」）
- いまの幅は 2025-03〜2026-05（決算期は14種類）

## 揺らしの道具（`tools/perturb/perturb.py`）

台帳も同じように動かす。

- 足す2社は `ledger.admit` で ID を振る（道具の中で `証券コード or EDINETコード` を組むのをやめた）。提出日は基準日
- 書類を替える1社は、台帳の数字の書類と提出日を替える。文章の工程の書類は前のまま
- 消す1社（実測値の1位）は台帳からも消す。**毎日の更新では台帳の行は消えない**が、ここで見たいのは「1位の会社がデータにいない」ことで、24か月で外れる形にすると D9 の範囲に入る
