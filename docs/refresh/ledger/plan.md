# plan.md — D2 更新台帳・企業 ID の固定・母集団の出入り

Issue: [#872](https://github.com/varmil/nenshu/issues/872)
spec: `docs/refresh/spec.md` 1.1・1.3・1.4・AC-7（母集団の側）・AC-8 ／ ADR: [0017](../../adr/0017-stable-company-id.md)・[0018](../../adr/0018-universe-entry-exit.md) ／ overview: `docs/refresh/overview.md`「D2」

会社ごとの状態を持つ更新台帳を作り、いまの全2,961社を写す。企業 ID をビルドのたびに計算し直すのをやめて台帳から引き、母集団から出る条件を「最後の有報から24か月」にする。**台帳を作った時点では、画面は1つも変わらない。**

---

## 段取り

### 1. 作り直す前の成果物を取っておく

`web/public/data/` を一式写しておく。**いまの入力から `build:data` を回し直すと、`companies.json` の `meta.generatedAt` 以外は1バイトも変わらないこと**を先に確かめる（変わるなら、台帳より前に原因がある）。

### 2. 年の直書きを外す

台帳より先にやる。**ファイル名が変わるだけの差分を、台帳の差分と混ぜない。**

- `pipeline/data/` の `_2026` の付いたファイルを `git mv` で改名し、コード・テスト・`.gitignore`・README の参照を書き換える
- `DATA_VERSION = "2026-06"` を外す。版は `companies.json` の中身から決める（形は design.md）
- docs は「いまの構造」を書いている文書（spec・overview・design・glossary・CLAUDE.md）だけ書き換える。plan.md と ADR はその時点の記録なので触らない

ここで一度 `build:data` を回し、`meta.version` と `meta.generatedAt` 以外が1.と同じであることを見る。

### 3. 最後の有報の提出日を集める

いまのデータには提出日が無い（`ranking_unified` の行にあるのは書類 ID と決算期だけ）。取得の窓（`universe.json` の `filingWindow`）の書類一覧を EDINET から取り直し、**全2,961社の書類 ID が一覧に見つかること**を確かめる。見つからない会社があれば、窓の外から来た書類なので、その理由を調べてから進む。

### 4. 台帳の読み書きと規則を、合成データのテストから作る

台帳を書くのは Python（毎日の取得 D4・文章の工程 D6 が Python なので）、読むのはビルド（TypeScript）。

- **ID の振り方**: 台帳にあればそれ、無ければ証券コード→EDINETコード、ぶつかれば EDINETコード。上場（証券コードが付く）・上場廃止（消える）・ぶつかりを合成データで確かめる
- **入る条件**: 台帳に無い会社は、提出日が直近12か月のときだけ載る
- **出る条件**: 最後の有報の提出から24か月を過ぎた会社は母集団の外。境目の日（ちょうど24か月）と月末（2月29日・31日）を確かめる
- **同じ ID が2社にあったら落とす**

テストは Python と TypeScript のそれぞれに書く。**同じ規則を両側に持たない**（振るのは Python、出る条件で絞るのはビルド）。

### 5. いまの全社を台帳に写す

3.の提出日と、各工程の成果物の書類 ID（数字・説明文・要約と分析・給与の決定方針）から台帳を作る。ID はいまの `companies.json` と同じものを写す。**写した後に確かめること**:

- 全2,961社が1行ずつあり、ID がいまの `companies.json` の ID と全社で一致する
- 工程ごとの書類 ID が、各成果物の書類 ID と全社で一致する

### 6. ビルドが台帳から ID を引くようにする

`build-data.ts`・`build-logos.ts`・`worklife/extract.ts` の3か所。**台帳に無い会社が行にあれば落とす**（ID を振るのは台帳を書く側の仕事で、ビルドは振らない）。台帳の会社が行に無いときも落とす（最後の有報の数字で残るはずの会社が消えている）。

出る条件で絞るのもここ。基準日は `universe.json` の `filingWindow.to`（データを取った日）で、**ビルドを回した日ではない**——同じ入力から同じ成果物ができるようにする。

決算期の幅のガード（24か月）は、猶予中の会社が混ざると超えうるので線を引き直す（ADR-0018「結果」）。

### 7. 揺らしの道具を台帳に追随させる

`tools/perturb/perturb.py` が会社を足す・消す・書類を替えるとき、台帳も同じように動かす。**足す2社は台帳の規則で ID を振る**（いまは道具の中で `証券コード or EDINETコード` を自前で組んでいる）。

### 8. 検証する

順に回す。

1. `build:data` の成果物が、1.の写しと `meta.version`・`meta.generatedAt` 以外で1バイトも変わらない
2. `astro build` の `sitemap.xml` が、2.の前（main）のビルドと1行も変わらない（AC-8）
3. pipeline・web のユニットテストと E2E
4. `tools/perturb/check.sh --e2e`（揺らしたデータで全部通る）

### 9. docs を実態に合わせる

- `docs/product/product.md`「データの前提」の母集団の書き方（入るのは12か月・出るのは24か月）
- `docs/product/glossary.md`「企業ID」に「一度振ったら変えない」、「更新台帳」を実物の場所に
- `design.md` を書き、CLAUDE.md の「現在地」と、ID・母集団・ファイル名に触れている節を直す
