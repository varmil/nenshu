# spec.md — データの定期更新

対象面: user-web（ユーザー画面）。画面が変わるのは、文章の節が名乗る期（1.5）・10年推移の範囲（1.10）・提出が途切れた会社のページ（1.16）だけで、残りはデータを作る側の仕様になる。

親 Issue: [#868](https://github.com/varmil/nenshu/issues/868)

年1回の一括更新をやめ、**毎日、前回以降に有報を出した会社だけを更新する。** 運営者の確認を待つ工程を置かない。用語は `docs/product/glossary.md` に従う。

決まったことの経緯は親 Issue の本文「決まったこと」1〜17 にある。ここにはその結果だけを書く。

---

## 1. 何を作るか（WHAT）

### 1.1 更新の単位は会社。会社ごとの状態を更新台帳に持つ

**会社ごとに「どの書類を、どの工程まで反映したか」を持つ。** これを更新台帳と呼ぶ（glossary）。定期実行は台帳を読んで、次に処理する会社を決める。

- 工程は **数字**（平均年収・平均年齢・在籍年数・従業員数・10年推移・稼ぐ力・ロゴ）と **文章**（説明文・要約・分析・給与の決定方針）に分かれ、**工程ごとに読んだ書類を持つ。** 数字は新しい書類、文章は前の書類、という状態を表せる必要がある（1.5）
- 企業 ID（1.4）と、母集団への出入り（1.3）も台帳に持つ
- 更新できなかった会社と、その理由も台帳に持つ（1.13）
- **台帳はコンテナの外に残る場所に置く。** 定期実行はまっさらなコンテナで始まるので、コンテナの中の状態は次の回に残らない

### 1.2 新しい有報は毎日の書類一覧から見つける

- **毎日、前回以降に提出された書類一覧を読み、掲載の対象になる有報を拾う。** 12か月ぶんの書類を毎回読み直さない
- **新規上場で初めて有報を出した会社も、同じ一覧から見つかる。** 載せる条件（1.3）を満たせば、翌日の定期実行で載る
- 訂正報告書・同じ会社の複数の有報の扱いは、いまの規則（期末が新しいほう、同じなら docID が大きいほう。ADR-0011）のまま

### 1.3 母集団の出入り——入るのは12か月、出るのは24か月（ADR-0018）

- **入る条件は ADR-0011 のまま。** 直近12か月に有報を出した内国法人・組合で、掲載の条件（単体従業員100人以上・平均年齢20〜65歳・平均年間給与100万円超）を満たす会社
- **出る条件は別に置く。** 一度載った会社は、**最後の有報の提出から24か月たつまで**母集団に残る。その間は最後の有報の数字で並ぶ
- 24か月を過ぎた会社は、ランキングと母集団（順位・偏差値・母集団の統計）から外れる。**企業ページは残す**（1.16）
- **窓そのものを24か月に広げない。** 1〜2年前に提出をやめた会社が新しく載ってしまう

**24か月の理由。** 提出の遅れに加え、**決算期を変えた最初の事業年度は1年を超えてよい**（会社計算規則では最長1年6か月）。有報の間隔は12か月を大きく超えうる。ページが誤って消えるほうが SEO の痛手が大きい（運営者の判断）。

### 1.4 企業 ID は一度振ったら変えない（ADR-0017）

- **EDINETコードごとに ID を1度だけ振り、以後は変えない。** 上場で証券コードが付いても、上場廃止で証券コードが消えても、URL は変わらない
- **2026-09-29 時点で公開している全社の ID はそのまま。** 証券コード 2,819社・EDINETコード 142社の URL は1つも変わらない
- 新しく振るときの規則はいまのまま（証券コードがあれば証券コード、無ければ EDINETコード。ADR-0006）
- **ID がぶつかったら、後から来た会社を EDINETコードにする**（証券コードが別の会社に振り直された場合）

### 1.5 数字を先に替え、文章は書き直すまで前の期のまま出す

- **数字は、有報が出たら次の定期実行で新しい書類に替える。** ランキングの順位・偏差値・母集団の統計は、そのたびに全社ぶん計算し直す。年齢別の説明文と「年収に関するQ&A」はコードが数値から組み立てているので、数字と一緒に替わる
- **文章（説明文・要約・分析・給与の決定方針）は、書き直すまで前の期のまま出す。隠さない**
- **文章の節は、それぞれ自分の中身を作った書類の期を名乗る。** 数字の側の期を借りない
  - 要約の節は、要約の原文の決算期を名乗る（いまは数字の側の `fiscalPeriod` を使っている）
  - 分析の節は、いまと同じく書いた年月を名乗る
  - 給与の決定方針の節は、原文の書類へリンクし、その期が読める。期の名乗らせ方（常に出すか、数字の期とずれたときだけ出すか）は design で決める
  - 説明文は、出典の1行に決算期を入れない決まりを変えない（C7）。中身を作った書類は「このページの出典」で辿れる
- 「このページの出典」の各行は、**その行の中身を作った書類**を指す
- **工程ごとの書類がずれていてもビルドは落ちない。** いまの給与の決定方針のガード（書類 ID が採用中の書類と違うとビルドが落ちる）をやめる

### 1.6 文章の書き直しは1社ずつ終わらせる。1社の中では分析を先に書く

- **1社ぶんの文章の工程を全部終えてから、次の会社に移る。** 順番は 分析と要約 → 説明文 → 給与の決定方針
- **分析だけを多くの会社で先に進め、ほかの文章を後から追いかける回し方はしない。** 1ページの中で文章の要素ごとに期がずれる期間を短くするほうを優先する（運営者の判断）
- 1社の途中で定期実行が止まっても分析は残り、残りの工程は次の回の最初に片付ける。**文章の要素どうしのずれは、長くても定期実行1回ぶん**
- 分析と要約は対で作る（C9 の決まり）。片方だけが新しい期になることはない

### 1.7 書き直す順番と1日の上限

- 文章の書き直しを待つ会社は、**実測値（既定の表示基準）の全体順位が高い会社から**処理する。数字は先に替わっているので、新しい期の値での順位になる。注目度の代わりの指標として置く（intent H3）
- **1回に処理する社数に上限を置く。** 上限は最初の数回で1社あたりの消費を測ってから決める。目安は1日16社前後（月約500社）
- 上限が月の流入を上回る月（6月以外）で残りが片付くので、順位の低い会社もいずれ順番が来る

### 1.8 何を毎期書き直すか

| 文章 | 新しい有報が出たとき |
| --- | --- |
| 分析と要約（C9） | 新しい原文から書き直す。年ごとに中身が最も大きく変わる |
| 説明文（C6） | **前の説明文を、新しい原文（事業の内容）に照らして検証だけする。** 通れば文はそのままで、出典を新しい書類に付け替える。落ちたら書き直す |
| 給与の決定方針（C18） | 新しい書類で範囲を答え直す。塊の番号が書類ごとに変わるので据え置けない |

**説明文を検証だけにする理由。** 事業の内容は年ごとの変化が小さく、検証だけなら書き直すより消費が小さい。新しい原文で確かめ直しているので、出典を付け替えても根拠を隠すことにはならない。

**分析は、有報以外のきっかけでは書き直さない**（当面。intent「作らないもの」）。

### 1.9 新しく載る会社

- 数字に加えて、**派生データ（ロゴ・10年推移・稼ぐ力・働きやすさ）も1社単位で足す。** E3〜E6 で全社まとめて行ったことを、会社ごとに行う
- 過去の有報が無い会社の10年推移は、1年ぶんから始まる
- 文章は 1.7 の順番で待ち行列に入る。**書けるまでは、その節を出さない**（前の期の文章が無いため）

### 1.10 10年推移は、会社ごとにその会社の直近10年を出す

- **全社一斉に横軸を回す時期は置かない。** 有報が出た日に、その会社の推移だけが1年ずれる
- 推移の「年」は、いまと同じく有報を提出した暦年
- 推移の範囲の説明（いまの「推移は2017〜2026年の各年」）は、その会社の範囲を名乗る
- 業種の中央値（在籍年数の推移）は、いまと同じく年ごとに「その年に値を持つ会社」で数える

**一斉に回す案を採らない理由。** 1月に回すと、3月期の1,881社が1〜6月の間、右端（新しい年）が空のまま左端だけを失う。7月に回すと、12月期の387社が3〜6月の間、新しい年の値が出ているのに推移に出ない（1.5 に反する）。

### 1.11 異常を見つけても運営者を待たない

途中で運営者の確認や判断を待つ工程を置かない。C6・C9 の初期生成（全社をバッチに分け、途中で一度も止めずに回した）と同じ形にする。

**A. 取得の失敗を疑うとき**（社数が前回から一定以上減った 等）

- その日の数字は公開しない。台帳を進めないので、次の回がそのままやり直しになる
- EDINET は流量制限に HTTP 200 で応え、書類一覧が取れないまま0件として扱われて会社が静かに消えたことがある（`pipeline/salary/edinet.py` の注記）

**B. 読み違いを疑うとき**

- 線は2つ。①平均年収がその会社の前の期から大きく動いた（起点 ±50%）、②前の期の値が無い会社が上位30社に入った（起点 30社）
- 「上位30社に新しく入った」は線にしない。31位が30位に上がっただけで引っかかる
- 引っかかった会社は、**生成AIが原文（従業員の状況）を読み直して確かめる。** 確かめるのは「有報にそう書いてあるか」で、「あり得る値か」ではない。本物の変化（持株会社化 等）はそのまま出す
- 読み直しても決まらなければ、前の期の数字のまま（新しく載る会社は載せない）。**知らせる**（1.13）

**文章の工程は、いまの仕組みのまま。** 機械ゲート → 検証パス → 落ちたら理由を添えて書き直し（2回まで）。それでも通らなければ前の期の文章のまま。

**閾値は回しながら調整してよい**（運営者）。

### 1.12 自動でマージする。ただし通る基準を変える変更は自動で入れない

- **データ更新の PR は、独立に回したテストが通れば、運営者を待たずにマージする。** テストが通ったかどうかを、定期実行のセッション自身の報告で判定しない
- **テストは、いまのデータの値ではなく、規則と不変条件を見る。** 社数・金額・順位が変わっても、規則が守られていれば通る。不変条件は 1.11 の A・B の線を含む
- **やり直しで直らない失敗**（EDINET の形式変更・コードの不具合 等）は、定期実行のエージェントが原因を調べてコードを直し、PR を出す。テストが通れば自動でマージする
- **通る基準を変える PR は自動でマージしない。** 基準は次の3つ。運営者が見るまで開いたままにし、知らせる（1.13）
  - テスト
  - 止める線の閾値（1.11）
  - 生成の規格（`pipeline/*/prompts/`）
- **コードでは直せない失敗**（API キーの失効・外部サービスの設定 等）は、知らせるだけになる
- 直るまでの間、サイトは最後に通ったデータで動き続ける。読者に出るのは「古い数字」で、「誤った数字」ではない

### 1.13 更新できなかったものを知らせる

- **対象は、更新できなかったものすべて。理由が分かっているかどうかによらない**（運営者の判断）
  - 読み直しても数字が決まらず、前の期の数字のままにした会社・載せなかった会社
  - 書き直しても機械ゲート・検証パスを通らず、前の期の文章のままにした会社
  - 取得の失敗が続いている
  - 基準を変えるために自動でマージしなかった PR
  - コードでは直せない失敗
  - 文章の品質のずれ（1.14）
- **知らせ方は GitHub の Issue。1件につき Issue 1つ。** 同じ件で Issue を重ねない。解消したら自動で閉じる。ラベルで他の Issue と分ける
- **知らせるだけで、何も待たない。** 定期実行はそのまま次の会社へ進む
- 次の回が読むのは台帳で、Issue ではない

### 1.14 文章の品質を見張り、書いたモデルを残す

- **月1回、その月に書いた分析をまとめて数える。** 物差しは C9 の版3で使ったもの（主観の語・事実の語の数、外部の資料を使った割合）。比べる相手は、いま載っている分析（全2,961社が版5）の分布
- **1社ずつの機械ゲートには入れない。** 主観の語に下限を課すと分析が単調になる（`pipeline/analysis/gate.py` の注記）
- ずれが大きければ知らせる（1.13）。**自動では直さない**——直すには規格を変えることになり、1.12 の「基準の変更」に当たる
- 運営者はいまの規格（版5）の出来に満足しており、劣化の心配は小さい。**予防策として置く**
- **文章の工程は、版5を書いたときと同じモデル・推論の設定で回す**（運営者の指定・2026-09-29）。いま載っている分析はこの設定で書いたもので、運営者は出来に満足している。**より大きいモデルも試したが、品質はほぼ変わらず消費だけが増えた**ので使わない。設定は定期実行の設定に持つ
- **文章を書いたとき、実際に使ったモデルの設定を記録する。** 品質がずれたとき、原因が規格かモデルかを切り分けるため。いまの `model` 列は `generate.py merge` の `--model` の既定値がそのまま入っており、実際の設定を表していない

### 1.15 女性活躍DB も自動で取り込む

- **全件版を自動で取得し、取り込む。** `docs/worklife/spec.md` の「取得は自動化しない」を改める（運営者の判断）。新しく載る会社の働きやすさが空のまま残ると、「この会社は残業時間をデータベースに登録していません。」という事実と違う文が出る
- 取り込みの規則（法人番号での突合・異常値の除去・236列の検証）は W0・W2 のまま
- **236列の検証に落ちた版は取り込まず、前の版のまま**にして知らせる。列がずれたまま取り込むと、別の指標を残業時間として公開することになる
- 取り込んだ版は manifest に残す（いまと同じ）
- 取得の作法は ADR-0008 の追記（2026-09-29）に従う。1日1回まで

### 1.16 提出が途切れた会社のページ

- **最後の有報から24か月を過ぎた会社の企業ページは消さない。** 最後の有報の決算期と、有報の提出が途切れていることが読める
- 順位・偏差値は出さない（母集団の外なので）
- sitemap に残すか、ページのどの節を残すかは design で決める

### 1.17 実行の間隔とコスト

- **毎日1回回す。** 文章の要素どうしのずれの上限は1日になる（1.6）
- **有料のサービスを増やさない**（`docs/product/product.md`「制約」）。生成は、いまと同じく Claude Code のセッションで回す（ADR-0010 の 2026-08-26 の追記）

### 1.18 対象外

- 年度の切り替え UI（intent H1）
- 分析を有報以外のきっかけで書き直すこと（intent「作らないもの」）
- 賃金カーブ（e-Stat）の更新。年1回しか出ないので、この施策の毎日の工程には入れない
- 母集団の掲載の条件（単体従業員100人以上 等）の変更

## 2. 受け入れ基準

### AC-1 提出の翌日に数字が替わる

```gherkin
Given 載っている会社が新しい有報を提出する
When 翌日の定期実行が終わる
Then その会社の平均年収・平均年齢・在籍年数・従業員数・10年推移・稼ぐ力が新しい書類の値になっている
And 全社の順位・偏差値・母集団の統計が新しい値で計算し直されている
And 定期実行は、その日より前に読んだ書類一覧を読み直していない
```

### AC-2 新規上場の会社が載る

```gherkin
Given 初めて有報を出した会社が、掲載の条件を満たす
When 翌日の定期実行が終わる
Then その会社の企業ページが公開され、ランキングに載っている
And ロゴ・10年推移・稼ぐ力・働きやすさが、取れた範囲で入っている
And 説明文・要約・分析・給与の決定方針の節は、書けるまで出ていない
```

### AC-3 文章の節は自分の期を名乗る

```gherkin
Given 数字は新しい書類、文章は前の書類から作った会社
When 企業詳細ページを開く
Then 要約の節は、要約の原文の決算期を名乗る
And 分析の節は、書いた年月を名乗る
And 給与の決定方針の節は、その原文の書類にリンクし、その期が読める
And 「このページの出典」の各行は、その行の中身を作った書類を指す
And ビルドは落ちない
```

### AC-4 文章は1社ずつそろえて替わる

```gherkin
Given 文章の書き直しの順番が来た会社
When 定期実行がその会社を処理する
Then 分析と要約・説明文・給与の決定方針が同じ回で替わる
And 途中で止まった場合は、残りが次の回の最初に替わる
And ほかの会社の分析を先に書き進めていない
```

### AC-5 書き直す順番と上限

```gherkin
Given 文章の書き直しを待つ会社が複数ある
When 定期実行が回る
Then 実測値の全体順位が高い会社から処理される
And 1回に処理する社数は上限を超えない
```

### AC-6 何を書き直すか

```gherkin
Given 載っている会社が新しい有報を出し、文章の順番が来る
Then 分析と要約は新しい原文から書き直される
And 説明文は新しい原文に照らして検証され、通れば文はそのままで出典が新しい書類になる
And 検証に落ちた説明文は書き直される
And 給与の決定方針は新しい書類で範囲が答え直される
```

### AC-7 母集団の出入り

```gherkin
Given 載っている会社の次の有報が、前の有報から12か月を過ぎても出ていない
And 最後の有報から24か月に満たない
Then その会社はランキングに載ったまま、最後の有報の数字で並ぶ

Given 最後の有報から24か月を過ぎた会社
Then その会社はランキングと母集団から外れる
And 企業ページは残り、最後の有報の決算期と、提出が途切れていることが読める
And 順位・偏差値は出ない

Given 一度も載ったことがなく、直近12か月に有報を出していない会社
Then 新しく載らない
```

### AC-8 URL が変わらない

```gherkin
Given 2026-09-29 時点で公開している全社
Then 企業ページの URL は1つも変わらない

Given 上場前から有報を出していた会社が上場し、証券コードが付く
Then その会社の企業ページの URL は変わらない

Given 上場廃止で証券コードが消える
Then その会社の企業ページの URL は変わらない

Given 新しく載る会社の ID が、既にある ID とぶつかる
Then 新しく載る会社の ID は EDINETコードになる
```

### AC-9 10年推移は会社ごとの直近10年

```gherkin
Given ある会社が新しい年の有報を出した
Then その会社の推移は、新しい年を右端にした直近10年を出す
```
