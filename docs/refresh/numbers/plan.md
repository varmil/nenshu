## 段取り

### 1. 既存の取得の道筋から、1件ぶんの処理を切り出す

いまの取得（`salary/run.py`・`unified.py`・`history.py`・`performance/extract.py`）は、どれも「全社を取り直してファイルを上書きする」作り。キャッシュの無いコンテナで回すと、ZIP の無い会社の行が消える。**1件の書類から「ランキングの1行」「10年推移の1行」「稼ぐ力の最大5行」を作る関数を切り出し**、既存の全件の道筋もそれを通すようにする（規則を2か所に持たない）。

### 2. 書類の選び方の不具合を先に直す

窓の一覧にはファンドの有報（`ordinanceCode` 030）が同じ EDINETコードで混ざる。期末が新しいほうを採る規則でファンドの有報が勝ち、**三菱ＵＦＪ信託銀行が母集団から落ちていた**。会社本体の有報（010）だけを採るようにし、合成データのテストで固定する。直した後、三菱ＵＦＪ信託銀行は最初の回で新しく載る。

### 3. 読んだところまでを持ち、昨日までの一覧だけを読む

- 書類一覧をどの日まで読んだかを持つ（`universe.json` の `filingWindow.to`。D2 で出る条件の基準日にもした値）
- **当日の一覧は読まない。** 一覧は正しい応答を期限なしでキャッシュするので、日中に当日を読むと、その後の提出が永久に欠ける
- 書類一覧が1日でも取れなければ、その回は何も書かずに止める（線 A。次の回がそのままやり直す）

### 4. 1社ずつ反映し、反映できなかったものを待ち行列に残す

- 台帳にある会社は数字の書類を替え、無い会社は入る条件（直近12か月・掲載の条件）を見て足す（`ledger.admit`）
- 書類が取れない・掲載の条件を割った・読み直し待ち、の会社は**待ち行列**（反映できなかった書類と理由）に残す。書類一覧は読み直さないので、ここに残さないと二度と拾えない
- 読み違いを疑う線（①前の期から ±50%・②前の期の値が無い会社が上位30社）に掛かった会社は反映せず、原文（従業員の状況）を読み直し用に書き出す

### 5. 読み直し（生成AI）を工程に入れる

定期実行のセッションが、書き出した原文を読んで「有報にそう書いてあるか」を判定し、判定をファイルに書く。反映の工程はその判定を読んで、通ったものだけを反映する。決まらなければ前の期の数字のまま（新しい会社は載せない）で、待ち行列に理由を残す。**判定の規格はプロンプトに書き、ここも「基準の変更」の対象にする**（D8）。

### 6. 派生データと成果物を作り直す

- 10年推移は、その会社のその年の行を足すか差し替える。値はランキングの行と同じ値（`build-data.test.ts` が両者の一致を見ている）
- 稼ぐ力は、同じ ZIP から最大5期ぶんを足す（`(会社, 年)` ごとに当期の書類を優先する規則はいまのまま）
- 新しく載る会社のロゴを取る（`build:logos --only`）。働きやすさは D7 まで取らない（女性活躍DB の ZIP が要る）
- 全社の順位の列を計算し直して `ranking_unified.csv` を書き、`build:data`・`build:brand` を回す

### 7. 合成データで確かめ、実データで1回回す

- 合成データのユニットテスト: 書類の選び方・読んだ日の扱い・線 A・線 B・待ち行列・新しい会社・10年推移と稼ぐ力の足し方
- 実データで1回回す（2026-08-26 から昨日までの一覧を読む）。所要時間と EDINET へのリクエスト数を測って design に書く
- `tools/perturb/check.sh --e2e`
