# design.md — D4 数字の差分更新

Issue: [#874](https://github.com/varmil/nenshu/issues/874)
spec: `docs/refresh/spec.md` 1.2・1.5・1.9・1.11・AC-1・AC-2・AC-10・AC-11 ／ ADR: [0017](../../adr/0017-stable-company-id.md)・[0018](../../adr/0018-universe-entry-exit.md) ／ 段取り: `plan.md`

前回読んだ日の翌日から昨日までの書類一覧だけを読み、有報を出した会社の数字（平均年収・平均年齢・在籍年数・従業員数・10年推移・稼ぐ力）を新しい書類の値に替える。台帳に無い会社は入る条件を見て足す。反映できなかった書類は待ち行列に残し、次の回で取り直すか、運営者への知らせ（D8）に回す。

**1回目は 2026-08-26〜2026-09-28 を読んだ。** 115社の数字を替え、17社が新しく載った（2,961社 → 2,978社）。うち1社は下の「書類の選び方」の不具合で落ちていた三菱ＵＦＪ信託銀行。

## 構成

```
pipeline/
  refresh/
    update_numbers.py        collect（ネットワークを使う・data に書かない）と apply（書く・ネットワークを使わない）
    test_update_numbers.py   合成データだけで見る
    prompts/reread.md        読み直し（線 B）の判定の規格
    work/                    gitignore。collect の成果物
      collected.json           書類ごとの判定と、反映する行
      reread/<EDINETコード>.txt  読み直しの材料（読み取った値・前の期の値・従業員の状況の原文）
      verdicts.json            読み直しの判定（生成AIが書く）
  data/
    numbers_pending.csv      待ち行列（新しい）
    universe.json            filingWindow.to が「読んだところまで」
    ledger.csv               提出日と数字の書類を替える・新しい会社の行を足す
    ranking_unified.csv      行を差し替え・足し、順位の列を全社ぶん計算し直す
    salary_history.csv       (会社, 提出した年) の行を足すか差し替える
    performance_history.csv  1書類ぶん（最大5期）を合流させる
  salary/
    edinet.py                is_company_annual_report（会社本体の有報だけを採る）
    unified.py               ineligible_reason（掲載の条件。全件の組み直しと共有）
  ledger/ledger.py           normalize_sec_code（0 だけの証券コードは無いものとして扱う）
```

1回の流れは次のとおり。定期実行（D8）はこれをそのまま回す。

```
python3 update_numbers.py collect          書類一覧を読み、書類を取り、1件ずつ判定する
  └ 読み直しが要る会社があれば、work/reread/ を読んで work/verdicts.json を書く（生成AI）
python3 update_numbers.py apply            判定を pipeline/data/ に反映する
npm run build:logos -- --only <新しい会社>   新しく載った会社のロゴ
npm run build:data -- --out ../web/public/data
npm run build:brand                         OG 画像の数字（社数）
```

**2段に分けたのは、間に生成AIの読み直しが入るため。** collect は `work/` にしか書かないので、途中で止まっても `pipeline/data/` は前の回のまま残る。apply はネットワークを使わないので、同じ `collected.json` と `verdicts.json` から何度回しても同じ結果になる。

## 読んだところまで

- **`universe.json` の `filingWindow.to` が「その日まで書類一覧を読んだ」を表す。** 出る条件の基準日（D2・ADR-0018）と同じ値。apply が `through` に進め、`from` はそこから12か月前にする。**collect は進めない**——collect の後で止まっても、次の回が同じ日から読み直す
- **読むのは昨日（日本時間）まで。** `edinet.list_documents` は正しい応答を期限なしでキャッシュするので、日中に当日の一覧を読むと、その後に提出された書類が二度と見えない
- **読むのは平日だけ**（全件の取得 `edinet.annual_reports` と同じ）
- **読んだ日より前の書類を拾い直す道は `--doc <書類ID>:<提出日>`。** 一覧の読み方の不具合で漏れていた会社を、一覧を丸ごと読み直さずに足すためのもの。三菱ＵＦＪ信託銀行（S100YIH8・2026-06-24 提出）はこれで拾った

## 書類の選び方

- **会社本体の有報だけを採る**（`edinet.is_company_annual_report`: 書類種別 120・府令 010）。全件の取得（`annual_reports`）と取り直し（`fetch_history.targets`）も同じ関数を通す
  - 窓の一覧には**ファンドの有報（府令 030）が、運用する信託銀行と同じ EDINETコードで**混ざる。期末が新しいほうを採る規則（`doc_rank`）でファンドの有報が勝ち、従業員の状況を持たないので会社ごと落ちていた。**三菱ＵＦＪ信託銀行（E03626）が2026-08-25 の全件の取得から抜けていたのはこれ**（ファンドの有報が窓の中に50件）。三井住友信託銀行・りそな銀行もファンドの有報を持つが、期末が自社より前だったので無事だった
  - それまで載っていた2,961社の書類は全部 010 で、この変更で替わる会社は無い
- 提出者種別は内国法人・組合だけ（`run.FILER_KIND`）。1社に複数あれば `doc_rank`（期末が新しいほう、同じなら書類 ID が大きいほう）
- **台帳にある会社は、同じ書類か期末が前の書類なら処理しない**（`should_process`）。訂正報告書は書類種別が別なので、ここには来ない

## 1件の処理

collect は書類ごとに次を通す。**どれも全件の組み直し（`unified.build`）と同じ関数**で、差分更新のための別の規則は持たない。

| 段 | 関数 | 中身 |
| --- | --- | --- |
| 取得 | `edinet.fetch_csv`・`parse_csv_zip` | ZIP を取って読む。流量制限の 200 を弾く（先頭が `PK`） |
| 1行にする | `edinet.to_record` | 平均年間給与・平均年齢・在籍年数・従業員数 |
| 読みの割れ | `unified.resolve_ambiguous_salary` | 基準は10年推移の中央値（`salary_reference`） |
| 桁 | `run.fix_salary_typos` | あり得る帯へ10の冪で戻す |
| 掲載の条件 | `unified.ineligible_reason` | 満たさなければ理由の文を返す |
| 稼ぐ力 | `performance.parse` | 同じ ZIP から最大5期の経常利益 |
| 線 B | `reread_reason` | 下の「読み直し」 |

**掲載の条件は `unified.ineligible_reason` の1か所。** D4 の前は `unified.build` の内包表記に直接書かれていた。理由の文（`単体の従業員が100人未満（40人）` 等）は待ち行列の `detail` にそのまま入る。

## 反映

apply は判定が `apply`（または読み直しで `confirmed`）の書類だけを反映する。

- **台帳**: `ledger.admit`。載っている会社は提出日と `doc_numbers` を替える（ID は変えない）。載っていない会社は、直近12か月の提出なら ID を振って足す。**文章の工程の書類（`doc_description` 等）には触らない**——文章は書き直すまで前の期のまま（spec 1.5・D3）
- **ランキングの行**: 同じ EDINETコードの行を差し替え、無ければ足す。そのあと `unified.rebuild_derived` で**順位の列を全社ぶん計算し直す**（AC-1）
- **10年推移**: `(会社, 提出した年)` の行を足すか差し替える。**値はランキングの行と同じ値**（`build-data.test.ts` が全社で見ている）。同じ年に書類が2件あれば書類 ID が大きいほう
- **稼ぐ力**: 1書類の最大5期を `performance/extract.py` の `_put` で合流させる（連結を優先し、同じ基準なら遡りの少ないほう）
- **ロゴ**: apply が新しく載った会社の ID を並べて出すので、それを `build:logos -- --only` に渡す。**載っている会社のロゴは取り直さない**（`docs/logo/spec.md` 1.6）
- **働きやすさ**: 取らない。女性活躍DB の ZIP を自動で取れるようになるのは D7。それまで新しい会社の節は「掲載なし」になる

**新しい会社の ID の振り方は台帳の規則のまま**（証券コードがあれば証券コード、無ければ EDINETコード）。**ただし 0 だけの証券コード（`0000`）は無いものとして扱う**（`ledger.normalize_sec_code`）。EDINET は証券コードがまだ無い会社に `00000` を入れることがあり、1回目の試しでクラサスケミカル（E42126）が `/company/0000` になった。次に同じ扱いの会社が来ると ID がぶつかる。

## 線 A（取得の失敗を疑う）

- **書類一覧が1日でも取れなければ、collect は何も書かずに止まる。** `work/` も作らず、`filingWindow.to` も進まないので、次の回が同じ日から読み直す（AC-10）
- **書類の ZIP が取れなければ、その会社だけ待ち行列に `fetch_failed` で残す。** 書類一覧は読み直さないので、ここに残さないと二度と拾えない。次の回の collect が待ち行列から取り直す
- **社数が前回から5%を超えて減ったら、ビルドが落ちる**（D0 の `checkCountDrop`）。差分更新は行を消さないので本来は起きないが、ビルドの側でも止める

## 線 B（読み違いを疑う）

- **線は2つ**（`REREAD_CHANGE = 0.5`・`REREAD_TOP = 30`。spec 1.11 の起点のまま）
  - ① 前の期の値がある会社で、平均年収が ±50% を超えて動いた
  - ② 前の期の値が無い会社（新しく載る会社）が、実測値で30位以内に入る。**「30位以内に新しく入った」は線にしない**（31位が30位に上がっただけで掛かる）
- 掛かった会社は反映せず、`work/reread/<EDINETコード>.txt` に材料を書き出す。先頭3行に読み取った値・前の期の値・理由、その後ろが従業員の状況の原文
- **判定は定期実行のセッションが `prompts/reread.md` に従って書く**（`work/verdicts.json`）。確かめるのは「有報にそう書いてあるか」だけで、「あり得る値か」は見ない。**値は直さない**——違っていれば `unresolved` にして、違っていた箇所を `note` に書く
- **判定は書類 ID が一致したときだけ使う。** 次の書類が出たときに古い判定が効かないように
- `confirmed` なら反映する。`unresolved` なら前の期の数字のまま（新しい会社は載せない）で、待ち行列に `unresolved` と `note` を残す。**判定が無ければ `reread` のまま待ち行列に残り、次の回で読み直す**
- **判定の規格（`prompts/reread.md`）と2つの閾値は、D8 の「通る基準」に入る**（spec 1.12）

1回目は線 B に掛かった会社が無かった。115社の平均年収の動きは −13%〜+20% に収まり、新しく載った17社の最上位は三菱ＵＦＪ信託銀行の978万円（実測値で30位より下）。

## 待ち行列

`pipeline/data/numbers_pending.csv`。1社1行・EDINETコード順・LF（台帳と同じ）。**反映できなかった書類だけを持つ**——反映できた会社の行は消す。

| 列 | 中身 |
| --- | --- |
| `edinet_code` | 鍵 |
| `doc_id` | 反映できなかった書類 |
| `sec_code`・`name`・`period_end`・`filed` | 書類一覧の値。取り直しと知らせに使う |
| `reason` | 下の表 |
| `detail` | 理由の中身（割った条件・動いた幅・読み直しの `note`）。知らせにそのまま載る |
| `since` | その書類が最初に待ち行列に入った日。同じ書類が居続ける限り変えない（何日待っているかが読める） |

| `reason` | 起きたこと | 次の回 |
| --- | --- | --- |
| `fetch_failed` | ZIP が取れない | 取り直す |
| `reread` | 線 B に掛かり、判定がまだ無い | 取り直して読み直す |
| `unresolved` | 読み直しても決まらない | 取り直さない。新しい書類が来たら入れ替わる |
| `not_eligible` | 載っている会社が掲載の条件を割った・新しい会社の提出が直近12か月の外 | 取り直さない。知らせる。**読み取りの規則を直したら `--doc` で拾い直す**（下の「知らせから直したもの」） |

- **取り直すのは `RETRY`（`fetch_failed`・`reread`）だけ。** 同じ書類を読み直しても答えが変わらないものは取り直さない
- **同じ会社の新しい書類が一覧に来たら、そちらを採る**（待ち行列の古い書類は捨てる）
- **載っていない会社が掲載の条件を満たさないのは、待ち行列に入れない。** 全件の取得で落としていたのと同じで、知らせることが無い。入れると、条件を満たさない新しい会社の数だけ毎日ふくらむ
- **載っている会社が条件を割ったら、前の期の数字のまま残す。** 読み違い（桁・従業員数の取り違え）でも会社が消えないように、機械の判断だけでは外さない。出る条件（最後に反映した提出から24か月）は進まないので、直らなければいずれ母集団から外れる

1回目で待ち行列に残ったのは2社、2回目（2026-09-30 の定期実行）で1社増えた。

| 会社 | `detail` | いま |
| --- | --- | --- |
| フルヤ金属（E02485） | 平均年間給与の桁を直せない（7567272000000→除外） | 直した |
| ニヤクコーポレーション（E04189） | 平均年間給与が読めない | 直した |
| サイバーステップＨＤ（E05601） | 単体の従業員が100人未満（40人） | 条件どおり。前の期の数字のまま残る |

### 知らせから直したもの（2026-09-30）

どちらも2026年の有報で初めて出た形で、全件の組み直しには現れていなかった。

- **フルヤ金属: タグの値が百万倍だった**（`7567272000000`。表には 7,567,272円とある）。`fix_salary_typos` の割る冪を百万まで広げた。1回目の時点では「広げると本物の値を戻し違える幅も広がる」として広げなかったが、1万倍で割っても帯（200万〜3,000万円）の上に出る値＝3,000億円を超える平均年間給与は実在しない。**広げて増えるのは戻せる書類だけ**で、どの冪で割るかの迷い（帯に隣り合う2つの冪が入る）は広げる前からある（小さいほうを採る）
- **ニヤクコーポレーション: 本文の表に「平均年間給与の対前事業年度増減率」の列が増えた。** タグの無い会社で、表から読んでいる。見出しに単位が付く表の読み方（`textblock._labels`）はこの列を知っていたが、単位が値の側に付く表（`51歳7ヶ月`）の読み方が知らず、`5,461,8826.72` の `6.72` を給与として読みに行って表ごと落としていた。列の定義を1つにして両方が使う
- **規則を直しただけでは、待ち行列の書類は読み直されない**（`not_eligible` は取り直さない）。直した後に `collect --through <読んだ日> --doc S100Z403:2026-09-28 --doc S100Z4R8:2026-09-29` → `apply` → `build:data` で拾い直した。`--through` を読んだ日（`filingWindow.to`）にすると、一覧を1日も読まずに `--doc` の書類だけを処理する
- 固定入力のテストは `pipeline/salary/test_readings.py`

## 1回目の実測

- **2026-08-26〜2026-09-28 の平日24日ぶんの書類一覧と、212件の ZIP を取って428秒。** キャッシュの無いコンテナで、EDINET へのリクエストは一覧24件＋書類212件＋`--doc` の一覧1件
- 会社本体の有報は212社。うち132社を反映（載っている115社＋新しい17社）、80社は掲載の条件を満たさない新しい会社で待ち行列にも入れていない
- 新しく載った17社のうち12社にロゴが付いた（全体 2,548 / 2,978社 = 85.6%）。証券コードのある会社が15社、EDINETコードが2社（三菱ＵＦＪ信託銀行・クラサスケミカル）
- 作り直した `web/public/data/` で、数字の書類より前の書類のままの文章は 説明文114社・要約と分析115社（D3 の `textBehindNumbers`）。給与の決定方針は0社——替わった115社の前の書類は改正前の様式で、方針の節を持っていなかった
- **最初の回だけ、ランキング CSV の同額の会社の順位の列が並べ替わった。** 同額の会社の順位は入力の並びで決まり、全件の組み直しのときの並びと `rebuild_derived` が返す並びが違ったため。`build:data` は順位の列を読まないので、`web/public/data/` には出ない（`check:data` で確かめた）

## 既知の制約

- **`universe.json` の「単体従業員100人未満で省いた社数」（`excludedByEmployees`・1,047社）は差分更新で動かない。** 省いた会社の一覧を持っておらず、差分から数え直せない。2026-08-25 の全件の取得の時点の数のまま残る。`fetched`・`eligible` も同じ。**`/about` に出していた数は外した**（2026-09-29・運営者の判断。動かない数を出し続けるより外す）
- **載っている会社のロゴは取り直さない。** 会社がロゴを替えても追随しない
- **条件を割ったまま24か月たった会社は、「提出が途切れた会社」のページになる**（D9）。提出はしているので、ページの断り（「新しい有報が出ていない」）が事実と違う。最初に起きうるのはサイバーステップＨＤの 2027-08-29（最後に反映した提出が 2025-08-29）。それまでに、残し方か断りの文を決める
- ~~**働きやすさは D7 まで新しい会社に入らない**~~ → D7（#877）で入るようになった。**定期実行では、この工程の後に `npm run update:worklife` を回す**（女性活躍DB の取り込みは、その日に足した会社まで突合する。`docs/refresh/worklife-fetch/design.md`）
