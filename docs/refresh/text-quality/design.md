# design.md — D10 文章の品質の見張り

Issue: [#880](https://github.com/varmil/nenshu/issues/880) ／ plan: `plan.md` ／ spec: `docs/refresh/spec.md` 1.14・AC-15・AC-16

月1回、その月に書いた分析（C9 の要約と分析のうち分析）を物差しで数え、いま載っている版5の分布と比べる。ずれが大きければ知らせ（Issue）が立つ。**規格は自動では変えない。** 集計には書いたモデルごとの内訳を並べる。

---

## 出来上がり

```
定期実行（SKILL.md の 6.・月初だけ）
  └ pipeline/analysis/quality.py report        先月に書いた分析を数える
       → pipeline/data/analysis_quality/<YYYY-MM>.json（コミットして PR に入る）
GitHub Actions（refresh-alerts.yml）
  └ alerts.py が、いちばん新しい月の集計にずれがあれば Issue を立てる（鍵 quality:analysis）
```

| もの | 置き場所 | 通る基準のファイル |
| --- | --- | --- |
| 物差し（語の並び・数え方・線の当て方） | `pipeline/analysis/quality.py` | ○ |
| 版5の分布（固定） | `pipeline/analysis/quality_baseline.json` | ○ |
| 線（閾値） | `pipeline/refresh/thresholds.json` の `quality` | ○ |
| 月の集計 | `pipeline/data/analysis_quality/<YYYY-MM>.json` | × |

**物差しと版5の分布は通る基準のファイルにした**（`criteria.txt`）。定期実行が物差しを書き換えれば知らせを消せるので、変える PR は自動でマージしない。

**1社ずつの機械ゲートには入れない。** 主観の語に下限を課すと分析が単調になる（`gate.py` の「逃げの語」の注記・spec 1.14）。見るのは月の平均だけ。

## 物差し

C9 は版3の頃、分析が要約に戻っていたのを「主観の語・事実の語・外部の資料を使った割合」で見つけた（`docs/company/analysis-generation/design.md`「分析が要約に戻っていた」）。ただし**語の並びはコードに残っていなかった**（機械ゲートに入ったのは「逃げの語」だけ）。D10 で語の並びを起こした。

| 物差し | 数え方 | 判定に使うか |
| --- | --- | --- |
| 主観の語 | 評価（強み・危うさ・追い風）・見立て（とみる・と読める・ほかならない）・読者への判断（べきだ・おきたい）の語を、見出しと本文で数える（`SUBJECTIVE`） | ○ |
| 事実の語 | 数字（全角も）と業績の言い回し（当期・前期・増収・減益・営業利益・億円 など）（`FACT`） | ○ |
| 外部の資料 | `sources` が空でない会社の割合 | ○ |
| 読者への語 | 求職者に向けた語（入るなら・入って・求職者 など） | 参考 |
| 逃げの語 | `gate.escape_phrases`（としている・と説明している など） | 参考 |
| 字数 | 見出し＋本文 | 参考 |

数えるのは、要約と分析が通って公開されている行（`analysis_verdict` が ok）。月は `generated_at` の日本時間の月。**物差しの版（`YARDSTICK`）を持つ。** 語の並びを変えたら版を上げて `baseline` を数え直す——版5の分布と版が食い違うと `report` が止まる（違う物差しで数えた値どうしを比べない）。

### 起こした物差しで、C9 の劣化を見分けられるか

git の履歴に、要約に戻っていた頃の**版2の分析が676社ぶん残っている**（2026-09-06 のコミット `4fb2880`）。版5（C9 が書き終えた全社）と並べた。

| 版2 それ以降 | 576 | 0.39 | 8.34 | 2% | 0.14 | 主観の語・事実の語・外部 |
| 版5 09-08〜09-09 | 500 | 1.27 | 5.25 | 24% | 0.33 | — |
| 版5 09-09〜09-10 | 500 | 1.24 | 6.66 | 18% | 0.29 | — |
| 版5 09-10〜09-16 | 500 | 1.52 | 5.94 | 12% | 0.35 | — |
| 版5 09-16〜09-17 | 500 | 1.39 | 6.30 | 13% | 0.24 | — |
| 版5 09-17〜09-18 | 500 | 1.56 | 5.75 | 12% | 0.27 | — |
| 版5 09-18〜09-23 | 460 | 1.19 | 4.97 | 10% | 0.18 | — |
| **版5 全社（固定した分布）** | **2,960** | **1.37** | **5.82** | **15%** | **0.28** | |

- **C9 の記録と同じ向きに開いた。** 版2 の後半は主観の語が版5の0.28倍、事実の語が1.43倍、外部は 15% → 2%（C9 の記録は「主観の語 109 → 44・事実の語 119 → 284・外部 26% → ほぼ0%」）
- 版5 の中のぶれ（書いた時期で500社ずつ）は、主観の語 −13〜+14%、事実の語 −15〜+14%、外部 −5ポイントまで
- **読者への語は判定に使わない。** 版2 と版5 の開きが小さく（0.14 と 0.28）、語の並びが版5の書き方（「入社して手にするのは」）を拾いきれていない
- 版5 の外部の割合（15%）は、C9 の181回目の記録（6社中6社）より低い。**固定する分布は「いま載っている分析」なので、この値のまま比べる**

## 線（`thresholds.json` の `quality`）

| 物差し | 線 | 向き |
| --- | --- | --- |
| 主観の語・事実の語 | 版5の平均から ±30%（`maxRelativeShift`） | 両向き |
| 外部の資料 | 版5の割合から10ポイントを超えて減る（`maxExternalDrop`） | 減るほうだけ |
| 判定する月 | その月に書いた分析が50社以上（`minCompanies`） | |

- **±30% は、版5 の中のぶれ（±15%）の2倍で、版2 の劣化（−72%・+43%）の内側。**
- **外部は減るほうだけ見る。** 増えるのは規格どおり（`gen_task.md` は採用ページと直近のリリースを見に行かせる。D6 の計測では2社とも外部を使った）。C9 で起きた壊れ方は「外部情報が死んだ」ほう
- **50社未満の月は判定しない**（集計は書く）。版5 から無作為に抜いて線を当てると、何も変わっていないのに線を越える割合が 30社で 10%、40社で 9%、50社で 3%、80社で 0.7% だった。定期実行の上限（1日16社）なら、ふつうの月は数百社になる
- 閾値は回しながら直してよい（spec 1.11 と同じ）。直す PR は基準の変更なので自動ではマージされない

## 月の集計と知らせ

- **月初の定期実行が先月の集計を作る**（`SKILL.md` の 6.）。先月のファイルがあれば飛ばす。ファイルは日次の PR に入ってマージされる
- 集計は、その月の平均・版5の値・判定したか・ずれた物差し・**書いたモデルごとの内訳**（`byModel`。D6 の `merge --model` が残した値。AC-16）。モデルを乗り換えた月は内訳が2行になり、前後が読める
- **知らせはいちばん新しい月の集計だけを見る**（`alerts.py` の `quality_case`）。鍵は `quality:analysis` で月を含めない——ずれが続けば同じ Issue の本文が新しい月に替わり、次の月がずれていなければ閉じる
- **規格は自動で直さない**（spec 1.14）。Issue を見て、規格の側かモデルの側かを運営者が決める
