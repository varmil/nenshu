# intent.md — データの定期更新

親 Issue: [#868](https://github.com/varmil/nenshu/issues/868)

## 狙い

**有報を出した会社から順に、毎日少しずつ更新する。運営者の手を借りずに回り続ける状態にする。**

いまのデータは「年1回、全社を一括で取り直す」前提で作ってある（`docs/product/product.md`「データの前提」）。この前提には問題が2つある。

**1. 生成AIの工程のトークン消費が1時期に偏る。** 数字を取り直す工程は機械で済み、軽い（有報CSV 4,132件の取得は並列3で36分・ADR-0011）。重いのは、セッションのエージェントが1社ずつ書く／判定する次の3工程で、全社ぶんを回した実績は次のとおり。

| 工程 | 中身 | 全社ぶんの実績 |
| --- | --- | --- |
| C6 説明文（#160） | 事業の内容 → 1〜3文 | 12回・535万字（＋C17 の回し直し） |
| C9 要約と分析（#241） | 有報4節＋Web → 要約・一言・分析 | 189回・2,236万字（分析は Web 検索込み） |
| C18 給与の決定方針（#851） | 節の中の範囲を番号で答える | 対象1,925社 |

年1回に全社ぶんを回すと、この量が1時期に集まる。

**2. 年1回の一括は、運営者の目と判断を挟んで成り立っていた。** ADR-0011 の「上位30社は目視で確かめてから公開する」、C6 の目視レビュー（AC-7）、C9 の規格の改定（版3〜5）はどれも運営者の指摘から来ている。**運営者は 2026年10月1日以降ほぼ手が空かない**（`docs/product/product.md`「制約」）。

**有報は会社ごとに、決算期末から3か月以内に出る。** 出た会社を毎日拾えば1回に回す量は小さくなり、数字は提出の翌日に新しくなる。

**ただし山は消えない。** 提出月は決算期で決まり、3月期の1,881社（63.5%）は6月に集中する（下の「先に測ったこと」）。毎日拾っても6月に来る量は変わらないので、**生成AIの工程には1日あたりの上限を置き、溢れた会社は翌日以降に回す。** 山を消すのではなく、後ろへ均す。

## North Star KPI

ranking 施策と同じ **自然検索からの月間セッション数**（`docs/ranking/intent.md`）。

この施策はページを増やさない。KPI への寄与は**鮮度と、ページが消えないこと**から来る。

- 数字が提出の翌日に新しくなる。年1回の一括では、最大で1年古い数字が出ていた
- 一度公開した企業ページの URL が変わらず（ADR-0017）、提出が数日遅れた会社のページも消えない（ADR-0018）

**運用の指標**（KPI ではなく、この施策が壊れていないかを見る数）:

- 1日に生成AIの工程を回した社数（上限を超えていない）
- 数字の期と文章の期がずれている会社の数と、ずれている日数
- 更新できなかった件数（知らせの Issue の数）
- 運営者の手作業の回数（0 を目指す）

## 仮説

**H1.** 読者の関心は主に最新の有報の数字にある。過去の年度を UI で切り替えられなくても困らない。

*検証*: 回り始めてから決める。見るとすれば、企業詳細の推移の節（表・図）がどこまで読まれているか。

**H2.** 企業詳細の文章の中で、年ごとに中身が最も大きく変わり、読者の注目も最も高いのは分析（「◯◯の現状と今後」）である。

*検証*: Clarity のスクロール深度で、分析の節まで読まれている割合を、要約・給与の決定方針の節と比べる。

**H3.** 年収ランキングの上位の会社ほど、企業ページの閲覧が多い。文章の書き直しの順番（spec 1.7）はこの前提に乗っている。

*検証*: Clarity の企業ページの閲覧上位と、実測値の全体順位を突き合わせる。

**H4.** 1日の上限を置いても、6月の山は秋までに片付く。

*検証*: 最初の6月（2027年）に、待ち行列の長さを日ごとに記録する。粗い見積りでは、月500社までなら9月ごろ、月300社までなら翌年1月ごろに片付く。

## 先に測ったこと

**掲載2,961社の決算期**（`pipeline/data/ranking_unified.csv` の `period_end`）。有報は決算期末から3か月以内に出るので、提出月はこれで決まる。

| 決算期 | 社数 | 提出はおおむね |
| --- | ---: | --- |
| 3月期 | **1,881（63.5%）** | **6月** |
| 12月期 | 387 | 3月 |
| 2月期 | 162 | 5月 |
| 6〜8月期 | 198 | 9〜11月 |
| 9月期 | 120 | 12月 |
| 4〜5月期 | 87 | 7〜8月 |
| 10〜11月期 | 86 | 1〜2月 |
| 1月期 | 40 | 4月 |

**6月以外の月の流入は多くて400社弱**（3月の12月期387社）。1日の上限を月500社ぶん（1日16社前後）に置けば、6月以外は溢れない。

**差分で回す仕組みは半分ある。**

- C6 の `plan` と C9 の `pending` は、原文の SHA-1 が変わった会社だけを選ぶ（`pipeline/summary/generate.py`・`pipeline/analysis/generate.py`）
- EDINET の書類一覧（日ごと）と ZIP（書類ごと）は、キャッシュにあれば取りに行かない（`pipeline/salary/edinet.py`）。10年推移の取得も ZIP の無いものだけを取る（`pipeline/salary/fetch_history.py`）
- 1社1件に寄せる規則（期末が新しいほう、同じなら docID が大きいほう）は窓の取り方によらない（`edinet.doc_rank`）
- ロゴは `npm run build:logos -- --only` で会社単位に取り直せる

**足りないものは親 Issue の本文に並べた**（台帳が無い・取得側に差分の入口が無い・工程ごとに読んだ書類がずれた状態を表せない・年の直書き・テストがいまのデータの値を固定している・CI が無い 等）。spec と overview はそれを前提に書いている。

## 作らないもの

- **年度の切り替え UI**（2026年版／2027年版を選ぶ）。H1 による
- **会社ごとにまとめて差し替える更新**（全工程が済むまで前の期のまま置く）。トークンの要らない数字まで、文章の順番待ちに付き合わせることになる
- **分析を有報以外のきっかけで書き直す仕組み**（当面）。どの会社も12か月以内に次の有報が出るので、分析はそのたびに新しくなる。提出の少ない1〜5月の余った枠で古い順に書き直す手はあり、1社あたりの消費を測ってから決める
- **途中で運営者の確認を待つ工程**。異常はやり直しと読み直しで自分で直し、直せなかったものは知らせるだけにする（spec 1.11〜1.13）

## 既知の限界

- **6月の山の間は、数字は新しい期・文章は前の期の会社が数か月出る。** 文章の節がそれぞれ自分の期を名乗ることで、読み違いを防ぐ（spec 1.5）
- **読み直しても決まらない数字は前の期のまま残る。** 知らせはするが、直すのは運営者になる
- **通る基準（テスト・止める線の閾値・生成の規格）を変える修正は、運営者が見るまで入らない。** その間もサイトは最後に通ったデータで動く
- **上場廃止・合併した会社が、最後の有報から最大24か月ランキングに残る**（ADR-0018）。ページが誤って消えるほうを重く見た
- **初期の全2,961社ぶんの分析を、どのモデルで書いたかの記録が無い。** `company_analysis.csv` の `model` 列は `generate.py merge` の `--model` の既定値のままで、全行が同じ値になっている。今後の分から記録する（spec 1.14）
