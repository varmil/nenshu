数字が新しい書類に替わった会社の文章（分析と要約・説明文・給与の決定方針）を、定期実行の中で1社ずつ新しい書類に合わせる。順番は実測値の全体順位の高い会社からで、1回に処理する社数に上限を置く。書き直しても通らなければ前の期の文章のまま残し、知らせる。書いたモデルを文章ごとに残す。

## 段取り

### 1. 下調べ

- 3つの工程（`analysis/generate.py`・`summary/generate.py`・`paypolicy/pick.py`）が、何を読んで何を書き、会社を名指しできるかを調べる
- 台帳の文章の列（`doc_description`・`doc_analysis`・`doc_pay_policy`）と、ビルドがそれを成果物と突き合わせる検査（`checkLedgerDocs`）を確かめる。**文章の工程は、いまは台帳を書かない**ので、成果物だけ書き換えるとビルドが落ちる
- いまの待ち行列の規模を数える（数字が新しく、文章が前の書類のままの会社）

### 2. 待ち行列の決め方を決める

- 台帳から、数字の書類と文章の工程の書類が食い違う会社を拾う。給与の決定方針は、数字の書類の決算期末が節の適用（2026年3月31日以後）に掛かる会社だけ
- 並びは **途中で止まった会社（分析は新しい書類・ほかの工程が前の書類）を先に**、残りを実測値の全体順位の高い順に
- **同じ書類で一度落ちた工程は、次の回で選び直さない。** 毎日同じ会社で上限を使い切らないため。落ちたものは文章の待ち行列（理由つき）に残し、次の有報が出たら選び直す
- 1回の上限は定期実行の手順から渡す。値は 8. で測ってから決める

### 3. 原文を1社ぶんだけ取る

- 数字の書類の ZIP（CSV 形式）から「事業の内容」と分析の4節を、XBRL 本体から給与の決定方針の節を取る。定期実行のコンテナにはキャッシュが無いので、選んだ会社のぶんだけ EDINET に取りに行く
- **分析の切った原文（gzip 17MB）は毎日書き直さない。** 1社ぶん替えるだけで gzip 全体が別物になり、git の履歴が毎回17MB ずつ増える。選んだ会社の切った原文はその回の作業場所にだけ置き、コミットするのは節ごとの字数と SHA-1（マニフェストの1行）だけにする。gzip の中の古い書類の行は、書類 ID がマニフェストと食い違うので使わない
- 「事業の内容」は1社1行の CSV なので、その会社の行を差し替えてコミットする

### 4. 各工程に「会社を名指す」入口を足す

- **分析と要約**: 名指しした会社だけをバッチにする。原文は 3. の作業場所の行を gzip より先に見る
- **説明文**: 前の説明文を、新しい原文に照らして検証だけするバッチを作る（生成を飛ばし、前の文を生成物として置く）。通れば文はそのままで出典を新しい書類に付け替え、落ちたら理由を添えて書き直しに回す（いまの `retry` の2回まで）。前の説明文の無い会社（新しく載った会社・前に落ちた会社）はふつうに書く
- **給与の決定方針**: 名指しした書類を取り、範囲を答えさせ、参照だけの会社は参照先で答え直させる（いまの2回の流れ）
- **書き直しても通らなければ、前の書類の文章を残す。** いまの説明文と給与の決定方針の取り込みは、落ちると空で上書きする（初回の生成なら「まだ無い」だが、書き直しでは「あったものが消える」）。分析と要約は既に前の版を残す
- 給与の決定方針は書類 ID で記録しているので、新しい書類で取り込んだら同じ会社の前の書類の記録を外す（2つ残るとビルドが古いほうを読む）

### 5. 台帳と待ち行列に書く

- 1社ぶんの工程が済んだら、台帳の工程ごとの書類を成果物に合わせる（通った工程は新しい書類、落ちた工程は前の書類のまま）
- 落ちた工程は文章の待ち行列に理由を残し、知らせ（`alerts.py`）が1件ずつ Issue にする。次の有報で通ったら閉じる

### 6. 書いたモデルを残す

- 3つの工程の取り込みに、実際に使ったモデルと推論の設定を渡す。給与の決定方針の記録にも持たせる（いまは持っていない）
- 定期実行の手順に、渡す値の取り方を書く

### 7. 定期実行の手順に足す

- 数字 → 女性活躍DB → ビルド → **文章（1社ずつ全工程、上限まで）** → ビルド → テスト → PR の順にする。分析の材料（稼ぐ力・業種の中央値）はビルドの成果物から読むので、文章の前に1回ビルドする
- 生成と検証はいまの規格のまま、手順のファイル（`prompts/`）をエージェントに読ませて回す。規格は1字も変えない
- 変更が無い回は PR を立てずに終わる（D8 の確認で抜けていた）

### 8. 実データで回して、上限を決める

- 待ち行列の先頭から数社を実際に回し、1社あたりの時間と消費を測る。分析と要約が最も重い
- 測った値から1回の上限を決め、手順に書く。目安は1日16社前後（spec 1.7）
- 書いた文章が規格どおり通っているか（機械ゲート・検証パスの通過、落ちた会社の前の版が残っているか）を確かめる
- 合成データのユニットテスト: 待ち行列の選び方と並び・名指しのバッチ・検証だけの経路・落ちたときに前の版を残すこと・給与の決定方針の前の記録を外すこと・台帳の書き方
