毎日1回の定期実行を置き、データ更新の PR を作る。CI（D1）が通れば運営者を待たずにマージし、通る基準を変える PR は止めて知らせる。更新できなかったものは1件につき Issue 1つで知らせ、解消したら閉じる。

---

## 段取り

### 1. 下調べ

- 定期実行（Claude Code の Routine）が新しいセッションを立てたとき、リポジトリ・GitHub のツール・API キー（`EDINET_API_KEY` など。いまはこの環境の環境変数）が揃うかを確かめる
- GitHub Actions の `GITHUB_TOKEN` でマージしたとき、Cloudflare のビルドが動くかを確かめる（`GITHUB_TOKEN` の push は他のワークフローを起こさないが、GitHub App への通知は出る）

### 2. どこで何を回すかを決める

- **機械の工程（EDINET・女性活躍DB の取得、ビルド）も定期実行のセッションの中で回す。** API キーはこの環境の環境変数にあり、GitHub Actions に載せるにはリポジトリの secrets を運営者が設定する手間が要る。数字の読み直し（線 B）は生成AIの工程で、どのみちセッションが要る
- **判定（マージするか・知らせるか）は GitHub Actions で回す。** spec 1.12 の「セッション自身の報告で判定しない」をそのまま形にする。マージは CI の結果で、知らせはリポジトリのファイルから数える

### 3. 閾値を1か所に寄せる

止める線の閾値（線 B の ±50%・上位30社、社数の減り5%、女性活躍DB の突合の減り5%、決算期の幅36か月）は、いま4つのファイルに散っている。**基準を変える PR をファイルで見分ける**（overview）ために、1つのファイルに寄せ、Python と TypeScript の両方がそこから読む。値は変えない。

### 4. 自動マージ

- 定期実行が作る PR にラベルを付ける
- CI の完了を受けて動くワークフローを置く。ラベルが付いていて、CI の3つのジョブがすべて通り、基準のファイルに触れていなければマージする。触れていればラベルを付けて止める
- 基準のファイルの一覧は1つのファイルに置き、その一覧自身とワークフローも基準に含める
- 判定の規則はスクリプトに書き、テストで固定する

### 5. 知らせ

- 「更新できなかったもの」をリポジトリのファイルから数え上げるスクリプトを書く（数字の待ち行列・女性活躍DB の落とした版・定期実行が止まっている・基準を変えて止めた PR・CI が落ちた PR）
- main への push と毎日の schedule で、そのスクリプトの結果と開いている Issue を突き合わせ、足りない Issue を立て、解消した Issue を閉じるワークフローを置く。**同じ件を重ねないための鍵は本文の1行目**に書く
- 知らせは定期実行を待たせない（Issue への応答を待つ工程を作らない）

### 6. 定期実行の手順を書く

- 手順は skill にしてリポジトリに置く（`.claude/skills/`）。定期実行の設定には「その skill に従う」だけを書き、手順の変更は PR で入れる
- 数字（D4）→ 女性活躍DB（D7）→ ビルド → テスト → PR（ラベル付き）の順。やり直しで直らない失敗は原因を調べてコードを直し、同じ PR に入れる
- 前の回の PR が開いたままのときの扱いを決める
- 生成AIの工程（数字の読み直し）で使ったモデルを判定のファイルに残す

### 7. 定期実行を置いて通しで回す

- Routine を置く（毎日・日本時間の朝・新しいセッション）。モデルと推論の設定は spec 1.14 のとおり
- 1回手で発火させ、PR が立ち、CI が通り、自動でマージされ、知らせが同期されるところまで確かめる
