# ADR-0003 年齢補正はブラウザで計算し、賃金カーブを配信する

状態: Accepted
日付: 2026-08-16

## 文脈

年齢スイッチは25〜60歳の8段（`docs/ranking/spec.md` 1.4）。各社について8通りの推定年収が要る。

補正の式は次のとおり。

```
推定年収(目標年齢) = 平均年間給与 × カーブ[業種](目標年齢) ÷ カーブ[業種](平均年齢)
```

配布済みの `ranking_unified_2026.csv` には35歳時点の値（`salary35`）と、その倍率（`factor`）しか入っていない。

事前検証として、賃金カーブ（`annual_curves.json`）から `factor` を再計算したところ、CSV との差は最大 0.00005（CSV側の丸め）に収まり、`salary35` は1,867社すべてで一致した。カーブから完全に再現できる。

## 決定

**推定年収をブラウザ側で計算する。ビルド時に事前展開しない。**

配信するのは、会社ごとの生の値（平均年間給与・平均年齢・業種）と、賃金カーブのテーブルそのもの。

## 理由

賃金カーブは17業種 × 年齢階級10点で、**170個の数値**にすぎない。これを配ったほうが、8列を事前計算して配るより小さい。

| 方式 | 生JSON | gzip後 |
| --- | ---: | ---: |
| 8つの年齢を事前計算して同梱 | 約400KB | 約90KB |
| **生値＋カーブを配りブラウザで計算** | 約250KB | 約60KB |

計算量は1,867行の乗除算1回ずつで、目標年齢を変えるたびに全件を再計算しても体感できる遅延にならない。spec の非機能要件（100ms以内）を満たす。

年齢の刻みを後から変えられる。8段を12段にする、あるいは Bolt 2 で企業詳細ページに1歳刻みを出す、といった変更がデータの作り直しなしで通る。

計算式とカーブがクライアントに露出するが、隠す理由がない。方法の全公開そのものが差別化であり（`docs/ranking/intent.md` H3）、`/about` で式もカーブの出典も明示する方針と一致する。

## 結果

**ビルド時の変換スクリプト** `pipeline/scripts/build-data.ts` が、CSV から次の2ファイルを生成する。手作業で JSON を編集しない。

`public/data/companies.json` — 列指向の配列で持ち、キー名の繰り返しを避ける。

```
{
  "meta": { "version": "2026-06", "count": 1867, "generatedAt": "..." },
  "industries": ["電気機器", "卸売業", ...],        // tse33 の一覧。行はここへの添字を持つ
  "curveKeys": ["製造業", "卸売業・小売業", ...],    // 産業大分類。同上
  "rows": [
    // [id, name, tse33Idx, curveIdx, avgAge, avgTenure, avgSalary, empNonCons, badge]
    ["6861", "株式会社キーエンス", 0, 0, 35.0, 11.3, 21783259, 3306, 0],
    ...
  ]
}
```

`public/data/curves.json` — 代表年齢と産業別カーブ。

```
{
  "agePoints": [22, 27, 32, 37, 42, 47, 52, 57, 62, 67],
  "curves": { "情報通信業": [3443.9, 4512.2, ...], ... }
}
```

**産業大分類（`curveIdx`）はユーザーに見せない。** 内部の計算キーであり、glossary の定義に従う。

**補間の実装は Python 側と一致させる。** 区分線形補間、範囲外は端の値で頭打ち。`salary35` の再計算値が CSV の `salary35` と全件一致することを、テストで固定する。ここがずれると全数値が静かに狂う。

**桁補正済みのデータをそのまま使う。** 有報の提出ミス（フジ日本・ヨロズ・クリアルが1,000倍、加藤製作所が10倍）はパイプライン側で処理済み。フロント側で再度の補正を入れない。

**id は証券コードを優先し、欠損時は社名スラッグにする。** 非上場107社は証券コードを持たない。`doc_id` は一意だが URL として読めないため、Bolt 2 の企業詳細ページのパスにも使えるキーをここで確定させる。社名の重複が2件あるので、スラッグ生成では末尾に連番を付けて一意性を担保する。

## 却下案

**ビルド時に8列を事前計算して同梱** — ペイロードが1.5倍になり、年齢の刻みを変えるたびにデータを作り直すことになる。得られるのは初回描画時の乗算1回ぶんで、割に合わない。

**API を立てて計算する** — サーバーを持たない方針（ADR-0001）と両立しない。

**1歳刻みのスライダーにする** — カーブの代表年齢が5年間隔で、その間は線形補間しているだけなので、1歳刻みは持っていない精度を見せることになる。8段に留める。
