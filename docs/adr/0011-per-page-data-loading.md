# ADR-0011: ページが読むデータファイルは、その画面が使うぶんだけに割る

- 状態: 採用
- 日付: 2026-08-24
- 関連: [ADR-0004](0004-ssr-opennext-cloudflare.md)（フルSSR）, Issue [#118](https://github.com/varmil/nenshu/issues/118)（親）, [#165](https://github.com/varmil/nenshu/issues/165)（R0）, `docs/runtime/spec.md`

## 背景

ADR-0004 で Cloudflare Workers 上のフルSSRにした。無料枠の CPU は**1リクエストあたり 10ms** で、`/company/[id]` が散発的にこれを超えて `exceededCpu` で落ちている。落ちたリクエストは HTML を返さない。

**踏んでいるのはクローラである。** 報告されたログの発生元は `ClaudeBot`（`verifiedBotCategory: "AI Crawler"`）で、1,867社ぶんの異なるURLを世界中のコロから叩くため、エッジキャッシュはほぼ全部ミスし isolate は毎回冷えている。

`import` したデータファイルは、その画面が1バイトしか使わなくても丸ごと `JSON.parse` される。しかもモジュールの初期化は isolate ごとに1度だけ走り、**その回のリクエストに課金される。** 実測（Node 22・中央値61回）で `/` は 2.98ms、`/company/[id]` は 3.58ms を `JSON.parse` だけで使っていた。内訳は次のとおりで、`/` が `stats.json` から使っていたのは 337B、`logos.json` から使っていたのは「ロゴがあるか」だけだった。

| ファイル | raw | `JSON.parse` |
| --- | ---: | ---: |
| `companies.json` | 130KB | 0.820ms |
| `stats.json` | 131KB | 0.908ms |
| `logos.json` | 202KB | 1.236ms |
| `history.json` | 160KB | 0.607ms |
| `worklife.json` | 491KB | 1.568ms |

## 決定

**1. ページは、その画面が使うデータファイルだけを import する。** 「ついでに入っているから」で読まない。どのページが何を読んでよいかは `docs/runtime/spec.md` 2.1 の表が正。

**2. 複数のページが大きいファイルの一部だけを使うなら、その部分を別ファイルに切り出す。元のファイルは消さない。** 切り出しは**生成側**（`pipeline/scripts/`）でやる。web 側で切り出しても、丸ごと読んだあとで捨てることになり CPU は1msも減らない。

**3. 切り出したファイルと元のファイルの整合は、生成する1か所と、公開ファイルを突き合わせるテストで担保する。** 手で同期しない。

**4. 規則は lint で強制する。** ページ単位の `no-restricted-imports` で、使ってはいけないデータファイルの import を落とす。型もテストも通ってしまう間違いで、レビューでは見つからない。

**5. 無料枠から出ない。** 有料プランに上げれば CPU 30秒で消える問題だが、`docs/product/product.md` の「ランニングコストをゼロに保つ」を優先する。

## 理由

**予算は増えないが、読む量は選べる。** フレームワーク（Next.js・React・OpenNext）の CPU には手が届かない。手が届くのは「読むデータ」と「自分のコードの計算」の2つだけで、前者は削っても画面が1文字も変わらない。

**切り出しはデータを増やさない。** `population.json`（337B）も `logo-ids.json`（11.3KB）も元のファイルの部分集合で、公開しているデータの中身は同じ。重複するバイト数は 12KB で、これは静的アセットとして配るだけなので Worker の CPU には乗らない。

**「使わないのに読んでいるぶん」は、放っておくと増える一方である。** データが増えるたびに全ページの cold が重くなる構造だと、社数を増やす（Issue #22）ことも指標を足す（worklife・company の説明文）こともできない。

## 影響

**この先データファイルを足す Unit は、必ずこの問いを通る。**

- **W1（#150）が `worklife.json`（491KB・1.568ms）を `/company/[id]` に足す。** 使うのは当該1社ぶんだけなので、丸ごと読むと `/company/[id]` の cold は 2.45ms から 4.02ms に戻る。**切り出しの形はそこで決める**（この ADR は「決めること」を課すだけで、切り方までは決めない）
- **C5〜C7（#159〜#161）の会社の説明文も新しいファイルを1つ増やす。** 同上

**`/about` は例外的に `logos.json` を丸ごと読んでよい。** 帰属表示が `w`/`h`/`from`/`lic` を実際に使う唯一の画面で、しかも静的に前生成されるためリクエスト時に評価されない。

**これで足りなければ次は静的生成の検討になる。** `/company/[id]` の 1,867枚を前生成すれば cold の描画そのものが消えるが、`searchParams`（共有リンクの `?age=N`）をSSRに反映する構成を崩す。**その判断は ADR-0004 の追記としてやる。**

## 却下した案

**有料プランへ上げる。** 制約に反する（決定5）。

**エッジキャッシュの `s-maxage` を延ばす。** クローラは1,867の異なるURLを1回ずつ叩くので、キャッシュの寿命を伸ばしても最初の1回は必ずミスする。**この問題はキャッシュでは消えない。**

**掲載データを減らす。** 社数・年数・項目を削れば読む量は減るが、それはサイトの価値そのものを削っている。

**`stats.json` の入れ子を平らな配列にする。** `JSON.parse` が 1.221ms → 0.854ms になる（実測）。**採らなかった**——0.37ms のために「`rankAll[行][基準]` が `rankAll[行×9+基準]` になる」表現へ移す取引が見合わない。**行がずれると別の会社の順位を出す**性質のデータで、いま入れ子であることがその事故を防いでいる。効かせたくなったときの手段としては残る。
