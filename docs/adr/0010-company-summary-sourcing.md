# ADR-0010 会社説明文の出所と生成方針

状態: Accepted

日付: 2026-08-23

親 Issue: [#158](https://github.com/varmil/nenshu/issues/158)。Unit は C5（[#159](https://github.com/varmil/nenshu/issues/159)）・C6（[#160](https://github.com/varmil/nenshu/issues/160)）・C7（[#161](https://github.com/varmil/nenshu/issues/161)）。施策は `docs/company/`。

**これは `docs/company/intent.md` の「作らないもの」を覆す決定である。** 方針転換の判断は運営者が 2026-08-23 に行い、ここに記録する。

## 文脈

企業詳細ページ `/company/[id]` の h1 直下——モック `改善案.dc.html` のアートボード 4b（PC）/ 2b（モバイル）が社名の直下に3行の紹介文を描いている位置——が空いている。C3（#89）でここを作らなかったのは `docs/company/intent.md` の次の一文による。

> **会社ごとの解説文。** 1,867社ぶんを人手で書けず、生成して埋めれば根拠の無い断定が混ざる。

同じ判断が `docs/company/spec.md` 1.10・1.16・1.17、`docs/company/summary-text/design.md`、`docs/company/company-mock-alignment/plan.md`、`CLAUDE.md` に繰り返されている。

覆すなら決めるべきことが3つある。**どこから取るか**、**どこまで書いてよいか**、**生成物であることをどう示すか**。

**この決定は不可逆である。** 1,867ページに文を載せた後で「根拠の無い断定が混ざっていた」となれば、根拠を全部公開していることを差別化に置いた立て方（`docs/ranking/spec.md` 2.）そのものが崩れる。数字は間違っても直せるが、「あのサイトは知ったふうな会社紹介を出していた」は残る。年収と違って**文は照らし合わせる先が読者の手元に無い**ぶん、誤りが見つかるのも遅い。

判断の材料として 2026-08-23 に実測した値（#158。無作為90社＝上場70・非上場20）。

| | 値 |
| --- | --- |
| 「事業の内容」の取得率 | **90 / 90（100%）** |
| 文字数 中央値 | 1,006字 |
| 平均 / 最大 | 1,415字 / 7,560字 |
| p90 | 3,028字 |
| 200字未満 | 2社（2%。1,867社換算で約41社） |
| 全社ぶんの要約費用 | Haiku 4.5 約$2.8 / Sonnet 5 約$5.6（Message Batches API） |

非上場でも取れる（みずほ銀行 612字、三菱UFJ銀行 358字、国際協力銀行 3,753字、横浜高速鉄道 1,342字）。「事業の内容」は開示府令の様式で記載が義務づけられた項目なので、構造的に全社が持っている。

## 決定

### 1. 出所は有価証券報告書の「事業の内容」だけにする

XBRL 要素 `jpcrp_cor:DescriptionOfBusinessTextBlock` の値を原文として持ち、**そこからの要約に限って載せる**。他の出所（外部サイトの企業紹介、Wikipedia、gBizINFO の `business_summary`、モデルの一般知識）を本文の材料にしない。

原文は既存の取得経路にそのまま入っている。`pipeline/salary/edinet.py` は EDINET API v2 の CSV 形式（`type=5`）を叩き、`jpcrp_cor:InformationAboutEmployeesTextBlock` を1つだけ拾っている。**`TEXT_BLOCK` を単数から複数にするだけ**で、パーサも取得経路も新規に書くところは無い（C5）。

**原文を増やして埋めない。** 沿革（`CompanyHistoryTextBlock`）と経営方針（`BusinessPolicyBusinessEnvironmentIssuesToAddressEtcTextBlock`）も見たが、前者は商号変更の年表、後者は中期経営計画の話で、「何をやっている会社か」には答えない。書けない会社は書けないままにする（決定2）。

### 2. 原文から導けない事実は書かない

生成に使う原文は**その会社の「事業の内容」1つだけ**とし、そこから導けないことは1文も書かない。**世間で知られている話をモデルの一般知識から補わない。評価語を書かない。**

線が要るのは、補った文が実際に出たからである。試作したキーエンスの紹介文はこうだった。

> センサ・測定器・画像処理機器などFA向け機器の開発と直販を手がける。**自社工場を持たないファブレス体制**と、代理店を介さない**コンサルティング営業で高い利益率を保つ**。

後半は原文から導けない。それどころか原文には「キーエンスエンジニアリング㈱は当社商品の製造を行っております」とあり、**「自社工場を持たない」とは逆のことが書いてある**（子会社が製造しているという意味では両立するが、原文だけを読んで書ける文ではない）。「高い利益率を保つ」は評価であって記述ではない。

この線を機械と LLM の二段で担保する（C6）。

- **機械ゲート** — 文字数・文数・禁止語・社名の混入に加え、**原文に現れない固有名詞を含む文を落とす**。キーエンスの「ファブレス」はここで落ちる
- **検証パス** — 生成とは別のプロンプトで「各文が渡した原文だけから支持されるか」を判定する。支持されない会社は `rejected` にして**説明文を空にする**

**書けない会社が出ることを受け入れる。** ENEOSホールディングスの「事業の内容」は417字あるが、中身は当期の異動（JX金属が上場し金属事業を非継続事業へ分類した）の説明だけで、事業の内訳は**画像の事業系統図**にあってテキストブロックには残らない。**文字数では検出できない**ので、落とすのは検証パスの仕事になる。

落ちた会社は**節ごと出さない**。ロゴが1,867社中1,636社にしか出ていないのと同じ扱いで、空の器・プレースホルダ・「準備中」を置かない。

### 3. 生成であることをサイト上で明示し、出典を併記する

説明文の近くに**出典と、要約であること**を出す（「有価証券報告書『事業の内容』（2026年3月期）をもとに要約」）。方法は `/about` に書き、説明文から導線を張る。決算期は直書きせず `web/lib/data/period.ts` から引く（`docs/site-chrome/spec.md` AC-20）。

**同じ断りを1画面に2回置かない**（Issue #128 で「推定」について決めたのと同じ扱い）。

**呼び方を分ける。** サイト上でもドキュメント上でも、この文は「**説明文**」——有報の「事業の内容」から導ける事実だけを述べたもの——であって、「解説文」「紹介文」ではない。一般に知られた話や評価を含む文は引き続き作らない。この区別は `docs/company/spec.md` 1.16 と 1.18 が持つ。

## 理由

**同じ一次情報から作れることが、この出所を選ぶ唯一の理由である。** 年収と同じ有報・同じ書類ID・同じ決算期なので、1文ごとに書類まで遡れる。外部サイトの説明文を引いてくる案とはここが違う。「数値の出典と計算方法は必ずユーザーから見える場所に置く」（CLAUDE.md）を、文に対しても同じ形で通せる。

**当時の懸念は2つあり、両方に手当てが付いた。** 「1,867社ぶんを人手で書けない」は生成で外れる。「生成して埋めれば根拠の無い断定が混ざる」は、**原文を1つに固定し、原文から導けない文を落とす**ことで外れる。**後者は「生成をやめる」以外の解き方が無いと思われていたが、混ざる経路がモデルの一般知識である以上、入力を絞って出力を検める形で塞げる。**

**全社で取れることを実測で確かめてから決めている。** 90/90 は「たまたま大手が持っていた」ではなく、開示府令の様式に由来する。取得率が7割なら、この決定は「ページの3割が空く」を抱えることになり、判断は変わっていた。

**費用は判断材料から外してよい。** 全1,867社ぶんの要約が $2〜6（約400〜900円）で、年1回の再生成でも同額。原文の SHA-1 が変わった会社だけ回し直せば2年目以降はさらに減る。原文の打ち切りも要らない（2,000字で切っても浮くのは1割で、代わりに p90 の3,000字クラスが事業の後半を失う）。

**【2026-08-26】この段落は「結果」の追記で置き換わった。** API を使わないので金額の見積りは効かず、代わりに1セッションに入る量が制約になる。**「打ち切りは要らない」という結論だけを引き継がないこと。**

**モックの3行を「データが無いから作らない」としてきた根拠が消える。** `docs/company/intent.md` の H1（「◯◯ 年収」の検索需要を受ける）に対して、1,867枚のページの一等地が空いたままだった。

## 結果

- **`docs/company/intent.md`・`spec.md`・`overview.md` を同時に改訂する。** intent の「作らないもの」から会社ごとの解説文を外し（外した理由は残す）、spec に 1.18 と AC-18〜AC-23 を足し、overview の Unit 一覧に C5・C6・C7 を足す
- **パイプラインに工程が2つ増える。** 原文の取得（C5）と要約の生成（C6）。年1回のデータ更新の手順が長くなる
- **ビルド工程に有料の外部API（Anthropic API）が入る。** `docs/product/product.md` の制約「ランニングコストをゼロに保つ」に触れるので明示する。**配信時には呼ばない**——生成はオフラインのバッチで、公開サイトは従来どおり DB も外部API も持たない（ADR-0004）。制約が防いでいるのは「稼働させ続けるのに金がかかる状態」で、年1回・数百円の生成費はそこに当たらない、というのが運営者の判断（2026-08-23）である
  - **【C6 で決め直した／2026-08-26】Anthropic API は使わない。生成は Claude Code のセッション（Max サブスクの枠）で回す。** 運営者の判断で、サブスクとは別課金になる API を増やさないことにした。**決定1〜3は変わらない**——出所も、原文から導ける事実だけという線も、生成であることを明示することも同じで、**変わったのは誰が呼ぶかだけ**である。ただし次の3つが結果として変わる
  - **年1回の更新手順に「スクリプトを回す」以外の工程が入る。** バッチの切り出し・機械ゲート・CSV への取り込みはスクリプトのままだが、**生成と検証はセッションのエージェントが担う**ので、`npm run …` 1本では終わらない。手順は C6 の design.md に書く
  - **1回では全社ぶんが回らない。** 原文は2,960社で 5,345,767字あり、生成で1回・検証でもう1回読ませると1,000万トークンを超える。**「回すたびに未生成のぶんを進める」形にする**——Issue #160 の AC-8（`source_sha1` が同じ社を再生成しない）がそのまま再開の仕組みになる
  - **費用をログに出す（AC-9）意味が変わる。** 出すのは金額ではなく、**進み具合（生成済み / 未生成）と、その回で読ませた原文の量**になる。**原文の打ち切りを却下した根拠も消える**——「2,000字で切っても浮くのは1割」は費用の話で、いま効くのは1セッションに入る量のほうである。切るかどうかは C6 のパイロットで実測してから決める
- **説明文の無い会社が出る。** 何社になるかは C6 を回すまで分からない。**節ごと出さない**ので、ページの構成が会社によって変わる
- **誤りが見つかったときの直し方は「その会社を `rejected` にして節を消す」だけになる。** 会社ごとの手動での上書きは持たない（C6 の非対象）。運用を増やさない代わりに、粒度の細かい訂正はできない
- **ペイロードは別ファイルに分ける。** 1,867社 × 約110字で raw 約600KB になり、`companies.json` の gzip 100KB の上限には収まらない（`worklife.json` の前例と同じ扱い。C7 で実測して上限を決める）
- **`/about` に節が1つ増える。** 出所・生成・検証の手順を書く。ロゴの出典（ADR-0008）と同じ位置づけ
- **glossary に「説明文」の項を足す**（C7）。「解説文」「紹介文」を使わない語の表に入れる
- **meta description と JSON-LD への流用はしない。** site-chrome の S2（#116）が構造化データを持っているので衝突する。必要になったら別 Issue にする

## 却下案

**モデルの一般知識で補う。** モックの3行に近い、読んで面白い文になる。だが上のキーエンスの例のとおり原文と逆のことを書き、しかも**混ざったことを検出する手段が無い**。1,867社ぶんのうち何社が誤っているかを誰も言えない状態になる。`spec.md` 1.17「SEO のための文だからといって、根拠の無い文は置かない」と両立しない。

**gBizINFO の `business_summary` をそのまま載せる。** 法人番号で引けて（ADR-0009 の突合キーがそのまま使える）、生成が要らないので断定も混ざらない。**だが説明文として弱い。** 無作為40社の実測で、APIは 40/40 成功したが `business_summary` があるのは 33/40（82.5%）、中身は「非鉄金属製造業」（三菱マテリアル）「卸売業」（兼松）「企画・販売」（ゴールドウイン）で、h1 の直下に置く文にならない。更新日が2018年のものが40社中17社ある。**要約が業種をまるごと取り違えたときの突き合わせ材料としては使える**（使うなら C6 の design に書く）。

**Wikipedia / Wikidata の説明を使う。** CC BY-SA の継承条件が付き、1,867ページにライセンス表記と履歴へのリンクを置くことになる。有報ベースの他の数値と出典の扱いが二重になる。カバー率も上場の大手に偏る。

**手動で上位N社だけ書く。** 誤りは出にくいが、上位200社を書いても残り1,667社のページは今のままになる。運営者は2026年10月から工数がほぼ取れない（`docs/product/product.md` の制約）ので、毎年の更新に人手の執筆を組み込めない。

**沿革・経営方針も原文に足して、書けない会社を減らす。** 材料は増えるが、答えが「何をやっている会社か」からずれる。ENEOS のような会社では**それらしい文が書けてしまう**ぶん、書けないことが見えなくなるほうが悪い。

**現状維持（説明文を作らない）。** 一等地が空いたままになる。C3 の時点ではこれが正しかったが、それは「全社ぶん取れる原文があるか」を実測していなかったためで、実測した後まで同じ判断を続ける理由が無い。
