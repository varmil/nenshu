# ADR-0012 全社ぶんのデータをHTMLに埋めるのをやめ、静的アセットとして1回だけ配る

状態: Accepted
日付: 2026-08-24

## 文脈

`/` は `RankingApp` を `"use client"` で描いており、`companies` を props で受け取っている。**Next.js はクライアントコンポーネントの props をハイドレーション用データとしてHTMLに直列化する**ので、結果として**全1,867社ぶんのデータが初回HTMLに丸ごと入っている**（`docs/ranking/ranking-pagination/design.md`・Issue #22）。

この方式は意図されたものである。年齢スイッチ・フィルタ・検索・並び替え・ページ送りを**ネットワーク無しで完結させる**という受け入れ基準（`docs/ranking/spec.md` AC-7・ADR-0003）を満たすには、クライアントが全件を持っている必要がある。U6 でページ送りを実ナビゲーションにしなかったのも、クライアントが既に全件を持っているためだった。

Issue #22 のコメントは「4,000社規模では約137KBになり、100KB予算を超える」と見込んでいた。**母集団の拡大（ADR-0011）の実データで測ったところ、この見込みは外れた。**

| | 1,867社（現行） | 2,962社（拡大後） |
| --- | ---: | ---: |
| `/` の HTML（gzip） | 63,654 B | **90,724 B** |
| `/` の HTML（raw） | 373,821 B | 456,338 B |
| `companies.json`（gzip -9） | 44,631 B | 70,610 B |
| `stats.json`（gzip -9） | 39,922 B | 68,515 B |

外れた理由は2つある。**掲載社数は4,000ではなく2,962だった**（`MIN_EMPLOYEES` で1,049社が落ちる）ことと、**gzip 後のサイズが行数に比例しない**ことである。

`docs/ranking/spec.md` 3.「データ量」の予算は **gzip 後 100KB 以内**で、90,724 B はその **90.7%** になる。**予算内だが、余白は 9.3KB しか残らない。**

**もう1つ、既に起きている問題がある。** Cloudflare Workers 無料枠の CPU 10ms/リクエストを本番で散発的に超えている（Issue #118・`outcome: exceededCpu`）。**全社ぶんの直列化はリクエストごとに走る。**

## 決定

**全社ぶんのデータをクライアントコンポーネントの props で渡すのをやめ、同じデータを静的アセットとして配る。クライアントは初回に1度だけ取りに行く。**

- **サーバーは、そのURLで表示する1ページぶん（30行）と、絞り込みに要るメタデータだけを渡す。** 全件の配列は渡さない
- **クライアントは初回に1度だけ全件を取り、以後の操作はいまと同じくクライアント側で完結する**（`docs/ranking/spec.md` AC-7 は守る）
- **届く前・届かなかったときは、実ナビゲーションに倒せること。** すべての状態は URL にあり、`/` はどの URL でも正しく SSR できる（ADR-0004）
- **HTML とデータのビルドがずれたら、クライアント側の引き継ぎをしない。** `companies.meta.version` を突き合わせる
- **`/` の初期表示（上位30社）は引き続き HTML に含める**（`docs/ranking/spec.md` 3.「SEO」）

**ただしこれを母集団の拡大（ADR-0011）の前提条件にしない。** 実測で予算内である以上、拡大を待たせる理由が無い。Unit の依存関係でも E0 は独立に置く（`docs/expansion/overview.md`）。

**この決定は方式だけを決める。** アセットのURLの形・キャッシュ規則・フォールバックの実装は Unit E0 の design.md に置く。**キャッシュ規則の置き場所は `web/lib/cache/headers.ts` の1か所という ADR-0004 の決定に従う。**

## 理由

**余白が 9.3KB しか無い状態を、次の機能追加まで持ち越せない。** すぐ後ろに1行あたりの情報を増やす変更が控えている——会社ごとの決算期（Unit E1・`docs/expansion/spec.md` 1.4）がその1つで、**「トップページのHTMLを1バイトも増やさない」を完了条件に書いた Unit（performance の P0・Issue #155）まである。** 予算の9割を1つのデータ形式が占めていること自体が、以後の設計の制約になる。

**予算を割るのは HTML であって `companies.json` ではない。** `build:data` が見ている100KB上限は `companies.json` 単体にかかっており（`COMPANIES_JSON_GZIP_LIMIT_BYTES`）、拡大後でも 70,610 B で収まる。**先に効くのはページ側になる。** データをページの外に出せば、同じバイト数でもページの予算に載らない。

**同じバイト数でも、配り方で回数が変わる。** いまの方式では、全社ぶんが `/`・`/?age=25`・`/?ind=銀行業`・`/?page=2` …の**どのURLのHTMLにも入っている**。読者が業種チップを踏んで別のURLへ移るたび、エッジは別のキャッシュエントリを配る。**アセットとして分ければ、それらは全部同じ1つのファイルを共有する。**

**リクエストごとの CPU が減る。** 全社ぶんの直列化がリクエストから消える。**本番で実際に出ている CPU 超過（Issue #118）と同じ側の負荷**なので、母集団を1.59倍にする前後で効く方向になる。

**この方式は既にサイトの中で使われている。** `stats.json` は `/` に丸ごと渡さず母集団統計だけを抜いて渡し（`pickPopulationStats`・1KB未満）、`logos.json`（gzip 41.7KB）はロゴの有無だけの文字列に畳んで渡している（`buildLogoMask`・約250B）。**`companies` だけが「全部渡す」のまま残っている。**

**`/data/companies.json` は既に公開されている。** `web/public/data/` に置いてあるので、`https://openreport.net/data/companies.json` が現に 200 を返す（実測）。**新しいビルド成果物を作る必要が無い。**

**AC-7 を割らない。** 「操作でネットワークが発生しない」は操作の話で、初回ロードの話ではない。**E2E の「リクエスト数0」は既に画像とファビコンで緩めてある**（`e2e/network.ts`）ので、同じ形で「操作の後に増えないこと」を測る形に寄せられる。

## 結果

- **`/` の HTML が大きく縮む。** 全社ぶんの直列化が消えるので、残るのは30行ぶんの markup と業種チップ・母集団統計になる
- **初回訪問の合計バイト数はほぼ変わらない。** HTML から出した分がアセットに移るだけになる。**変わるのは、それが2ページ目以降で再送されなくなること**
- **初回ロードの直後に、操作できない短い時間ができる。** アセットが届くまでは実ナビゲーションに倒す。**この経路を持たない実装にしない**——届かなかったときに操作が沈黙する
- **`e2e/network.ts` の測り方が変わる。** 「0件」から「操作の後に増えない」へ
- **U6 の前提（クライアントは既に全件を持っている）が「初回ロード後は持っている」に変わる。** ページ送りをネットワークにしない判断そのものは変わらない
- **`docs/ranking/spec.md` 3.「データ量」の読み方をはっきりさせる必要がある。** 予算は「初期ロードのペイロード」＝HTMLにかかる。アセットは別枠として上限を持つ
- **`stats.json` の側は解決しない。** gzip 68,515 B はページには乗らないが、Worker のモジュール評価では読まれる。CPU 超過（Issue #118）の調査はこの ADR の範囲外に残る

## 却下案

**何もしない（全件embed のまま）。** 拡大後も予算内なので、**この選択は成り立つ**。退けるのは、余白が 9.3KB しか残らず、次に1行あたりの情報を増やす変更で必ず戻ってくるためである。**「いま壊れていない」と「次の変更が入る」は両立する。**

**予算（100KB）を引き上げる。** 数字を動かせば超過は消えるが、**gzip 90KB の HTML をモバイルの読者に配る事実は変わらない。** 予算は測るための線であって、当てにいく的ではない。

**行の符号化を詰める。** `companies.rows` は既に配列の配列で、業種は添字、社名以外はすべて数値になっている。**残っているバイトのほとんどは社名（日本語・UTF-8で1文字3バイト）で、検索に要るので落とせない。** 削りしろが無い側を削ることになる。

**操作のたびにサーバーへ取りに行く（`<Link>` ＋ RSC）。** `docs/ranking/spec.md` AC-7（操作でネットワークが発生しない）を正面から割る。URL同期を `pushState` で直接やっている実装（U5・U14）と、`useRouter()` を使わないという決定（CLAUDE.md）もこの上に乗っている。**Workers のリクエスト数も操作のたびに増える**ので、CPU 超過（Issue #118）に対して逆向きになる。

**絞り込み・検索に要る最小限だけHTMLに埋め、詳細は別に取る。** 検索に要るのは社名で、それがバイト数のほとんどを占める。**分けても軽くならない。**

**D1（Cloudflare の無料SQLite）に載せる。** 読み取り専用のデータにDBを持ち込まない、という判断は `worklife` で既にしてある（`docs/worklife/`）。リクエストごとのクエリは AC-7 とも CPU 予算とも噛み合わない。

**ページ送りだけサーバー側にする。** ページ送りは動くようになるが、**フィルタと検索がクライアント側にある以上、全件は結局クライアントに要る。** 何も解決しない。
