# ADR-0007 既定の表示基準を有報の実測値にし、モードは `age` の有無で表す

状態: Accepted

日付: 2026-08-20

ADR-0003・ADR-0005 の推定式は変えない。変えるのは**何を既定で見せるか**と、その状態をURLでどう表すかである。ADR-0006 が決めた `?age=` 8件の自己canonical・sitemap 登録はそのまま有効で、supersede しない。

> **2026-08-24 追記（[ADR-0012](0012-prerender-company-pages.md)）**: 決定2「モードは `age` の有無で表す」は、**企業詳細ページについては置き換わった。** `/company/[id]` は全社を事前生成しており、`force-static` のページは `searchParams` を読めない。表示基準はクライアントの状態としてだけ持ち、URL には出さない。**ランキング（`/`）は変わらない**——あちらの `?age=N` は1,867行の並び順そのものを変え、8件をインデックスさせている。決定1（2モードを両ページに置き、既定は実測値）は変わらない。

## 文脈

クエリ無しで `/` を開いたときに出るのは、これまで **35歳に補正した推定年収**だった。「推定」バッジと注記は付けていたが、既定で見せる数字が推定値であるという構図そのものに次の問題がある。

- `docs/product/product.md` の「根拠を隠した推定値を表示しない」という立て方と噛み合わない。初見の読者にとって、2,178万円という数字が有報に載っているのか計算で出したのかは、バッジ1つでは区別が付きにくい。
- 「有価証券報告書の平均年間給与」は**検証可能な一次情報**である。サイトの信頼はここから立ち上がるはずで、既定はこちらが素直になる。
- 推定は**読者が明示的に求めたときに出す**ほうが、値の性格が伝わる。「年齢をそろえて比べたい」という意図が操作として表れてから推定を出す。

年齢補正そのものを捨てるわけではない。`docs/ranking/intent.md` H1 の「知りたいのは順位ではなく金額」は変わらず、平均年齢がばらつく会社どうしを比べるには補正が要る。既定から外して2つ目のモードにする。

## 決定

### 1. 表示基準を2つ持ち、既定を「実測値」にする

| モード | 出す数字 | 順位・偏差値の母集団 |
| --- | --- | --- |
| **実測値**（既定） | 有報の平均年間給与（提出会社単体）そのまま | 実測値の分布 |
| 年齢そろえ | 業種の賃金カーブで目標年齢に補正した推定年収（ADR-0005） | その年齢の推定値の分布 |

ランキングページと企業詳細ページの両方に同じ2モードを置く。**片方だけ変えない**——同じサイトの中で既定の表示基準が食い違うと、ページを行き来した読者が数字の変化を理解できない。

母集団統計は別物になる。実測値の平均は 719万円・標準偏差 200万円で、35歳そろえの 629万円・155万円とは異なる。同じ会社でも順位が動く（トヨタ自動車は実測値121位・35歳そろえ120位、三菱商事は実測値2位・35歳そろえ3位）。

### 2. モードは `basis` パラメータではなく `age` の有無で表す

```
/                     実測値（既定）
/?age=35              年齢そろえ・35歳
/?ind=銀行業          実測値・銀行業
/?age=45&ind=銀行業   年齢そろえ・45歳・銀行業
```

検討した対案は `?basis=raw`（既定・省略）／`?basis=age&age=35` の2パラメータ構成だった。採らない理由は次のとおり。

- **矛盾した状態が表現できてしまう。** `basis=raw&age=35`、`basis=age`（`age` 無し）といったURLが作れ、そのたびにどちらを優先するかの分岐がURL解析・状態・描画のそれぞれに要る。`age` の有無で表せば、状態は `targetAge: TargetAge | null` の1つの値になり、**矛盾を型の上で作れない。**
- **パラメータが1つ減る。** `basis=age` と `age` が常に同伴する冗長さが無くなる。
- **ADR-0006 の canonical 規則が増えない。** `?age=` 8件の自己canonical・sitemap 登録（U8・Issue #53）はそのまま使える。

**年齢そろえのときは35歳でも `age=35` を出す。** 35歳を既定値として省略していた頃とは扱いが変わる——省くと実測値のURLと区別が付かなくなるため。

意味が変わるのは「クエリ無しの `/`」だけである。`/?age=45` のように年齢を明示して共有された既存のURLは、開いたときの見え方が変わらない。

### 3. 実測値のとき年齢スイッチは消さずに無効化する

消すと「年齢そろえ」に切り替えたとき何が使えるようになるのかが事前に分からず、切替そのものの意味が読めない。表示は残し `disabled` にして淡くする。

### 4. 実測値では「推定」の語を一切出さない

推定バッジも「推定年収は年齢補正後の推定値です」の断りも出さない。有報そのままの数字に推定の体裁を被せると、`docs/ranking/spec.md` AC-9 が要求する「推定値と実測値を同じ書式で並べない」が逆向きに壊れる。

## 結果

- 既定で見せる数字が検証可能な一次情報になる。出典（EDINET の有報・提出会社単体）を数字のすぐ隣に書ける
- 年齢補正は読者が選んだときだけ出るので、推定であることが操作の文脈で伝わる
- **母集団統計を表示基準ごとに持つ必要がある。** `stats.json` の `population` / `rankAll` / `rankIndustry` は `bases = [null, 25, 30, ..., 60]` の9列になった（先頭が実測値）。ビルド時に確定させる方針は `docs/company/company-page/design.md` のまま変わらない
- **実測値は平均年齢の高い会社に有利に出る。** 総合商社・不動産・放送が上位に来て、若い会社は低く出る。これは補正していないことの当然の帰結であり、見出し直下の説明文と表の caption で明示する。「年齢そろえ」がその対処として同じ画面にある
- 既存のE2Eが広く当たった（17本）。既定が変わった結果として正しいかを1本ずつ見て直した

## 代替案

- **既定を年齢そろえのまま、推定の注記を強くする。** バッジと注記は既にあり、それでも「既定が推定値」という構図は変わらないので採らない。
- **2つの数字を常に並べて出す。** 1行に2つの金額が並ぶと、どちらで並んでいるのかが読めなくなる。ランキングは並び順が主要な情報なので、基準は1つに決まっている必要がある。
- **`?basis=` の2パラメータ構成。** 上記2のとおり。
