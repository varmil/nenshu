# ADR-0012: 企業詳細ページを事前生成し、表示基準を URL に出さない

- 状態: 採用
- 日付: 2026-08-24
- 関連: [ADR-0004](0004-ssr-opennext-cloudflare.md)（フルSSR。一部を supersede）, [ADR-0006](0006-public-url-strategy.md)（公開URL）, [ADR-0007](0007-default-salary-basis-raw.md)（表示基準。企業詳細ぶんを改訂）, Issue [#118](https://github.com/varmil/nenshu/issues/118)（親）, [#180](https://github.com/varmil/nenshu/issues/180)（R1）

## 背景

ADR-0004 で Cloudflare Workers 上のフルSSRにし、**全ページをリクエストごとに描画している。** 無料枠の CPU は1リクエストあたり 10ms で、`/company/[id]` が散発的にこれを超えて `exceededCpu` で落ちている。踏んでいるのはクローラ（`ClaudeBot`）で、1,867社ぶんの異なるURLを世界中のコロから叩くためエッジキャッシュはほぼ全部ミスし、isolate は毎回冷えている。

一度は「ページが読むデータを減らす」方向で当てた（#165）が、稼げたのは cold で 1.7〜2.0ms、予算の2割ぶんだった。**仕掛けの重さに対して効果が見合わず、丸ごと戻した**（#179）。

**調査で分かったのは、いちばん重いのは描画そのものだということ。** そして OpenNext の `incrementalCache` は既定が `"dummy"` で、**`next build` が `○ (Static)` と出しているページすら毎リクエスト描画し直していた**——`/about` が企業詳細より重かったのはこれが理由である。

実測（`wrangler dev --local`・40リクエストの平均 CPU・同一セッション。この環境は本番より数倍遅いので絶対値ではなく前後の比を見る）:

| | 前 | 後 |
| --- | ---: | ---: |
| `/company/8282` | 29.6〜29.7ms | **14.0〜14.1ms** |
| `/company/7203` | 26.5〜29.0ms | **13.6〜13.7ms** |
| `/about`（`incrementalCache` を挿す前） | 47.7〜59.6ms | **12.4〜13.5ms** |
| `/`（動的のまま） | 41.7〜46.5ms | 46.3〜48.5ms |
| `/favicon.ico`（静的アセットの床） | 5.3〜6.1ms | 5.1〜5.6ms |

床を引いた「アプリぶん」では、企業詳細が 21〜24ms → 8〜9ms、`/about` が 42〜54ms → 7〜8ms。

**企業詳細の「前」は、同じコードの `force-static` を `force-dynamic` に入れ替えただけのビルドで測っている。** 同じデータ・同じ節で、違うのは描くか引くかだけ。

## 決定

**1. `/company/[id]` は全1,867社をビルド時に生成する。** `generateStaticParams` ＋ `dynamic = "force-static"` ＋ `dynamicParams = false`。一覧に無いIDは 404。

**2. OpenNext の `incrementalCache` に `staticAssetsIncrementalCache` を挿す。** 事前生成した結果は Workers の静的アセット（`cdn-cgi/_next_cache/`）に置き、Worker は `ASSETS.fetch` で引くだけにする。**KV・R2・D1 のバインディングは増やさない**（`docs/product/product.md` の「ランニングコストをゼロに保つ」）。再検証はできないが、このサイトのデータは年1回のビルドでしか変わらない。

**3. 企業詳細ページの表示基準（実測値／年齢そろえ）は URL に出さない。** `/company/[id]?age=N` を出さず、クライアントの状態としてだけ持つ。配ってしまった `?age=N` は読まずに `replaceState` で落とす。**ADR-0007 の「モードは `age` の有無で表す」は、企業詳細ページについてはこれで置き換わる。ランキング（`/`）は変えない。**

**4. `enableCacheInterception` は使わない。** Next.js のルーティングに入る前にキャッシュを返すので CPU は少し減る（19.7ms → 15.6ms）が、**プリフェッチのリクエストにもフルの RSC ペイロードを返してしまい、クライアントのルーターが取り直しを繰り返す**（Issue 183。本番で `/about?_rsc=…` が毎秒約128回）。事前生成の主効果とは無関係の上積みなので、外す。

**5. `/` は動的なまま残す。** `searchParams`（`?age=`・`?ind=` の41ファセット・`?q=`・`?page=`）を読んでSSRするため事前生成できない。

## 理由

**描かないのがいちばん効く。** データを読む量を削っても、描画そのものは残る。事前生成すれば `JSON.parse` も `buildCompanyView` も `findNeighbors` も React の描画も、全部ビルド時に移る。

**`?age=` を外すのは、機能を削らずに済む交換だから。** 年齢そろえで変わるのは推定年収まわり（金額・順位・偏差値・分布・近傍5社・要点）だけで、実測値の節も10年推移も変わらない。**この先この画面に項目が増えるほど、ページ全体にかかるパラメータとしての `?age=` は意味が薄れる**——いずれ推定年収の要素に付いたスイッチへ寄せる。SEO 上の損も無い: `?age=N` は sitemap に無く、canonical は既に素の `/company/[id]` へ寄せてある（ADR-0006）。

**ランキングの `?age=N` とは役割が違う。** あちらは1,867行の並び順そのものを変え、8件をインデックスさせている。同じ語だが、企業詳細の `?age=` は1社の1要素の見せ方でしかない。

## 影響

**メタデータが1組に固定される。** 企業詳細の title・description・canonical は表示基準で変わらなくなる。**U16（#135）が企業詳細で直していた「タイトルの金額と画面の金額が食い違う」（親 #130）は起きようが無くなった。** ただし `usePageMeta` は呼び続ける——ランキングから遷移してきたときに前のページの canonical と description が `<head>` に残るため（`usePageMeta` は DOM を直接書き換えるので React の管理外にあり、遷移では戻らない）。

**戻る/進むで表示基準は復元されない。** URL に無いものは復元できない。ランキング側の絞り込み・ページ番号は URL が正のまま変わらない（U14・#108）。

**この先 `/company/[id]` に項目を足す Unit は `searchParams` を読めない**（C5〜C7・#159〜#161）。読みたくなったらそれは「このページを動的に戻す」という決定なので、この ADR を改訂すること。

**デプロイのアセットが 15MB → 344MB になる。** 1,874ページ × 約180KB。無料枠の上限は「ファイル数 20,000・1ファイル 25MiB」で、ファイル数は 1,655 → 3,528 に収まる。**アセットへの配置は `opennextjs-cloudflare deploy` が自動でやる**（`populateStaticAssetsIncrementalCache`）ので手作業は無い。

**データを更新したら全ページを作り直す。** 年1回なので運用の負担にならない。ビルドの実測は 1,874ページで 19.9秒（`next build` 全体で1分5秒）。

**追記（2026-08-25・E2 で母集団を 2,961社に広げた後の実測）。** ページ数がそのまま増える構造は変わらず、**上限には当たっていない。**

| | R1 の時点（1,867社） | E2 の後（2,961社） | 無料枠の上限 |
| --- | ---: | ---: | --- |
| 事前生成のページ数 | 1,874 | **2,967** | — |
| アセット | 344MB | **634MB** | 1ファイル 25MiB |
| ファイル数 | 3,528 | **4,629** | 20,000 |
| 1ファイルの最大 | — | **0.48MiB** | 25MiB |
| Worker（gzip） | 1.70MB | **1.85MB** | 3MiB |
| 事前生成の時間 | 19.9秒 | **26.4秒**（`next build` 全体で45秒） | — |

**ファイル数がいちばん先に当たる枠だが、まだ4分の1にも届かない。** 1ページあたりは 214KB（R1 の時点は 230KB）で、増えているのはページ数だけになる。

## 却下した案

**有料プランへ上げる。** CPU 30秒で即座に解決するが、`docs/product/product.md` の制約に反する。

**ページが読むデータファイルを分割する。** 一度やって戻した（#165・#179）。cold で 1.7〜2.0ms しか稼げず、生成物と lint の規則が増えた。**事前生成すれば `JSON.parse` はビルド時にしか走らない**ので、この筋が残るのは `/` だけになる。

**ISR（`revalidate`）。** KV か R2 のバインディングが要る。**再検証したい対象が無い**——データは年1回のビルドでしか変わらないので、読み取り専用で足りる。

**`?age=N` を残したまま事前生成する。** `force-static` のページは `searchParams` を読めないので、両立しない。`generateStaticParams` に `?age=` の9通りを掛けることもできない（クエリ文字列はパスではない）。

**古い `?age=N` を1度だけ読んでから落とす。** 共有リンクの意図（「この会社の30歳時点」）は活きるが、「URL が正」の規則に半分戻ることになる。**読まずに落とす**——落とさないと「URLは30歳・画面は実測値」がそのまま残り、親 #130 が報告した形になる。
