# ADR-0006 公開URLの構成とインデックス戦略

状態: Accepted

日付: 2026-08-18

`docs/ranking/overview.md` 末尾および `docs/ranking/url-sync/design.md` で確定していた Bolt 2 のパス設計（`/age/[age]` 8枚・`/industry/[industry]` 33枚・`/company/[key]` 1,867枚）を supersede する。`/company/[id]` は残すが、ID の作り方を変える。

## 文脈

North Star KPI は自然検索からの月間セッション数（`docs/ranking/intent.md`）で、公開URLの構成はその土台になる。一度公開したURLは、変えれば積み上げた評価を捨てることになるため、企業詳細ページを出す前に決め切る必要がある。

論点は2つある。

### 論点1: 年齢別・業種別のページを独立したパスにするか（Issue #49）

U5 の時点では `/age/25`・`/industry/銀行業` を静的ページとして生成する前提だった。しかしその後 ADR-0004 でフルSSRに移行し、**`/?age=25` や `/?ind=銀行業` を直接開いても、サーバーが返すHTMLは既にその絞り込み結果になっている。** パスにしなければクロールできない、という当初の制約は消えている。

残るのは純粋にSEO上の優劣の問題で、調べた範囲では次のとおりだった。

- Google のファセットナビゲーション指針は「必要でなければファセットURLをクロールさせない」を基本とし、**クロールさせるものとして推奨しているのは「個別アイテムのページ」と「フィルタ無しの一覧1枚」**である。組み合わせは `rel="canonical"` で寄せると、時間とともに非正規版のクロール量が減る（[Managing crawling of faceted navigation URLs](https://developers.google.com/crawling/docs/faceted-navigation)）。
- この指針はURLの形（パスかクエリか）で分岐していない。**パスにしても同じ扱いになる。** サーバー側のリライトでクエリをパスに変換する手法は紹介されているが、それが有利になるのは「検索に意味のあるキーワードを含む属性」の場合という但し書きが付く。
- URL に含まれるキーワードは、Google が繰り返し「ごく小さな要因」と説明している。

つまり `/age/25` と `/?age=25` の差は小さく、41枚ぶんのルート実装・テスト・内部リンクを新たに抱える対価に見合わない。**一方で「どのURLをインデックスさせ、どれを寄せるか」を決める作業は、パスにしてもクエリにしても等しく必要になる**（パスにすればクエリ版との重複をどちらに寄せるかという問題が新たに増えるだけ）。

なお、年齢の切り替えは表の全数値が変わるので純粋なファセットではない。一方で業種フィルタは行の部分集合を出す典型的なファセットにあたる。それでも両者を同じ扱いにするのは、業種名を含む検索（「銀行業 年収 ランキング」）が現実に存在し、33件という規模ならクロール予算を脅かさないためである。

### 論点2: 企業詳細ページのIDに何を使うか

現行の `makeId`（`pipeline/scripts/lib/slug.ts`）は、証券コードがあればそれを、無ければ社名のASCII部分＋**書類ID**（EDINET書類管理番号）を使う。1,867社の内訳は証券コード1,760社・書類ID由来107社（証券コードを持つ1,760社には、上場廃止後も証券コードが残る2社を含む。`listed` 列で数えた上場は1,758社）。

**書類IDは毎年の有報提出ごとに新しく振られる。** 年1回のデータ更新（`docs/product/product.md`）のたびに、この107社のURLが変わる。

| 会社 | 現行のID |
| --- | --- |
| 株式会社みずほ銀行 | `s100yfah` |
| 株式会社ＪＥＲＡ | `jera-s100ycjz` |
| 株式会社日本政策投資銀行 | `s100ylav` |

非上場の事業会社を載せていることは `docs/ranking/intent.md` が挙げる差別化要因そのもので、みずほ銀行のような会社がまさにこの107社に入る。**最も価値のあるページのURLが毎年リセットされる**構成のまま公開するわけにはいかない。

`makeId` の docstring には「Bolt 2 で企業詳細ページを作る際、正式な読み仮名データを調達してから作り直す前提」と書いてあった。しかし読める URL にするかどうかと、URL を年をまたいで安定させるかどうかは別の問題で、後者のほうが先に効く。前提のほうを見直す。

## 決定

### 1. 年齢別・業種別の独立したパスは作らない

`/age/[age]`・`/industry/[industry]` は実装しない。ランキングは `/` 1枚のままで、状態はクエリで表す（U5 で決めた形をそのまま公開URLとして使う）。

インデックスさせる対象を次のように定める。

| URL | canonical | sitemap |
| --- | --- | --- |
| `/` | 自己 | 載せる |
| `/about` | 自己 | 載せる |
| `/?age=N`（8件） | 自己 | 載せる |
| `/?ind=X`（33件） | 自己 | 載せる |
| `/company/[id]`（1,867件） | 自己 | 載せる |
| `/?age=N&ind=X` | `/?age=N` | 載せない |
| `emp`・`ten`・`aage`・`q`・`page` を含むURL | `/` | 載せない |

`?age=N&ind=X` を年齢側に寄せるのは、年齢補正がこのサイトの主軸だからである。Search Console のデータが溜まった時点で見直す余地がある（見直しは canonical の付け替えだけで済み、URLの引っ越しにはならない）。

**ADR-0007 で `age` の有無が表示基準（実測値 / 年齢そろえ）を表すようになったが、この表はそのまま有効である。** `/` は「実測値・フィルタ無しの一覧1枚」になり、Google のファセットナビゲーション指針が推奨する形により素直に合う。`/?age=N` 8件が年齢そろえのページとして自己canonical を持つ点も変わらない。ただし**上の「年齢補正がこのサイトの主軸」という前提は弱まった**ので、`?age=N&ind=X` をどちらに寄せるかは U8（Issue #53）の実装時に再考する。

**【U8（Issue #53）で決め直した／2026-08-21】`?age=N&ind=X` の canonical は `/?ind=X`（業種側）に変えた。** 上の表の当該行を読み替える。決め手は「主軸がどちらか」ではなく、**どちらと重複しているか**に置いた。

| URL | 並ぶ会社 | 金額の基準 |
| --- | --- | --- |
| `/?ind=銀行業` | 銀行業のN社 | 実測値 |
| `/?age=35` | 全1,867社 | 35歳そろえ |
| `/?age=35&ind=銀行業` | 銀行業のN社 | 35歳そろえ |

`/?age=35&ind=銀行業` は `/?ind=銀行業` と**同じ会社が同じ順で並ぶ** near-duplicate で、`/?age=35` とは行数から違う別のページである。canonical は重複している相手を指すものなので、業種側が正しい。「銀行業 年収 ランキング」という検索の受け皿が `/?ind=銀行業` である点も同じ向きを指す。

**`/company/[id]?age=N` は素の `/company/[id]` へ寄せる**（上の表に無かった行）。1,867社×9基準＝16,803 URL をインデックスさせる意味がない。sitemap に載せるのも素の1,867件だけで、表の `/company/[id]` の行と一致する。

**【U8 で決め直した／2026-08-21】`page` を含むURLは `/` へ寄せない。自己canonical にする。** 上の表の「`emp`・`ten`・`aage`・`q`・`page` を含むURL → `/`」の行から `page` を外す。`page` はファセットではなく、同じ一覧の続きである。

| URL | canonical |
| --- | --- |
| `/?page=3` | 自己 |
| `/?age=N&page=M` | 自己 |
| `/?ind=X&page=M` | 自己 |
| `/?age=N&ind=X&page=M` | `/?ind=X&page=M` |
| `emp`・`ten`・`aage`・`q`・`sort` を含むURL | `/`（`page` ごと落とす） |
| 総ページ数を超える `page` | ページを落として先頭へ |

理由は2つある。

1. **`/?page=2` は `/` の複製ではない。** 別の30社が並ぶ。実測すると `/` の会社リンクは30件、`/?page=2` も30件で、**1社も重ならない**。
2. **どのページからも `<a href>` で辿れる企業ページは30件しかない。** 残り1,837社への内部リンクは、ページ2〜63の中にしか存在しない（`RankingPagination` は `<a href="?page=N">` の実体を持つ）。ここを `/` の複製だと宣言すると Google はページ2以降のクロール頻度を落とし、**1,837社への内部リンク経路を自分で細める**ことになる。sitemap には1,867件載せてあるが、sitemap は発見の手段であって内部リンクのように評価を渡さない。

Google のページネーション指針も「連番の各ページに自分自身の canonical を与え、先頭ページに寄せるな」と明記している（[Pagination and incremental page loading](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)）。**sitemap には1ページ目しか載せない**ので、インデックスを勧めているわけではない——辿り着ける道を残すだけである。

合わせて、`RankingPagination` が範囲外のページへリンクしている問題を直した。`?page=999` は200で最終ページの7社を返しつつ `?page=1000` へのリンクを出しており、クローラが際限なく歩ける状態だった（実測）。`aria-disabled` と `pointer-events-none` はクローラには効かないので、総ページ数に丸めて `href` そのものを出さないようにしている。

**総ページ数はフィルタを実際に走らせなくても出せる。** 行数は業種でしか変わらない——年齢は金額を書き換えるだけで行は減らない。`emp`・`ten`・`aage`・`q` が効いているURLは丸ごと `/` へ寄せるため、canonical の判断に総ページ数を見るのは「全体」と「業種」の2通りだけになり、どちらも `companies.json` から数えられる。

### 2. 企業詳細ページは `/company/[id]`、ID は 証券コード / EDINETコード

- 証券コードがあればそれを使う（1,760社。`6861`・新形式の `285A` を含む）
- 無ければ **EDINETコード**（`E01798` 形式）を使う（107社）
- どちらも無ければ例外にして止める。**書類ID由来のフォールバックは削除する**

上場か否かではなく **証券コードの有無**で分ける。上場廃止後も証券コードが残る2社（広栄化学・養命酒製造）は証券コード側になる。

EDINETコードは提出者に対して振られる識別子で、年をまたいで変わらない。公開の EDINETコードリスト（`Edinetcode.zip`、APIキー不要）から取れる。

これに伴い `pipeline/data/ranking_unified_2026.csv` に `edinet_code` 列を追加する。

## 理由

- **41枚ぶんの実装を作らずに、同じSEO上の価値をほぼ取れる。** Google の指針が推奨するのは「個別アイテムのページ＋フィルタ無しの一覧」で、その両方を満たす構成になる。実際に取り組む価値のある作業（canonical の設計・sitemap・内部リンク）はどちらの方式でも同じだけ必要で、パスはそこに実装コストを上積みするだけになる。
- **企業詳細ページ1,867枚のほうが、年齢8枚・業種33枚よりSEO資産として厚い。** 内容が1社ずつ本当に異なり、「◯◯ 年収」という検索の実需がある。ここに労力を寄せる。
- **EDINETコードは年をまたぐ主キーとしても要る。** 将来 `docs/product/product.md` の `timeseries` 施策（平均年収の10年推移）を作るとき、年ごとの有報を同じ会社に紐づける鍵になるのは証券コードでも社名でもなくEDINETコードになる。今入れておけばそのまま使える。

## 結果

- `docs/ranking/overview.md` の「Bolt 2 以降」と `docs/ranking/url-sync/design.md` の Bolt 2 パス設計は本ADRで置き換わる。`/company/[id]` だけが残り、ID の作り方が変わる。
- `docs/ranking/intent.md` の仮説 H2 の検証方法（「`/age/[age]` を公開して3ヶ月後」）を `?age=` のURL群での計測に書き換える。Search Console はクエリ付きURLを別のページとして報告するため、計測方法としては成立する。
- `makeId` の変更で全社のIDが確定するが、**現行の `id` は React の `key` にしか使われていない**（`RankingTable.tsx`・`RankingCardList.tsx`）ため、ランキングの表示は変わらない。
- パイプライン側に `edinet_code` 列を足す。上場は証券コード、非上場は正規化した社名で EDINETコードリストと突合する。**突合できない行があれば社名を列挙して異常終了させる**（空のIDを黙って作らない）。
- `metadataBase`（canonical の絶対URLの基点）を1か所に閉じる。**ドメインは 2026-08-21 に `openreport.net` を取得済み**で、`web/lib/seo/site.ts` の `SITE_ORIGIN` がその1か所になった（U8）。公開ホストは apex 1本で、`www` は Cloudflare の Redirect Rule で apex へ 301 する。`wrangler.jsonc` の `"workers_dev": false` は、wrangler がルート指定の無い Worker に対して既定で workers.dev を有効にするため必要になる——無いとデプロイのたびに `nenshu.<subdomain>.workers.dev` が本番と同じHTMLを返す状態に戻り、同じサイトが2つのホストにある状態になる。
- `next.config.ts` の `headers()` は `/` と `/about` を列挙する形なので、`/company/:id`・`/sitemap.xml`・`/robots.txt` を追加する。

## 却下案

**予定どおり `/age/[age]`・`/industry/[industry]` を作る** — 上記のとおり、Google の扱いはパスでもクエリでも変わらず、URL内キーワードの寄与はごく小さい。41枚ぶんの実装・テスト・内部リンクに加え、クエリ版 `/?age=25` との重複をどちらに寄せるかという判断が新たに増える。得るものに対して払うものが大きい。

**`/` 以外のクエリURLをすべて `/` に寄せ、企業ページだけをSEO資産にする** — Google のファセット指針には最も忠実で、実装も最小になる。採らなかったのは、年齢別・業種別の検索需要（`docs/ranking/intent.md` の仮説 H2）を取りに行けなくなるため。8＋33件ならクロール予算の懸念は小さく、仮説を検証する余地を残すほうを選んだ。

**日本語スラッグ（`/company/キーエンス`）** — 日本語の検索結果では読みやすく見える。採らなかったのは、社名に全角スペースを含むものが74件あり、法人格の除去・重複時の解決・正規化の規則を新たに決める必要があるため。URL の可読性が順位に効く度合いは小さく、規則を発明するコストに見合わない。

**現行 `makeId` のまま公開する** — 107社のURLが毎年変わる。積み上げた評価が毎年リセットされ、外部からのリンクも切れる。KPI が自然検索である以上、選べない。

**読み仮名データを調達してローマ字スラッグにする** — `makeId` の docstring が想定していた案。**読み自体は取れる**——EDINETコードリストに `提出者名（ヨミ）` 列があり、11,383社すべてカタカナで埋まっている（`slug.ts` の docstring にあった「コードリストにも読み仮名は無い」は誤りで、C0 の実装時に実物を確認して分かった）。

それでも採らなかったのは、ローマ字化の規則（ヘボン式か訓令式か・長音の扱い・法人格を残すか・同じ読みになる会社の解決）を新たに決める必要があり、**URL の可読性が検索順位に効く度合いは小さい**ため。まず年をまたいで変わらないIDでURLを固定し、可読性が必要になればその時点で考える（リダイレクトを張ることになるが、URLが毎年変わり続ける現状より悪化しない）。
