# U14 戻る/進むの状態復元 — plan.md

Issue: [#121](https://github.com/varmil/nenshu/issues/121)（親 [#108](https://github.com/varmil/nenshu/issues/108)）
仕様: `docs/ranking/spec.md` AC-7・AC-15 ／ 分解: `docs/ranking/overview.md` U14

着手前の段取り。出来上がりの構造は design.md に書く。

## 手順

1. **再現する。** 報告された経路（トップ → 2ページ目 → 企業詳細 → 戻る）を実ブラウザで再現し、URL・描画されている画面・`history.length` を並べて記録する。**「1ページ目に戻る」以外の壊れ方が混ざっていないか**をここで見る（報告は読者から見えた症状であって、原因の数とは限らない）。
2. **周辺の経路も同じ手順で当たる。** Issue が挙げている「他にも怪しい所」を、URL を書いている場所の一覧（`pushState`/`replaceState` の呼び出し）から逆に辿って確かめる——ランキングの絞り込み、企業詳細の表示基準、共通ヘッダの検索、サイト名、業種チップ。壊れ方ごとに再現手順を残す。
3. **本番ビルドでも確かめる。** 開発サーバーは StrictMode で effect を2回走らせる。**片方でしか出ない壊れ方があるので、どちらで再現するかを記録する**（どちらか一方でしか出ないものも直す対象にする）。
4. 原因を突き止めたうえで、直す単位を決める。**同じ規則を書き写している箇所が複数あるなら、規則を1か所へ寄せてから直す**——片方だけ直すと残りに同じ壊れ方が残る。
5. 規則そのもの（純粋関数）に Unit テストを書く。ブラウザが要る部分は E2E に回す。
6. E2E を書く。**先に「修正前のコードで落ちること」を確認してから**修正を入れる（落ちないテストは回帰を止めない）。
7. 型・lint・Unit テスト・E2E をすべて通す。ビルドしてサイズの変化を見る。
8. 実測した挙動と、直さないと決めたこと（およびその根拠）を design.md に残す。spec の受け入れ基準に足りない点があれば spec.md を改訂する。
9. PR を出してマージする。

## 検証の順序

- Unit テスト（規則の純粋関数）→ E2E（実ブラウザの戻る/進む）→ 本番ビルドでの手動確認、の順。
- E2E は**修正前に落ちること**と**修正後に通ること**の両方を見る。
- 既存の E2E 全件（215件）が緑であること。とくに「操作でネットワークリクエストが発生しない」（AC-7）と、同一ページ内の戻る/進むを壊していないこと。
