## 単位を揃える必要が出た（1,000倍ずれる罠）

`curves.json` のカーブは**千円**単位、会社の平均年間給与は**円**。旧式 `平均給与 × C(t) ÷ C(平均年齢)` はカーブの比しか取らないので単位が打ち消し合い、千円のままで正しい答えが出ていた。

2点モデルは `C(22) + (平均給与 − C(22)) × …` とカーブの値を**給与そのものと足し引きする**ので、揃えないと1,000倍ずれる。型はどちらも `number` なので型チェックでは捕まらない。

対策として `curve.ts` に `curveValuesInYen` を置き、`estimateSalary` の docstring に「`curveValues` は `avgSalary` と同じ単位（円）で渡すこと」と明記した。`rank.ts` は1,867行ぶん配列を作り直さないよう、産業大分類ごとに1本だけ変換して `Map` で使い回す（産業は17系列しかない）。

## 単調性は保証しない（テストで踏んだ）

「目標年齢が上がれば推定も上がる」を全社で固定しようとして落ちた。原因は**産業カーブ自体が下がる区間を持つ**こと。

| 産業 | 下がる区間 |
| --- | --- |
| 鉱業 | 42歳 7,113千円 → 47歳 6,627千円 |
| 金融業・保険業 | 47歳 7,876千円 → 52歳 7,841千円 → 57歳 7,587千円 |
| 運輸業・不動産業・複合サービスなど | 47〜57歳のどこかで下がる |

推定はカーブに忠実に従っているだけで、**旧式でも同じ挙動**。モデルの変更で入った性質ではない。テストのほうが誤りだったので、保証される性質「カーブの値が上がれば推定も上がる」に置き換えた（`salary.test.ts`）。

## `/about` の書き換え

3つのセクションを書き換えた。

**補正の式** — 式が2本になったので、目標年齢が平均年齢より下か上かで分けて示す。実例（みずほ銀行・35歳）は、**途中の値を小数第1位まで出す**。万円に丸めた値どうしで引き算すると読者の電卓が756万円になり、表示している755万円と1万円食い違う（U7で同じ罠を踏んでいる）。`formatManYen1` を足し、「本文に出した桁で計算しても表示と同じ万円になる」ことを Unit テストと E2E の両方で固定した。

**「年齢スイッチは同業種内の順位を動かしません」→「年齢スイッチで順位はほとんど動きません」** — 旧式では業種内の順序が完全に不変で、その理由（目標年齢が約分で式から消える）まで書いていた。2点モデルでは平均年齢が違う会社どうしで入れ替わりうる。実測して `sameIndustrySwapPercent`（同業種ペアの1.7%）を本文に出す。**intent.md が「隠さない」と決めて書いた性質なので、売り文句を増やす方向に書き換えない。**

**この方法の限界** — 「若い側が過大」という項目は解消したので消し、代わりに2つ足した。

1. **22歳の水準を業種平均と置いている** — 会社ごとの開き（中央値1.22倍・最大4.32倍）が22歳では無いと仮定していること、初任給が業種平均より高い会社では今度は**低めに出る**ことを書く
2. **平均年齢より上は倍率一定のまま** — 60歳時点の最大値（キーエンス2,213万円）を数字で出し、直すだけの根拠を持っていないと書く

あわせて、U7から残っていた記述の誤りを1つ直した。「カーブは**会社間の差**から作っています」「平均年齢の高い会社ほど年収も高いという会社をまたいだ関係を年功カーブと読み替えている」と書いていたが、カーブの出どころは賃金構造基本統計調査の**産業×年齢階級別の労働者の平均**であって、会社をまたいだ関係ではない。「ある時点の労働者の断面であり、同じ人の軌跡でも1社の中の軌跡でもない。中途入社を含むぶん、同じ会社に勤め続けた場合より傾きが緩い」に書き換えた（緩いことは、却下した標準労働者カーブとの比較で実測している）。

## `sameIndustrySwapPercent` の計算

同業種の全ペア（96,469組）× 8つの目標年齢を総当たりする O(n²)。計算方法ページは静的プリレンダーでビルド時に一度だけ実行されるので問題にならない。各社の8年齢ぶんの推定を先に配列にしてから比較する。

## パイプライン側の追随（Issue #46）

**当初「EDINETキーが無いとCSVを再生成できない」と見立てていたが、これは誤りだった。** `salary35` は `avg_salary` / `avg_age` / `industry` だけから決まり、3つとも既にCSVに入っている。有報を取り直さなくても派生列だけ計算し直せる。

`unified.py` に `rebuild_derived()` を切り出し、EDINETから取り直す経路（`build()`）と既存CSVを式に追随させる経路（`--from-csv`）の両方が同じ関数を通るようにした。式が2箇所に分かれると片方だけ直して静かに食い違う。

```bash
cd pipeline/salary35 && python3 unified.py --from-csv ../data/ranking_unified_2026.csv
cd pipeline && npx tsx scripts/build-data.ts --out ../web/public/data
```

### 実装中に踏んだこと

**Pythonがwebと別のカーブを読んでいた。** `curves.py` は `annual_curves.json` を自分の隣（`salary35/`）だけ探していたが、リポジトリに入っている・build-data.ts が読んでいるのは `pipeline/data/annual_curves.json` のほう。ファイルが見つからず、フォールバックのハードコード定数 `INDUSTRY_CURVES`（**所定内給与＝月額・賞与を含まない**）が黙って使われていた。最初の再生成でキーエンス2,178万に対し三菱商事1,310万（web は1,578万）と出て気づいた。`pipeline/data/` を先に探すよう直し、理由をコメントに残した。

**丸めが言語で違う。** Python の組み込み `round()` は偶数丸め、JavaScript の `Math.round` は0.5切り上げ。1円ずれる可能性があるので Python 側は `floor(x + 0.5)` を使う。

### 列の変更

- `factor` — 若い側は倍率で表せないので、**実際に掛かった比率 `salary35 ÷ avg_salary`** に意味を変えた
- `salary35_fit` — 落とした。データ自身から局所線形回帰で引いたカーブでの参考値だったが、そのカーブは26〜55歳でしか定義されておらず22歳のアンカーを持てない。ADR-0005 に対応する定義が無く、web も読んでいない
- `rank_adj` / `rank_delta` — 新しい `salary35` から振り直し。行順も `rank_adj` 順に並び直るので、CSVの差分は全行になる

### 照合テストを本物に繋いだ

`pipeline/scripts/build-data.test.ts` は、式を書き写すのではなく **`web/features/ranking/lib/salary.ts` の `estimateSalary` をそのまま import して** CSV の `salary35` と全1,867社で突き合わせる。書き写すと web 側の変更を取り逃す。目標年齢を35から36に変えて全1,867社で落ちることを確認済み（テストが空回りしていないことの確認）。

ADR-0003 が求めていた「補間の実装は Python 側と一致させる」を、式が複雑になった後も保つための線がこれになる。
