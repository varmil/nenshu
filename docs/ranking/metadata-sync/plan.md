# U16 表示状態とメタデータの同期 — plan.md

Issue: [#135](https://github.com/varmil/nenshu/issues/135)（親 [#130](https://github.com/varmil/nenshu/issues/130)）
仕様: `docs/ranking/spec.md` AC-16（AC-7・AC-9・AC-15 も参照） ／ 分解: `docs/ranking/overview.md` U16
関連: ADR-0006（公開URL戦略）・ADR-0007（表示基準）

着手前の段取り。出来上がりの構造は design.md に書く。

## 手順

1. **報告の前提を先に検める。** 親 Issue は「`/?age=40` のタイトルが実測値のものになっている」と読める。**サーバーが返す生のHTMLを `curl` で見て、SSR のメタデータが本当に間違っているのかどうかを確かめる**——ここが違うと直す場所が丸ごと変わる（文言を書き直す Unit なのか、同期を足す Unit なのか）。8年齢・33業種・`/`・ページ2以降を一通り当たる。
2. **クライアント操作の後を見る。** 実ブラウザで表示基準・業種チップ・並び替え・ページ送り・ヘッダの検索を順に操作し、そのたびに URL と DOM 上の `<title>` / `meta[name="description"]` / `link[rel="canonical"]` を並べて記録する。**1 と食い違うなら、読者が見ているのは DOM の側**である。
3. 企業詳細ページでも同じ手順を繰り返す。**こちらはタイトルに金額が入っているので、食い違いが金額の食い違いとして出る**——壊れ方の重さが違うので分けて記録する。
4. **メタデータの文言を書いている場所を数える。** ランキング・企業詳細・レイアウトの受け皿の3か所を洗い、クライアントから引くにはどれを動かす必要があるかを決める。**書き写して2つ目を作らない**——同じ文言が2か所にあると、片方だけ直した状態に必ずなる。
5. 切り出した純粋関数に Unit テストを書く。**サーバーが `Metadata` として返す値と、クライアントが DOM に書く値が同じ関数から出ていること**を型とテストの両方で押さえる。
6. E2E を書く。**判定は「同じURLを直接開いたときの値と一致するか」にする**——文言をテストに書き写すと、文言を直すたびにテストも直すことになり、そのときテストは何も守らない。**修正前のコードで落ちることを先に確認する。**
7. 型・lint・Unit テスト・E2E をすべて通す。ビルドしてページのサイズが増えていないことを見る（メタデータの同期はクライアントに関数を1つ増やすので、`/` のHTMLとJSの両方を見る）。
8. 実測した値と、直さないと決めたこと（およびその根拠）を design.md に残す。spec に受け入れ基準が無いので AC-16 を足す。
9. PR を出してマージする。

## 検証の順序

- **1（SSR の実測）を終えるまでコードを書かない。** 前提が違えば以降の手順は全部無駄になる。
- Unit テスト（文言を組み立てる純粋関数）→ E2E（実ブラウザでの操作後の DOM）→ 本番ビルドでの手動確認、の順。
- E2E は**修正前に落ちること**と**修正後に通ること**の両方を見る。
- 既存の E2E 全件が緑であること。とくに次の2つを壊していないこと。
  - `e2e/seo.spec.ts` — canonical の寄せ先（ADR-0006 の1,910 URL）は動かさない
  - 「操作でネットワークリクエストが発生しない」（AC-7）— DOM を書くだけで、ルーターを経由しない
