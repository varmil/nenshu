## 実施順序

```
U0 ─┐
    ├─→ U2 ─→ (U3, U4 は並列) ─→ U5 ─→ U6
U1 ─┘   └─→ U7（独立して進められる）

（company施策の C0 → C1）─→ U8
```

U0 と U1 は互いに独立なので先に片付ける。U2 が通れば施策として最低限の価値が出る。

**U8 は Bolt 1 の後に足した Unit で、company 施策の C1 に依存する**（sitemap に企業詳細ページ1,867件のURLを載せるため）。

**U9・U10 は Bolt 1 の途中・直後に、当初の分解に無かった Unit として足した**（U9 は U5 のあと、U10 は U7 のあと）。どちらも `docs/ranking/<unit>/` に plan.md・design.md を持つ Unit なので、後からこの一覧に登録した。Unit 一覧に無い Unit を作らないための運用は CLAUDE.md の「Unit の起票（着手前）」にある。

**U11 は Bolt 2 で足した Unit で、company 施策の C1 に依存する**（企業詳細ページにも同時に適用するため）。

**U12 は U11 の上に積む。** 表示基準が2モードあることを前提にレイアウトを組む（年収バーの基準も偏差値の母集団も基準ごとに別）ので、U11 が入る前には作れない。


## U11 実測値モードと既定化

サイトが既定で見せる数字を、年齢補正後の推定年収から**有報の平均年間給与そのまま**に変える（ADR-0007）。表示基準は「実測値」と「年齢そろえ」の2モードで、**URL の `age` の有無がモードを表す**。

**ranking 施策の Unit だが、企業詳細ページ（company 施策）も同じ PR で変える。** 既定の表示基準が2ページで食い違う期間を作らないため。`docs/company/overview.md` にも追記する。

Claude Design `改善案.dc.html`（Issue #21）のアートボード 5a / 5b / 5c に対応する。同じデザインのレイアウト刷新は U12（ランキング）と C2（企業詳細）に分けてある。

## U12 ランキングのレイアウト刷新

Claude Design `改善案.dc.html`（Issue #21）のアートボード 4a（PC）/ 2a（モバイル）/ 5a・5c（実測値モード）に対応する。U11 で表示基準の中身を入れ替えたので、U12 は器を入れ替える。

足す機能は spec.md 1.10〜1.12（並び替え・年収バー・偏差値列）。加えてレイアウトを PC 2カラム（左に絞り込みサイドバー）に組み替え、行を高密度化する（Issue #41・#24 がここで解消する）。

**施策を跨いで触るもの。**

- **共通ヘッダへの検索の統合** — `features/navigation/components/SiteHeader.tsx` は site-chrome 施策のもの。`docs/site-chrome/overview.md` に追記する
- **業種チップ（33件）** — U8 が計画しているリンクハブと出すものが同じ。**U12 で先に出し、U8 は canonical・sitemap・robots に絞る**（下の U8 の節を参照）
- **`design-system/ui/` に `sheet` が無い** — モバイルの絞り込みパネルに要る。在庫にないものはその場で作らず起票する（CLAUDE.md）。Issue #79

## 共有コンポーネント

**絞り込み状態（`useRankingState`）** — U3・U4・U5 が同じ状態を触る。目標年齢・4つのフィルタ・検索語・表示件数を1か所で持ち、派生値（絞り込み後の行と順位）を導出する。

3つの Unit が衝突する唯一の箇所なので、**U2 の設計時にこの状態の形を確定させ、設計承認を厚く取る。** U3 以降は状態の形を変えずに項目を足すだけで済ませる。ここが割れると3 Unit ぶんの手戻りになる。

**推定年収の表示コンポーネント** — 金額の書式（万円・カンマ区切り）と、推定であることを示す表記を1か所に閉じる。同じ書式が表・カード・ページ見出しに散らないようにする。

## 昇格の判断

`features/ranking/components/` に置くものが既定。複数の施策から使うものだけ `design-system/components/` へ昇格させる。Bolt 1 の時点では昇格させない。データテーブルは Bolt 2 で企業詳細・業種ページを作る段階で、共通化するか判断する。

## U8 検索エンジン向け導線

ADR-0006 で決めたインデックス戦略を実装する Unit。

- `app/sitemap.ts` — `/`・`/about`・`?age=`8件・`?ind=`33件・`/company/[id]`1,867件（約1,910 URL）
- `app/robots.ts`
- `/` の `generateMetadata` — searchParams から title・description・canonical を組み立てる。`?age=N` のみと `?ind=X` のみは自己canonical、`?age=N&ind=X` は `/?age=N` へ、`emp`・`ten`・`aage`・`q`・`page` を含むURLは `/` へ寄せる
- リンクハブ — **U12 で業種33件のチップを出すので、U8 では作らない。** 年齢8件ぶんが U12 の年齢スイッチで出ているかを確かめ、足りなければそこだけ足す
- `metadataBase` を1か所に閉じる（独自ドメインが未決のため。spec.md 5.）

## Bolt 2 以降

**`/age/[age]`・`/industry/[industry]` は作らないことに決めた（ADR-0006・Issue #49）。** U5 の設計時にパスを確定させていたが、ADR-0004 のフルSSR移行によって `/?age=25` を直接開いてもサーバーが絞り込み済みのHTMLを返すようになり、「パスにしなければクロールできない」という前提が消えた。Google のファセットナビゲーション指針もパスとクエリを区別せず、推奨するのは「個別アイテムのページ＋フィルタ無しの一覧1枚」で、41枚ぶんの実装を作る対価に見合わない。代わりに U8 でクエリURLに canonical と sitemap を与える。

企業詳細ページ `/company/[id]`（1,867枚）は作る。**ID は 証券コード／EDINETコード に変える**（ADR-0006）——現行の書類ID由来のIDは毎年の有報提出で変わるため。施策としては `docs/company/` に独立している（`docs/product/product.md` の施策マップ）。

その先（平均年収の10年推移・株価・信用格付け）は `timeseries`・`market-data` 施策として別に扱う。
