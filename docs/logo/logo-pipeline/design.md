# design.md — L0 ロゴの調達パイプライン

Issue: [#109](https://github.com/varmil/nenshu/issues/109)
仕様: `docs/logo/spec.md` 1.／決定: `docs/adr/0008-company-logo-sourcing.md`

出来上がりの内部構造。作業の順序は `plan.md` にある。

## ディレクトリ

```
pipeline/
  scripts/
    build-logos.ts            実行の入口（npm run build:logos）
    build-logos.test.ts       ネットワークに出ない部分の単体テスト
    lib/logo/
      houjin.ts               EDINETコード → 法人番号
      wikidata.ts             法人番号 → 項目・P154・P856（SPARQL）
      gbiz.ts                 法人番号 → company_url（gBizINFO）
      commons.ts              Commons API（実寸・ライセンス・作者・原寸URL）
      site.ts                 公式サイトのHTMLから候補を集める
      candidates.ts           候補の型と優先順の決定（純関数）
      image.ts                取得したバイト列の判定と正規化（sharp）
      fetcher.ts              HTTP。UA・タイムアウト・再試行・並列制御・キャッシュ
  logo-cache/                 gitignore。生バイトと索引の中間結果
    index.json                 工程2の結果（Wikidata・gBizINFO）

```

**`pipeline/` の中で完結し、`web/` のコードは1行も変えない。** 出力先だけが `web/public/` にある（`build-data.ts` と同じ形）。

                                                                        │          │

                                                                        │          │
                                        公式サイトのHTML ────────────────┘          │

                                    候補（4種・優先順つき）───────────────────────────┤
                                                                                    ↓

                                                                                    ↓
                                                              画像として検める（壊れたものを落とす）
                                                                                    ↓

                                                                                    ↓

## 候補の型と優先順

```ts
type LogoSource = "commons" | "jsonld" | "header" | "icon";

type Candidate = {
  source: LogoSource;
  url: string;
  /** 宣言されたサイズ（`sizes` 属性・manifest の `sizes`）。実寸ではない */
  declared?: { w: number; h: number };
};
```

優先順は **`commons` → `jsonld` → `header` → `icon`** で固定する。同じ `source` の中では**宣言サイズの大きいものを先に試す**（`apple-touch-icon` が `favicon.ico` より先に来る）。

**「先に取れたものを採る」であって「一番大きいものを採る」ではない。** 出典の確からしさを解像度より優先する——ヘッダのロゴは間違いなくその会社のロゴだが、大きいアイコンは提携先やキャンペーンの画像であることがある。

## 何を「壊れている」と見なすか

`image.ts` の判定。**解像度では落とさない**（ADR-0008 決定3）。

| 落とす条件 | 理由 |
| --- | --- |
| 画像として読めない | HTMLエラーページ・JSONを掴んだ場合。**HTTP 200 で返ってくる**（CLAUDE.md の EDINET 429 と同じ形） |
| 幅または高さが 2px 未満 | トラッキング用の 1x1 |
| 全画素が同色（不透明部分） | 読み込みプレースホルダ |
| 不透明な画素が全体の 0.5% 未満 | 実質透明の飾り |
| 縦横比が 20:1 を超える | 罫線・区切り画像 |

## 正規化

`sharp` で行う。**`sharp` は `web/node_modules` に既にある**（Next.js の依存）が、`pipeline/package.json` に明示的に足す——依存は使う側が宣言する。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 形式 | WebP（アルファ保持・quality 82） | 1ファイル20KB以下（AC-6）に収めるため。**SVG をそのまま配らない**（ADR-0008 決定2） |
| 高さ | 128px に統一（元が小さければ拡大しない） | 表示は最大60px。ラスタで足りない会社はそのまま小さく残り、**実寸が索引に残るので後から判定できる** |
| 幅 | 高さに従う。512px を超える場合は幅512pxに収める | 20:1 までの横長を許すため |
| 余白 | 透明・単色の余白をトリムしてから収める | 器の中で大きさが揃わないため |

**SVG は高さ256pxでラスタライズしてから128pxに縮める。** 直接128pxで描くと細い線が飛ぶ。

## 索引の形（`logos.json`）

```jsonc
{
  "meta": {
    "generatedAt": "2026-08-21T...",
    "count": 1867,          // 母集団
    "withLogo": 0,          // ロゴを持つ会社
    "bySource": { "commons": 0, "jsonld": 0, "header": 0, "icon": 0 },
    "missReasons": { "noUrl": 0, "fetchFailed": 0, "noCandidate": 0, "allRejected": 0 }
  },
  "byId": {
    "6861": {
      "w": 320, "h": 57,            // ★元画像の実寸（正規化後ではない）
      "src": "commons",
      "from": "https://commons.wikimedia.org/wiki/File:...",
      "lic": "Public domain",       // commons のみ
      "by": "…",                    // commons のみ・帰属が要るとき
      "attr": true                  // 帰属表示の対象か
    }
  }
}
```

**元画像の実寸を持つのがこの索引の要点である。** 「短辺◯px未満は頭文字に戻す」を**再取得なしで**決め直せる（ADR-0008 決定3）。正規化後のサイズは全社128px高で同じなので持たない。

**画像のURLは索引に持たない。** 企業IDから `/logos/<id>.webp` で引ける。`from` は出典の表示（AC-14）用で、表示側のホットパスでは使わない。

### 表示側が読む量

**`/` は `logos.json` を丸ごとは読まない。** 1,867社ぶんの索引をクライアントに渡すとページの予算（AC-13）を超える。L1 が必要とするのは「ロゴの有無」と「縦横比」だけなので、**`companies.json` の行と同じ並びの数値配列1本**に畳んで渡す（縦横比×10 の整数、ロゴが無ければ0）。**畳む処理は L1 の担当**で、L0 は索引を出すところまで。

## HTTP の作法（`fetcher.ts`）

| 相手 | 並列 | 間隔 | 備考 |
| --- | ---: | --- | --- |
| Wikidata SPARQL | 1 | 1秒 | 300件/クエリで7回 |
| Commons API | 1 | 0.3秒 | 50件/クエリ |
| gBizINFO | 3 | — | URLが無い263社のみ |
| 公式サイト | 4 | — | 1社あたり最大6リクエスト |

- `User-Agent` に用途と連絡先を入れる
- タイムアウト15秒・再試行1回。**再試行しても失敗したらその会社を諦める**（1社の欠損より全体が止まらないことを優先）
- **応答の中身を必ず検める。** `Content-Type` を信用しない（EDINET の件）
- 取得したバイト列は `logo-cache/raw/<sha1>` に置く。**2周目以降はここから読む**

## 配信

`web/public/_headers` に `/logos/*` の1行を足す。**Worker を経由しない静的アセットなので、`next.config.ts` の `headers()` では設定できない**（`_next/static/*` と同じ事情。CLAUDE.md）。

```
/logos/*
  Cache-Control: public, max-age=604800, stale-while-revalidate=2592000
```

**`immutable` にはしない。** ファイル名が企業IDで内容ハッシュを含まないため、年1回の再取得でロゴが変わったときに古い画像が残り続ける。1週間で取り直し、その裏で30日ぶんは古いものを出してよい、という設定にする。

## テスト（`build-logos.test.ts`）

ネットワークに出ない部分だけを固定する。

- HTMLの断片から候補を集める（JSON-LD・ヘッダの `<img>`・`<link rel=icon>`・manifest）
- 候補の優先順（`commons` が `icon` より先／同じ `source` では宣言サイズの大きい順）
- 相対URLの解決と、gBizINFO の深いパスからオリジンへの正規化
- ICO のヘッダから最大サイズを読む
- 「壊れている」判定（1x1・単色・縦横比20:1超）
- 索引の形と AC-1〜AC-6 の検証関数

**1,867社を1周させるテストは書かない。** 30〜40分かかるうえ、外部サイトの状態で結果が変わる。

## 1周目の実測（2026-08-21）

| | 結果 |
| --- | ---: |
| **ロゴを持つ会社** | **1,636 / 1,867 = 87.6%** |
| 出典の内訳 | ヘッダ 872・**Commons 441**・アイコン 202・構造化データ 121 |
| 落ちた理由 | URLが無い 115・候補が無い 85・全部落ちた 31 |
| 画像の合計 | 8.9MB（1枚平均 5.5KB・最大 18.4KB） |
| `logos.json` | gzip 41.7KB |
| 元画像の短辺 | 中央値 77px・32px未満が146件・48px未満が429件 |
| 元画像の縦横比 | 中央値 3.69・2.0超が1,129件・正方形付近が230件 |

**見込みの75〜85%を上回った。** 効いたのは、途中で見つけた2つの取りこぼしを直したことである。

### 見つけた取りこぼし1: 単色のロゴを「空の画像」として捨てていた

読み込みプレースホルダを弾くつもりの「全画素が同色なら捨てる」が、**1色のワードマークを片端から落としていた。** Commons のロゴは1色のSVGが大半で、**522社ぶん持っていたのに190社しか使えていなかった**（三井物産・伊藤忠・丸紅・野村…が軒並み落ちていた）。

判定を「**全面が不透明で、かつ1色**」——塗りつぶしの矩形だけ——に直した。透明部分があるなら、単色でもそこに形がある。

これで到達率は 75.5% → 81.8% になった。

### 見つけた取りこぼし2: sharp は ICO を読めない

`favicon.ico` を渡すと `metadata()` が投げる。**「画像として読めない」に分類していたので、ICO しか置いていないサイトが丸ごと落ちていた**（`notImage` 122件）。

`icoToImage` を足した。ICO のディレクトリから面積が最大のエントリを採り、

- 中身が PNG ならそのまま切り出す（大きいエントリはたいていこれ）
- BMP（DIB）なら手で開く。**ICO の DIB は AND マスクを含むので高さが2倍で入っており、行は下から上に並ぶ。** 32bpp と 24bpp だけ扱う——それ未満はパレット式で、実質16px級しか無い
- 32bpp でもアルファが全て0のことがあるので、その場合は不透明として扱う

これで 81.8% → 87.6% になった。

### 残り231社の内訳

| 理由 | 件数 | 中身 |
| --- | ---: | --- |
| URLが無い | 115 | Wikidata にも gBizINFO にも公式サイトが無い。**現状ここに届く手段が無い** |
| 候補が無い | 85 | サイトは取れたが、ロゴらしき画像もアイコンも1つも見つからない |
| 全部落ちた | 31 | 404 が41・429 が9・画像でないものが10 |

**取得の失敗はキャッシュしていないので、走らせ直すたびに少しずつ回収される**（429 と一時的な失敗のぶん）。実際、同じコードで2回目を回すと15社増えた。

### 表示側（L1）への申し送り

- **短辺48px未満が429件ある**（32px未満は146件）。ADR-0008 決定3のとおり一旦すべて載せてあるので、**見てから閾値を決める**。実寸は `logos.json` の `w`・`h` にある
- **縦横比の中央値は3.69。** 正方形付近は230件しかない。器を横長にする判断（決定4）は実データでも裏付けられた
- **地の色が問題になる。** ロゴは透明背景で、ダークモードでは濃い色のワードマークが沈む。器の側で明るい地を敷くかどうかは L1 で決める

## 公開後に直したもの（2026-08-23）

企業ページ `/company/4674`（クレスコ）に **X（旧Twitter）のロゴ**が出ていた、という指摘から。

### ヘッダの `logo` を名前に持つ画像は、その会社のロゴとは限らない

クレスコのサイトには `<header>` が無いので先頭60,000文字を見る。その範囲に SNS リンクの帯（42,758文字目）が入っており、**X のアイコンのファイル名が `logo-black1.png` だった。** 本物のロゴは58,616文字目にあり、先に見つかったほうが採られた。

「`logo` を名前に持つ `<img>` だけを採る」という絞り込みは**名前しか見ていない**ので、SNS アイコンのファイル名に `logo` が入っていれば通ってしまう。名前の代わりに、**囲んでいる `<a>` の行き先**で仕分けるようにした（`headerLogos`）。

| 行き先 | 扱い | 理由 |
| --- | --- | --- |
| SNS（`SOCIAL_HOSTS` の20ドメイン） | **捨てる** | 後ろへ回すだけでは、他の候補が全部落ちたときに自社ロゴとして出る |
| いま見ているページ自身、またはトップらしいパス | 先に試す | ヘッダのロゴはトップへ戻るリンクになっている |
| それ以外（下層ページ・リンクの外） | 後で試す | 関連サービス・関連会社のロゴがここに来る |

**「自サイトではない」を捨てる理由にしない。** コニカミノルタ（4902）は CDN 配信の HTML から `kmbs.konicaminolta.us` へリンクしており、別ホストというだけで捨てると本物のロゴを落とす。捨てるのは一覧に載っている SNS のホストだけにした——**一覧に無いものを捨てない**、が線である。

**公式サイトの URL は深いことがある。** KDDI の P856 は `https://www.kddi.com/english/` で、パスの形だけでトップを判定すると `/english/` は通らない（言語コードとしては長い）。その結果、`https://povo.jp/`（別サイトのトップ）のロゴが先に来ていた。**ベース URL 自身を指すリンクもトップとして扱う**（`samePage`）ことで直る。

### 直さなかったもの: 明るい器で見えない白いロゴ

ユニバンス（7254）のヘッダのロゴ（`logo.svg`）は**白**である。構造で仕分けると正しくこれが1位に来るが、当サイトの器は `--logo-surface` の明るい面を敷く（ADR-0008 決定4）ので沈む。いま出ている `logo-black.svg` はローディング画面の中にあり、構造としては「リンクの外」だが、**読者から見えているという一点で勝っている。**

これは**別の症状**である。ロゴの選び方ではなく、`image.ts` の「壊れている」判定に「明るい器で見えない」を足すかどうかの話で、ADR-0008 決定3の「取れたものは一旦すべて載せ、明らかにおかしいものを見てから頭文字に戻す」がまさに指しているもの。デンカ・石川製作所も**同じ理由で真っ白な画像を配っていた**（今回は別の候補に替わって直ったが、原因は残る）。[#156](https://github.com/varmil/nenshu/issues/156) として別に扱う——**下の「公開後に直したもの2」で片付けた。**

### 1社だけ取り直す（`--only`）

`--limit N` は先頭 N 社を対象にするので、**1社を直すのに使うと `pruneOrphans` が残り1,866社の画像を消す。** `--only <ID,…>` を足した。

- 既存の `logos.json` を読み、**そこへ上書きする**。全周の結果を捨てない
- `pruneOrphans` を呼ばない
- `meta.count`・`missReasons`・`rejectReasons` は前回の値を残す。**母集団ぜんぶを回して初めて意味を持つ数**だから
- 取れなかった会社は既存の記録を残し、警告を出す。消すと「直しに来たはずが画像を1枚減らして帰る」ことになる
- 索引のキャッシュは `index-partial.json` に分ける。全周のキャッシュに1社ぶんを被せると、次の全周が索引を引き直すところから始まる

## 公開後に直したもの2: 明るい器で見えない白いロゴ（2026-08-24・[#156](https://github.com/varmil/nenshu/issues/156)）

上の「直さなかったもの」に置いた症状。器の地は `--logo-surface` の明るい面で固定してあり（ライトは白、ダークも `oklch(0.93 …)`）、**白いロゴを置くとどちらのモードでも空白のマス目になる。**

### まず数えた: 50枚 / 1,636枚（3.1%）

閾値を決める前に、配っている画像を走査した（再取得は要らない）。**明るい器に重ねてインクが1画素も乗らない画像が50枚あった。**

出典は **49枚がサイトのヘッダ・1枚が JSON-LD** で、URL がそのまま理由を語っている——`logo_w.svg`・`logo-header-white.png`・`logo_wht.svg`・`toppan_logo_white-wm-signed_v2.svg`。**濃いヘッダに載せるための白抜き版**を、構造だけを見て1位に採っていた。

被覆率（インクの画素の割合）で見ると境目がはっきりしている。

| 被覆率 | 枚数 |
| --- | ---: |
| 0.00% | 44 |
| 0.09〜0.27% | 6 |
| **（ここに空きがある）** | |
| 2.26%以上 | 残り1,586枚すべて |

**1%を境にすれば、迷う画像が1枚も無い。**

### 判定は「明るい器に重ねてから」見る

`blankOnLight`（`lib/logo/image.ts`）。不透明度を掛けて白（#fff）に重ねた値の最小チャンネルが 234 以下の画素を「インク」と数え、**インクが全体の1%未満なら空白と見なす。**

- **重ねてから見るのが要点。** 生の RGB だけを見ると、薄いアルファの乗った白い画素も「白」と数えられてしまい、逆に色の付いた縁は残る——という都合のよい話にはならない。重ねる計算にすると、薄い黒（重ねれば灰色のインク）と薄い白（重ねても白）が正しく分かれる
- **色の付いた縁を持つ白抜きロゴは残る。** 縁がインクとして数えられるため。落ちるのは「重ねても何も現れない」ものだけ

### `reject` の24×24走査には相乗りさせなかった

Issue の見立てでは既存の走査に足せるはずだったが、**そこでは足りなかった。同じ50枚を24×24で数えると23枚しか挙がらない。**

理由は2つある。**縮小の平均化が細い線を白へ寄せる**のと、**アルファを戻す計算が低アルファの画素に暗い値を作る**（実測で `(127,127,127,23)` のような画素が現れ、これがインクとして数えられて「白くない」と判定される）こと。

代わりに、**`normalize` を通した後の画像＝配るものそのもの**を見る。判定と配るものの間に加工を挟まない。高さ96pxに収まっているので縮小も要らず、走査は原寸のままでよい。

`pick` の中では**画質を落として入れ直す前に**見る——白いことは画質と関わりが無いので、落として入れ直しても結論は変わらない。

### `--only` は「取り直した結果で置き換える」に直した

`--only` は取れなかった会社について前回の記録を残す（「直しに来たはずが画像を1枚減らして帰る」のを避けるため）。**この規則のままだと、白いロゴを直しに来た50社のうち代わりが見つからない会社は、白いロゴをそのまま置いて帰ることになる。**

残す条件を足した。**残すのは、いま配っている画像がいまの判定を通るときだけ。** 通らなければ記録と画像を消し、頭文字に戻す。判定を厳しくしたあとで `--only` を回せば、対象社の古い画像は必ず片付く。

### 結果

50社を `--only` で取り直した。

| | 社数 |
| --- | ---: |
| **別の候補に替わった** | **39** |
| **代わりが無く頭文字に戻した** | **11** |

替わった39社の中身は、同じサイトの色付き版（`logo.png`・`logo_blue.svg`・`logo_st.png`）・favicon / apple-touch-icon・Commons（ブラザー工業・TOPPAN）である。**39枚すべてを目で見て、読める図が出ていることを確かめた。**

| | 直前 | 直後 |
| --- | ---: | ---: |
| ロゴを持つ会社 | 1,636 / 1,867 = 87.6% | **1,625 / 1,867 = 87.0%** |
| 出典の内訳 | ヘッダ 870・Commons 442・アイコン 203・構造化データ 121 | ヘッダ 832・Commons 444・アイコン 228・構造化データ 121 |
| 画像の合計 | 8.9MB | 8.8MB |
| `logos.json` | gzip 41.9KB | gzip 41.5KB |

**到達率は0.6ポイント下がる。** 空白のマス目を「ロゴが出ている」と数えていたのをやめたので、下がるのが正しい。読者から見れば11社が空白から頭文字に変わっただけで、減ってはいない。

ユニバンス（7254）は今回も触っていないが、**構造で選び直しても白いロゴは判定で落ちる**ので、次の全周でいまの `logo-black.svg` に落ち着く。

### 見張りはリポジトリ側に置く

判定を足すのは安いが、**足す前に配ってしまったものは判定では消えない**（現にこの50枚がそうだった）。パイプラインを回すのは年1回なので、`build-logos.test.ts` が `web/public/logos/` の全画像を走査し、空白に見えるものが1枚でもあれば落ちるようにした（1,625枚で約1秒）。

## 公開後に直したもの3: 会社ごとの候補の指定（2026-08-26・豊田通商）

運営者から「豊田通商（8015）のロゴが変」という指摘。器の中でロゴが上に寄り、下に大きな余白が出ていた。

### 原因は候補の選び方で、加工ではない

採っていたのは英語版サイトの JSON-LD の `Organization.logo`（`…/english/app-files/img/symbol/logo.png`）で、**1200×630 の共有用の絵**だった。ロゴは上端の帯にしか無く、残りは白から薄いグレーへのグラデーションの余白である。

**`normalize` の `trim` はこの余白を落とせない。** `sharp` の `trim` は左上の画素を地として単色の縁だけを削るので、グラデーションには効かない（実測で 1200×630 → 323×96 までは詰まるが、下の75%は余白のまま残る）。

**Wikidata の公式サイト（P856）が英語版を指していることが効いている。** 候補は英語版のページから集まるので、日本語版の意匠は最初から候補に入らない。英語版ヘッダの `TOYOTA TSUSHO CORPORATION` は 3828×192＝19.9:1 で、88×50 の器に入れると読めない（`MAX_RATIO` の 20 はぎりぎり通る）。

### 余白の割合で機械的に落とす線は引けなかった

「明るい器に重ねたインクの外接矩形が、画像に対して小さすぎるものを落とす」を配っている2,509枚で測った。

| インクの外接矩形の面積比 | 枚数 |
| --- | ---: |
| 0.5 未満 | 52 |
| 0.9 未満 | 112 |
| （分位）1% 0.26 ・ 5% 0.93 | |

**52枚の大半は正しいロゴだった。** 薄い色のワードマークを持つロゴ（5903・7035 など）は、`blankOnLight` のインク判定（明るい器に重ねて 234 以下）に文字が掛からないので外接矩形が過小に出る。8015（0.114）と同じ帯に並ぶ。

自前の余白トリム（行・列の明度レンジで地を判定して削る）も試した。8015 は 544×85 まで正しく詰まるが、**横縞の色帯で組んだロゴ（6543）を削り落とす**——行の中が単色である点が余白と同じだからである。隣り合う行の色の連続性を条件に足すと 6543 の全滅は避けられるが、それでも 2,509枚のうち217枚の寸法が変わる。**1社の指摘に対して217枚を動かす変更で、確かめる術がない。**

### 「この候補を使う」という指定を1つ持つ

`candidates.ts` の `PINNED` に会社ID → 候補を書き、`prioritize()` が `sortCandidates()` の結果の先頭に置く。8015 は日本語版ヘッダの `cmn_logo01.svg`（680×107）を指す。

- **判定（`image.ts`）で選び直せないものだけを置く。** あちらが落とすのは「壊れている」と「明るい器で消える」の2つで、**「絵としては正しいが、この器に置くロゴとしては不適当」はどちらにも当たらない**
- **指定として持つのは、次の全周でも同じ結論を再現するため。** `web/public/logos/` の画像を手で置き換えると、取り直した瞬間に元へ戻る
- **候補が1件も集まらなくても指定は試す。** 公式サイトが読めない年でも、指定した1件だけは取りに行く
- **書くのは絶対URL。** 候補は `absolute()` を通った絶対URLで届くので、相対で書くと1つも一致しないまま「効いている」ように見える（テストが形を検める）

### 結果

`npm run build:logos -- --only 8015` で取り直した。出典は `jsonld` → `header`、記録の実寸は 1200×630 → 680×107、画像は 1,560B → 7,624B（上限20KB）。ロゴを持つ会社は 2,509社のまま変わらない。

**同種のものが他にもある。** 上の52枚には、白いワードマークが横に伸びて明るい器では消えている画像（3329・6677 など）が混ざっている。`blankOnLight` はインクが1%以上あれば通すので、シンボルだけが見えて残りが空白のまま配られている。**この Unit では触っていない**——1社の指摘に対する修正なので、まとめて見直すなら別に起票する。

## 公開後に直したもの4: シンボルだけが見えて残りが沈んでいるロゴ（2026-08-26・[#221](https://github.com/varmil/nenshu/issues/221)）

上の「公開後に直したもの3」が末尾に残した宿題。**`blankOnLight` はインクが1%以上あれば通すので、シンボルが見えていればワードマークが全部白くても配られる。**

### まず51枚を目で見て仕分けた

「明るい器に重ねたインクの外接矩形が、画像の半分未満」で候補を切り出すと51枚（2,509枚中2.0%）。**1枚ずつ、明るい器と濃い地に並べて描いて仕分けた**——濃い地に置くと、明るい器で消えているものがそのまま現れる。

| 仕分け | 枚数 |
| --- | ---: |
| **白いワードマークが沈んでいる** | **31** |
| 問題なし（正方形のアイコンや白地のカードで、余白があるだけ） | 19 |
| 余白が多いだけ（#220 と同じ型） | 1（8217・オークワ） |

**Issue が3つめに置いていた「淡い色で読みにくいが図としては出ている」は0枚だった。** 5903・7035 を淡いグレーと見立てていたが、隠れている画素の輝度を測ると**平均 251〜255 でほぼ純白**である。線をどこに引くかを決める必要は無くなった。

**8217 は指定（`PINNED`）にしていない。** 白い矩形の左端に「オークワ」が置かれた GIF で、ロゴ自体は欠けずに読める。器の中で左に寄って小さく出るだけなので、#220 の豊田通商（ロゴが上端の帯にしかない）ほどの実害が無い。

### 判定は2つの条件で引ける

31枚と、残る2,478枚とを機械的に分けられるかを測った。**単独の指標では分けられない。**

| 試した指標 | なぜ足りないか |
| --- | --- |
| 外接矩形の面積比だけ | 正方形のアイコン（余白がある）が同じ帯に来る |
| 見えない不透明画素の割合 | **白地のカード**に載ったアイコンが最上位に並ぶ（地が白いのは正常） |
| 見えない画素が縁から透明を通って届くか | 同上。白地のカードの地は縁まで続いている |
| 見えている図から離れた不透明画素 | 白い縁取り（Aiming・亀田製菓）と分かれない |

**`mostlyHiddenOnLight`（`lib/logo/image.ts`）は2つを見る。**

1. **描かれている図に対して、見えている図がどれだけか**（`VISIBLE_MIN` = 0.5）。インクの外接矩形と、「インクまたは不透明」の外接矩形の面積比を採る。**分母を画像ではなく描かれている図にする**のが要点——画像の寸法は正規化の都合で決まるが、描かれている図の広がりは意匠そのものである
2. **その外側が透明か**（`OUTSIDE_TRANSPARENT_MIN` = 0.4）。透明なら、そこにある不透明な画素は**地ではなく描かれたもの**である

**2つめが要る。** 1つめだけだと、丸い白のカードに載ったアイコン（151A・138A）や、白い矩形の左端に置かれたワードマーク（8217・2961）が落ちる。**白は地であって、沈んだ図ではない。**

**「白い縁取り」「色の中の白抜き」は1つめで残る。** インクが図の全体に及ぶので面積比が下がらない（亀田製菓・Aiming・東和薬品・山形銀行・DIC など実測22枚）。

配っている2,509枚に当てると**目視で決めた31枚とちょうど一致する**（取りこぼし0・誤検出0）。

### `blankOnLight` と重ねない。呼ぶ側は1つから引く

2つの判定は見ているものが違う（まるごと沈む／一部が沈む）ので分けたままにし、**「明るい器に置けない画像か」を `unusableOnLight` の1つに寄せた。** `pick`・`--only` が前回の記録を残してよいかの判断・`build-logos.test.ts` の全画像走査の3か所が同じものを見る必要があるためで、**片方だけに足すと、次の全周で落とすはずの画像を配り続けることになる**（`pick` だけは理由を別々に数えたいので2つを直接呼ぶ）。

**インクが1画素も無い画像は `mostlyHiddenOnLight` では判定しない。** 外接矩形が取れないので、そこは `blankOnLight` の担当である（境目をテストで固定した）。

### 結果

`--only` で31社を取り直した。

| | 社数 |
| --- | ---: |
| **別の候補に替わった** | **29** |
| 代わりが無く頭文字に戻った | 2（6496・中北製作所／5986・モリテックスチール） |

替わった29社の出典は header 12・icon 17 で、**多くは favicon に落ちた**——濃いヘッダ用の白抜き版しか持たないサイトでは、次に確からしい候補がそれになる。ロゴを持つ会社は 2,509 → **2,507社（84.7%）**、画像の合計は 13.09MB → **13.02MB**、`logos.json` は gzip 62.3 → **63.2KB**。

**6496 の apple-touch-icon は 404 を返す**（HTML には書いてあるが実体が無い）ので、頭文字に戻るのが正しい。

### 判定で選び直せない1社を指定に足した

**日本コークス工業（3315）は `logo_w.png`（白）と `logo_b.png`（濃色）を同じディレクトリに並べている。** 構造だけを見ると白いほうが1位に来て、判定で落とすと次の候補は 32×32 の favicon——社名が読めないところまで落ちる。`PINNED` に `logo_b.png` を書いた（291×34、社名が読める）。**「同じ意匠の濃淡2版があり、濃いほうを名指しできる」ときだけ指定にする**、が線である。

### 残った質の低下

**ジーニー（6562）は `AD INSIGHT by GENIEE` という製品のロゴになった。** 公式サイトの企業ロゴは白抜き版しか無く、他にあるのは全部製品のロゴである。会社名（`GENIEE`）は絵の中に入っているので、クレスコに X のロゴが出ていた（#220）ような別の主体ではない。**直していない**——指定で名指しできる企業ロゴがサイトのどこにも無い。

**日本瓦斯（8174）は 16×16 の favicon になった**（他に宣言されたアイコンが無い）。ADR-0008 決定3のとおり解像度では落とさないが、**器の中では拡大されてぼやける**。同じ帯に 8150（48×48）・2411 などがある。

**2社とも直さないと決めた**（2026-08-26・運営者の判断）。**直すと、どちらも「ロゴ」とは言えないものになるため。** 6562 は白抜き版を無理に見せる加工か、製品でない何かの持ち込みになり、8174 に解像度の下限を引けば、その先で出るのは頭文字——**その会社の意匠ではない何かを、意匠の場所に置く**ことになる。**製品のロゴも小さな favicon も、その会社が自分で置いているもの**である点は変わらない（雇用管理区分を統一しないのと同じ線・spec 2.2b）。**次に見直しに来ても、この2社は触らない。**

### 見張りは #156 のものを広げた

`build-logos.test.ts` の全画像走査を `blankOnLight` から `unusableOnLight` に替えた。**判定を足す前に配ってしまったものは判定では消えない**——#156 で50枚、今回31枚が現にそうだった。
