# intent.md — 企業ロゴ

## 狙い

いま社名の左にあるのは**破線の枠に入った社名の頭文字**である（`CompanyLogoMark`）。1,867行のどれも同じ見た目で、目印として働いていない。「三菱商事」を探すのに社名の文字列を読むしかない。

ロゴは**読む前に見つけられる**唯一の要素である。OpenWork をはじめ企業情報を並べるサイトが例外なくロゴを置いているのはこのためで、行の識別だけでなく「一次情報を持っているサイト」という印象にも効く。

親 Issue: [#23](https://github.com/varmil/nenshu/issues/23)。

## North Star KPI

ranking・company 施策と同じ**自然検索からの月間セッション数**。

ロゴ自体は検索順位を動かさない。効くのは**流入後**なので、補助指標として次を見る。

- ランキングから企業詳細ページへの遷移率（行が見分けられれば上がるはず）
- ランキングページの滞在時間

## 仮説

**H1.** 行の識別コストが下がると、ランキングから企業詳細への遷移が増える。

*検証*: 公開前後で、`/` から `/company/[id]` への遷移率を Clarity で比較する。

**H2.** ロゴの有無が半々でも、無い行が「欠け」ではなく「そういう表示」に見えれば減点にならない。

*検証*: 頭文字マークは現状すでに破線の枠で「意図した空き」として設計してある（`CompanyLogoMark` のコメント）。ロゴが載る行と並んだときにそう見えるかを、実装後に実機で確認する。

**H3.** ぼやけたロゴは、無いより悪い。

*検証*: 仮説というより方針。運営者の判断で**解像度の下限を 128px に引く**（2026-08-21）。下限を割るものは載せず頭文字マークに落とす。

## 前提の確認（調査済み・2026-08-21 実測）

### 名寄せキーは既に手元にある

`pipeline/salary35/Edinetcode.zip`（EDINETコード一覧）に **`提出者法人番号` 列**があり、**1,867社すべてに値が入る**（欠損0）。法人番号は Wikidata のプロパティ **P3225** なので、外部データにそのまま繋がる。証券コードと違い、上場・廃止で変わらない。

### Wikidata との突合（1,867社を SPARQL に投げた実測）

| | 件数 | 率 |
| --- | ---: | ---: |
| Wikidata に項目がある | 1,656 | 88.7% |
| 公式サイトURL（P856）を持つ | 1,604 | 85.9% |
| ロゴ画像（P154, Wikimedia Commons）を持つ | 522 | 28.0% |

**Wikidata に項目が無い211社には、ロゴを得る手段が現状無い。** 非上場・小規模の会社が中心である。

### Commons のロゴは大半が横長ワードマークだった

522件から120件を抽出して Commons API で実寸とライセンスを見た。

| | 結果 |
| --- | --- |
| アスペクト比（横/縦） | **中央値 3.8:1**。3.0超の横長が60%、ほぼ正方形（1.3以下）は**11%だけ** |
| 形式 | SVG 425件（81%）・PNG 53件 |
| ライセンス | Public domain 107/120（PD-textlogo）、CC BY-SA 4.0 が6、CC BY-SA 3.0 が4、CC BY 2.5 が2、CC0 が1 |

**これが器の設計を決めた。** 40px 角の枠に 3.8:1 のワードマークを入れると高さ10pxの帯になり、狙いと正反対の「ぼやけて怪しい」見た目になる。正方形の器を維持するなら Commons は全体の3%しか寄与しない。**運営者の判断で器のほうを見直す**ことにした（2026-08-21）。

### 公式サイトのアイコンは「あるが小さい」

120社の公式サイトを実際に叩き、`apple-touch-icon`・`sizes` 付きの `<link rel=icon>`・**web app manifest の `icons`**・`/apple-touch-icon.png`・`/favicon.ico` を辿って、取れた画像のヘッダから実寸を読んだ。

| 下限 | サンプル120社 | 全1,867社への換算 |
| --- | ---: | ---: |
| 何かある（16px 含む） | 87% | 74% |
| 64px 以上 | 61% | 52% |
| 96px 以上 | 48% | 42% |
| **128px 以上** | **47%** | **40%** |
| 192px 以上 | 25% | 21% |

**96px と 128px の差は2ポイントしかない。** 下限を下げても大して増えないので、128px に引くのが素直だった。64px まで下げれば+12ポイント買えるが、そこは Retina で1.6倍しかない「やや甘い」層である。

### 合わせての到達率は約53%

サンプル120社のうち「128px以上のアイコン **または** Commons のロゴ」を持つのは 74社（62%）。公式サイトURLを持つのが85.9%なので、**全体では約53%＝おおよそ2社に1社**。残りは頭文字マークのままになる。

## 既知の限界

**半分は埋まらない。** 上のとおり。カバー率を上げる手段（解像度を下げる・第三者のロゴAPIを使う）はあるが、いずれも H3 と衝突するか、後述の「作らないもの」に当たる。

**リブランドに即応しない。** 取得は年1回のデータ更新に合わせる。ロゴを変えた会社は最大1年古いままになる。

**ロゴが並ぶと行あたりの情報量が増える。** ランキングの行は U13 でモックに合わせたばかりで、器を広げるぶんモバイル360pxの社名の幅が削られる。ここは L1 の設計で詰める。

**ランキングの「操作でネットワークが発生しない」不変条件に穴が開く。** 絞り込み・並び替え・ページ送りで行が入れ替われば、新しいロゴ画像のリクエストが出る。E2E は現在リクエスト数を0で固定している（`e2e/ranking-refresh.spec.ts` ほか5箇所）。**画像を例外にする**——HTML/RSC を取りに行かないことが元々の主旨で、そこは変わらない。

## 作らないもの

**OpenWork からのスクレイピング。** 親 Issue に候補として挙がっているが採らない。規約上の複製・転載の禁止に正面から当たるうえ、ロゴの権利者ですらない第三者から取る形になる。

**ランタイムでの外部ロゴAPI（logo.dev 等）へのホットリンク。** 読者のIPが第三者に渡り、「DBも外部APIも持たない」（product.md）構成が崩れる。Clearbit の Logo API は2025年に終了しており、この種のサービスは寿命も読めない。

**ロゴの加工。** 色を抜く・角を丸める・単色化するといった変形はしない。商標をそのままの形で出す。

**ロゴを検索・絞り込みの対象にする。** ロゴは目印であって属性ではない。

**211社ぶんの手作業での収集。** Wikidata に項目が無い会社を人手で埋める運用は、運営者1名・2026年10月以降は工数がほぼ取れない（product.md）前提と噛み合わない。
