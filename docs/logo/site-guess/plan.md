# plan.md — L2 英字社名からの公式サイト推定を測る

Issue: [#243](https://github.com/varmil/nenshu/issues/243)（親: [#23](https://github.com/varmil/nenshu/issues/23)）
spec: `docs/logo/spec.md` 1.1（どこから取るか）・AC-3（到達率）
ADR: `docs/adr/0008-company-logo-sourcing.md` 決定1・決定3

**測って採否を決める Unit。** 実装を足すことが目的ではないので、**「入れない」で終わる道筋を最初から工程に入れておく**（下の「打ち切る条件」）。

## 手順

### 1. 母集団を2つ切り出す

- **測定用**: いま公式サイトのURLが分かっている会社（Wikidata の P856 または gBizINFO）。ここから**無作為に500社**を抜く。乱数の種を記録し、同じ標本を後から再現できるようにする
- **判断用**: ロゴが出ていない271社のうち英字名を持つ211社

**先に測定用を回す。** 判断用で当てるのは、precision が条件を満たしてからにする。

### 2. 候補を作る規則を書く

英字名を受け取ってドメイン候補の配列を返す純粋関数を書き、Unit テストを付ける。**取得はまだしない**——規則だけを先に固めて、テストが通ってから外へ出る。

### 3. 検証する規則を書く

HTML を受け取って「その会社のサイトか」を真偽で返す純粋関数を書き、Unit テストを付ける。**ここが precision を決める**ので、通す例より**落とす例を先に書く**（別会社のサイト・ドメイン売却のパーキングページ・検索結果ページ）。

### 4. 測定用500社で測る

候補を順に叩き、検証を通った最初のものを「推定結果」とする。既知のURLとホスト名で突き合わせて、recall と precision を出す。**95%区間まで出す**——点推定だけだと標本の揺れを採否の根拠にしてしまう。

**取得は並列3まで。** 測定のために他社のサーバーを叩くので、本番の取得と同じ礼儀にする。

### 5. 打ち切る条件を先に見る

**precision が 0.99 を下回ったら、ここで止めて「入れない」を結論にする。** 検証の規則を作り直して測り直すのは1回まで——2回目からは規則を標本に合わせているだけになる。

### 6. 判断用211社に当てて、見込みを出す

新規に到達する社数を数える。**この数字は「増える見込み」であって成果ではない**——実際に増やすのは採否が決まった後の別 Unit。

### 7. 無作為30社を目視する

211社から無作為に30社抜き、推定したドメインが本当にその会社かを目で見る。**測定用の集団は有名・老舗に偏っている**ので、この工程が偏りの補正になる。**誤りが1件でも出たら precision の実測を信用しない。**

### 8. 判断を書き残す

`design.md` に、採否とその根拠・測った数値・却下した案を残す。**「入れない」結論でも残す**——次に同じ案を思いついた人が測り直さずに済む。

## 検証の順序

| 工程 | 何で確かめるか |
| --- | --- |
| 2・3（規則） | Unit テスト（`npm --prefix pipeline test`） |
| 4（測定） | 実データ。標本と乱数の種を記録 |
| 6（見込み） | 実データ |
| 7（目視） | 人が見る。**機械の判定を信用しない工程なので自動化しない** |

**画面は変わらないので E2E は増えない。** 既存の E2E が緑のままであることは確かめる（L0 と同じ形）。

## この Unit で触らないもの

- `web/` 以下すべて。表示は1文字も変わらない
- `candidates.ts` の `PINNED`。流し込みは採否が決まってから
- `logos.json` と `web/public/logos/`。**測定は成果物を書き換えない**
